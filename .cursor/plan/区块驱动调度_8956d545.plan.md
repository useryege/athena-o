# 区块驱动项目调度重构

## 当前问题定位

现有调度器在 `[/home/yege/work/athena/internal/application/project_scheduler.go](/home/yege/work/athena/internal/application/project_scheduler.go)` 中把三类任务都放入同一个 heap：

```go
const (
    sourceCodeTask    ProjectSyncTaskKind = "source_code"
    pairDiscoveryTask ProjectSyncTaskKind = "pair_discovery"
    pairSnapshotTask  ProjectSyncTaskKind = "pair_snapshot"
)
```

其中 `pairSnapshotTask` 通过 `PairSnapshotInterval` 周期重排，和“每个新区块刷新所有项目状态”的目标不一致。现有 `[/home/yege/work/athena/internal/application/block_watcher.go](/home/yege/work/athena/internal/application/block_watcher.go)` 继续作为项目发现组件，不承载状态刷新触发职责。

## 目标设计

- 合约源码：独立分钟级节奏，默认 `1 * time.Minute`；每分钟尝试一次未完成源码获取，完成后 `SyncSourceCodeOnce` 自身会快速返回。
- 其他链上字段：由新区块 header 事件触发；每收到一个新区块，调度器读取 registry 中所有 project，并发刷新每个 project 的链上状态。
- 项目发现：保持当前 `BlockWatcher -> ProjectFilter -> Registry` 逻辑不变，不在这次重构里调整项目发现的扫描方式、起始块或输出语义。
- 新区块事件：新增独立线程/组件订阅最新区块号，只负责向调度器发送“新区块产生”的刷新事件。
- 刷新一致性：每轮链上读取必须固定到同一个 `blockNumber`，避免 100-200 个 project 在刷新过程中混入不同区块的状态。
- 性能边界：调度器采用 latest-wins 全局刷新 epoch，不为过期 block 堆积任务；当刷新还未完成又来了新区块时，只记录最新区块，当前轮结束后立即追最新轮。
- 字段分层：源码低频刷新，静态字段成功后不按块刷新，动态字段按新区块刷新，pair discovery 仅在 pair 未创建前按块检查。
- 批量读取：每轮全量刷新先构建 call plan，优先使用 JSON-RPC batch 或 Multicall3 在同一个 block 上聚合读取，避免 100-200 个项目把节点打成 1200-2000 次独立 RPC。

## 实施步骤

1. 新增新区块事件订阅组件
  - 新增独立类型，例如 `BlockEventSubscriber`，内部使用 `SubscribeNewHead(ctx, headers)` 订阅最新区块。
  - 每个 header 到达后，只输出 block number 到 `blockCh chan<- uint64` 或等价回调，不参与项目发现和合约创建交易扫描。
  - 处理订阅错误：订阅异常时退出并记录错误，保留 `ctx` 取消语义。
  - 不修改 `[/home/yege/work/athena/internal/application/block_watcher.go](/home/yege/work/athena/internal/application/block_watcher.go)` 当前项目发现行为，除非服务装配需要最小化生命周期接线。
2. 重塑 `[/home/yege/work/athena/internal/application/project_scheduler.go](/home/yege/work/athena/internal/application/project_scheduler.go)`
  - 移除 `pairSnapshotTask` 的时间间隔驱动，废弃 `PairSnapshotInterval`。
  - 引入两个内部循环：
    - `sourceCodeLoop`：`time.Ticker(SourceCodeInterval)` 每分钟遍历 registry，执行 `SyncSourceCodeOnce`。
    - `blockRefreshLoop`：消费新区块事件，维护全局刷新 epoch，并触发所有 project 的链上状态刷新。
  - `blockRefreshLoop` 使用 latest-wins 状态机：
    - 收到新区块时更新 `latestBlockNumber`。
    - 如果没有刷新在跑，立即启动一轮全量刷新。
    - 如果已有刷新在跑，只设置 `dirty=true`，不追加过期 block 的项目任务。
    - 当前轮完成后，如果 `dirty=true`，清除 dirty 并使用最新 `latestBlockNumber` 立刻再跑一轮。
    - 永远不为旧 block 堆积 100-200 个 project 任务。
  - 每轮刷新开始时先 `registry.ListProjects(ctx)` 获取项目快照，释放 registry 锁后再做 RPC。
  - 每轮刷新把 block number 传入同步层，所有链上读取都使用该固定 block number。
  - 保留 worker pool 作为 fallback 或非 batch 路径的并发上限，默认建议 `32`，最大建议不超过 `64`；不要无限 goroutine。
  - `EnqueueProject` 只负责新项目进入后尽快做一次源码尝试，并请求一次最新区块状态刷新，不再启动 pair discovery 的指数退避周期。
3. 调整 `[/home/yege/work/athena/internal/application/project_sync.go](/home/yege/work/athena/internal/application/project_sync.go)`
  - 新增 `SyncProjectStateOnce(ctx, blockNumber, project)` 或批量版本 `SyncProjectStatesOnce(ctx, blockNumber, projects)`，表示“除源码外的链上状态刷新”。
  - 内部整合现有 `SyncPairDiscoveryOnce` 与 `SyncPairSnapshotOnce`；pair 未创建时只做 discovery，pair 已存在时刷新 snapshot/simulation/liquidity/reserve 等字段。
  - 字段刷新策略：
    - `SourceCode` / `SourceCodeABI`：源码循环每分钟获取一次。
    - `Name` / `Symbol` / `Decimals` / `Token0` / `Token1`：基本静态，创建后成功一次即可，不随每个新区块刷新。
    - `TotalSupply` / `BalanceOfPool` / `WethBalance` / `Reserve0` / `Reserve1` / `BlockTimestampLast` / `LockedLiquidity` / simulation：按新区块刷新。
    - pair discovery：`IsContractCreated=false` 时每块检查；一旦创建，后续只刷 snapshot 类动态字段。
4. 新增按固定 block 聚合读取接口
  - 在 `[/home/yege/work/athena/internal/application/evm/fetcher.go](/home/yege/work/athena/internal/application/evm/fetcher.go)` 或新的 batch fetcher 文件中增加批量状态读取接口，例如 `FetchProjectStatesAtBlock(ctx, blockNumber, projects)`。
  - 每轮全量刷新构建所有 project 的 call plan，再一次性执行，返回 `map[projectID]snapshot` 后统一写回 `FieldValue`。
  - 初版优先使用 `rpc.Client.BatchCallContext` 降低网络 RTT；如果 Multicall3 合约地址已知或可配置，再切换为 Multicall3 实现。
  - 接口边界保持稳定：调度器和 `ProjectSync` 只依赖“按 block 批量拿 project 状态”的抽象，后续从 JSON-RPC batch 换成 Multicall3 不改调度器。
  - batch 调用允许部分失败：单字段失败只标记对应 `FieldValue.MarkFailed`，不要让整轮刷新全部失败。
5. 更新 `[/home/yege/work/athena/internal/application/service.go](/home/yege/work/athena/internal/application/service.go)`
  - 创建 `blockCh` 并传给 `NewProjectScheduler` 与新增的新区块订阅组件。
  - 如果采用 JSON-RPC batch，启动链路需要保留底层 `*rpc.Client`，用 `ethclient.NewClient(rpcClient)` 构造现有 `nodeClient`，并把 `rpcClient` 注入 batch fetcher。
  - 现有 `BlockWatcher` 和 `ProjectFilter` 仍按当前方式启动，继续负责项目发现。
  - 启动顺序保持：scheduler 先启动，新区块订阅组件与 block watcher 再产出事件，project filter 继续处理新增项目。
  - Stop 流程保持 `ctx cancel -> watcher/filter/scheduler/subscriber Stop`，避免关闭 channel 时仍有发送者。
6. 更新测试
  - 重写 `[/home/yege/work/athena/internal/application/project_scheduler_test.go](/home/yege/work/athena/internal/application/project_scheduler_test.go)`：
    - 验证源码按 `SourceCodeInterval` 执行，不再指数退避。
    - 验证收到一个新区块后会对 registry 快照中的所有 project 发起一轮固定 block number 刷新。
    - 验证刷新进行中连续收到 block N+1/N+2 时不会堆积旧任务，只在当前轮结束后使用最新 block 再跑一轮。
    - 验证 `Stop` 在 source ticker、block event loop、worker 都存在时能退出。
  - 为新增的新区块订阅组件补测试时优先抽接口封装 eth client，避免真实 RPC 依赖。
  - 为 batch fetcher 补单元测试：确认 call plan 使用传入的 block number，并能处理部分字段失败。

## 预期影响

- `ProjectSchedulerOptions` 会从 `InitialDelay/MaxDelay/PairSnapshotInterval/PairDiscoveryMaxAttempts` 这类退避参数，收敛为 `WorkerCount/QueueCapacity/SourceCodeInterval` 以及必要的 block refresh epoch 合并参数。
- 新增的新区块订阅组件依赖 WebSocket RPC；当前 CLI 已使用 `--node-ws-url` 和 `ethclient.Dial`，符合 `SubscribeNewHead` 的前提。
- 每块刷新所有项目会显著增加 RPC 调用量；实现时需要把 batch/multicall、固定 block number、worker 上限和 latest-wins epoch 作为第一优先级，避免项目数增长后拖垮节点。
- 对 100-200 个 project，不应让每个新区块展开成无界 goroutine 或过期任务队列；系统应优先追最新块状态，而不是保证每个历史块都完整刷新。
