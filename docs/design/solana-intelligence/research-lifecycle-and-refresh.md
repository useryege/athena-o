# Solana 持续研究与刷新调度

> 阶段调整：用户要求先完成发现与列表，本文件的研究与活动刷新全部延后；保留业务决定及未决建议，不作为首版实现或验收前置。

>
> 关联需求：[Solana 项目研究](../../requirements/solana/README.md)。发现入口见[新项目发现方案调研](project-discovery.md)。

## 已确认的业务约束

- 新项目发行被观测后进入持续研究。首次交易、项目年龄和无活动时长都不使研究自动结束。
- 创建与初始买入发生在同一交易，不影响项目进入持续研究。
- 交易或其他认可的链上活动触发资料刷新；完整活动清单仍待确认。
- 每项目最多每一小时发起一轮刷新，下一轮至少间隔一小时；不同项目独立计算，不能使用按自然整点重置的计数代替。
- 资料限频不降低活动监听频率。长期静默项目仍被监控，活动恢复后无需重新建立研究资格。

本文不为 Solana 引入 EVM 的 Swap 停止、观察期到期、续期截止时间及事实冻结状态。进程故障或运维停机属于服务恢复问题，不等同于项目业务研究结束。

## 建议的调度语义

本节是对已确认规则的实现建议，计时锚点、首次采集、失败重试及待刷调度细节仍需在完整设计中确定。

### 首次采集与时间锚点

首次发现立即安排项目初始采集。建议将首次采集作为第一轮刷新，以每轮实际开始刷新时间计算下一次最早允许时间：上次开始时间加一小时。仅排队或等待配额不消耗该时间窗口。

“实际开始”需要由后续持久任务模型定义原子准入与恢复语义；本文不承诺外部调用恰好执行一次。计时针对逻辑刷新轮次，不代表一轮只有一个 RPC 请求；一轮的采集项、外呼预算及重试计数尚未设计。

### 活动合并与到期调度

1. 监控识别活动后，保存活动依据并记录该项目有待刷新需求。
2. 当前无在途刷新且已满足一小时间隔时，可以启动一轮刷新。
3. 冷却期内的新活动合并到同一待刷新需求，不按活动数量创建逐次补刷队列。
4. 有待刷新需求时，在到达最早允许时间后调度一次；无需等待另一笔新活动来唤醒。新活动不延后已有截止时间。
5. 没有待刷新需求时，到期本身不触发资料采集；监控继续进行。
6. 同一项目已有刷新执行时，不同时启动第二轮；到期但仍在运行的项目等待本轮结束后重新判断。

限频给出可启动的最早时间，未承诺在到期时立即完成。共享资源不足时仍需公平推进，并展示排队与延迟；容量和时效目标待定义。

### 活动覆盖与并发

每轮刷新需要记录自己覆盖的活动范围。只有已经被本轮资料覆盖的活动需求才能完成；执行期间到达、且未被本轮采集覆盖的活动仍待下一次允许刷新。

后续持久化设计应保证：新活动登记与刷新完成并发时不丢需求；多个执行者不能为同一项目各自获得一次刷新资格。活动版本、时间或链上位置如何表示，随确认等级与证据模型一起定义。

## 建议行为示例

下例以“刷新实际开始时间”为计时锚点，假设资源可用且每轮在下一允许时间前结束；它说明建议语义，不是性能验收结果。

| 时间/事件 | 行为 |
| --- | --- |
| 10:00 首次发现并开始采集 | 进入持续研究，下次最早允许刷新为 11:00 |
| 10:10 至 10:50 发生 40 次活动 | 持续记录活动，合并一项待刷新需求 |
| 11:00 到期 | 即使最后一次活动发生在 10:50，也安排一次刷新，不补做 40 次 |
| 11:00 之后没有新活动 | 12:00 不因整点自动采集，监控保持 |
| 第十天再次发生认可活动 | 仍可触发刷新，不需要重开项目；继续受本项目间隔限制 |

## 故障与恢复要求草案

- 活动合并、时间约束和在途状态需要持久保存，进程重启不能把所有项目重置为立即可刷新，也不能丢失已记录的待刷新需求。
- 冷却到期期间服务离线，恢复后重新判断到期需求并合并处理，不能为停机期间每个小时补做一次无活动依据的刷新。
- 失败时保留未完成需求与已有有效资料，失败不能产生项目研究结束状态。
- 失败尝试是否占用一小时、同轮技术重试是否允许在窗口内执行、次数与退避仍待确认。不能默认通过把新调用标为重试来绕过资源限制。
- 节点离线或证据不完整须显示监控/覆盖异常，不能解释为项目没有活动。历史补查触发刷新时如何避免重复刷新，随活动证据去重模型细化。

这些是后续设计必须核对的问题，当前没有相应数据库字段、任务执行器或恢复实现。

## 服务边界与实施范围

持续监控与持有持久调度状态的业务能力须遵守 [SDS-R1 至 SDS-R8](../../developer-guide/service-development-standards.md)，在独立业务进程中运行；API 不承载其后台循环。具体服务数量、职责 owner、同步接口、事务、授权、配置、资源配额及独立运行入口尚未设计。

本轮仅新增和同步文档，适用 SDS-R7、SDS-R8 的事实记录及静态检查；没有新增代码、RPC 或运行命令，也不表示完整服务边界方案已经完成。

## 后续验证场景

已确认规则需要验证：首次交易不停止、长时间静默不结束、第十天及以后仍响应活动、每项目独立限频、跨自然整点不突破一小时约束、监听不随刷新冷却暂停。

建议语义确认后还应验证：首次采集立即安排、窗口内多次活动到期仅补刷一次、持续活动不推迟截止时间、无活动不周期采集、在途新活动不丢失、同项目不并行刷新、多执行者竞争、重启恢复及刷新失败。失败重试的预期必须先依据已确认计数规则定义。

当前仅完成需求映射与调度草稿，未运行目标流程或性能测试。
