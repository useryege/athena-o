# Polymarket 结算领取、持仓与历史同步

> 设计状态：本段设计已确认。2026-09-15，用户回复「認可」，确认第三段手动领取、全部持仓与买卖历史、同步覆盖和页面状态详细设计；此前已认可[账户接入](polymarket-account-onboarding.md)及[报价、交易执行与资产占用](polymarket-trade-execution.md)。设计确认不表示相应功能已经实现，也不表示真实领取或完整资产验收已通过。

业务依据为[手动交易需求](../../requirements/polymarket-copy-trading/copy-trading.md)和[已确认的页面组织](../web-ui/trader-sync-manual-trading.md)。普通市场与 Neg Risk 单个选项支持手动操作；Combo 沿用既有只读展示范围，本段不新增 Combo 专项研究。绑定前、其他渠道和已解绑钱包的持仓／历史继续保留。

## 1. 方案和证据边界

采用交易服务内的「原领取尝试核对＋当前资产核准＋历史持续同步」三类处理任务，分别配置并发预算。页面读取本地投影并显示数据时间，执行资格读取本次必要事实。与只依赖当前持仓列表相比，这个方案能保留小额、归档和历史关联；与等待全历史后才开放操作相比，它落实已经确认的当前条件就绪即可交易规则。

## 2. 领取到底处理什么

### 2.1 先核准协议，再决定范围

产品选择的是实际钱包、市场与持仓。后端通过已核准的市场映射、资产合约、资产 ID 和部署版本选择执行路径，不能让用户输入任意 adapter、接收人或 calldata。

| 路径 | 本次领取范围 | 确认及占用方式 |
| --- | --- | --- |
| 普通 CTF 市场 | 经核准 `CtfCollateralAdapter` 的市场领取；当前官方示例为两侧 index set `[1,2]`，没有数量参数 | 展示该市场两侧全部余额及各自兑付额，包含会被处理的零兑付份额；取得该实际账户、市场和相关资产的完整范围占用 |
| Neg Risk 的一个候选市场 | 经核准 `NegRiskCtfCollateralAdapter`，以该候选市场的 condition 为范围 | 同样展示实际影响的 Outcome；不扩大到整个多候选事件，也不执行转换其他候选份额的操作 |
| SDK 所称 protocol V2 的独立 YES／NO position | 已核准 Router 的 `redeem(condition, outcomeIndex, amount)`，数量明确 | 只构造此次选中 Outcome 的明确数量；不直接调用可能展开两侧余额的通用 market 工作流 |
| 不明协议、控制关系或领取影响 | 不生成可发送调用 | 保留仓位及具体待核对原因，不靠 ID 长度、SDK 旧函数名或市场标题猜测 |

SDK 中的 protocol V2 position 命名与 CLOB Exchange V2／V3 版本不能混为一谈；能解码一个 position ID 也不证明它属于首版允许操作的单个市场。普通单 Outcome 与 Combo 的业务分类必须独立验证，不能因为旧函数名包含 Combo 就误排除普通仓位，也不能放行真正的 Combo。

同一产品市场若存在不同资产协议的余额，分别列出其实际资产身份。本次不将不同协议、其他市场或其他 Wallet 余额暗中拼成一个领取批次，不增加跨市场「全部领取」功能。

### 2.2 数量与实际兑付额

预览核对实际账户控制、正确资产合约上的余额、condition 与 Outcome 映射、最终结算状态、兑付分子／分母、必要授权、费用及占用。`closed=true`、到达市场结束时间、`redeemable=true` 或参考价格为 1，都不能代替完整领取资格。

对已核准的 CTF 独立 index set 路径，以基础单位计算每项 `floor(balance_i × numerator_i / denominator)`，再合计；分母须为正，按真实合约的分组与舍入顺序执行。[上游 ConditionalTokens 源码](https://github.com/gnosis/conditional-tokens-contracts/blob/master/contracts/ConditionalTokens.sol)及本次保存的 hash 支持这一算术顺序。不能先将所有小额份额合并再舍入，也不能假定兑付比例只有 0 或 1。Router／Neg Risk 包装与 pUSD 输出需分别核准，不能仅凭底层 CTF 公式宣布所有路径实测通过。

说明性例子：同一普通市场持有 YES 10 份、NO 3 份，若最终兑付比例为 1／0，领取预览列出「处理 YES 10、NO 3；预计到账 10 pUSD；NO 兑付为 0」。若最终比例为 1/2、1/2，则按真实精度算出各侧兑付并合计，不能仍显示 10。这些数字仅用于说明，未执行真实领取。

只有核准有正金额可领取时才给出确认领取入口。总兑付为零的仓位保留「暂无可领取资金」，不自动销毁份额清理列表。极小正金额保留实际精度，不因显示为两位小数而变成 0；gas 或费用与领取金额分别显示，不能把不同币种直接相减。未知费用不得填零。

**全余额路径的确认范围是所列市场／Outcome 在实际执行时的全部余额。** 当前金额是预览事实；发送前发现余额变化时刷新后重新确认。发送后其他渠道转入或转出仍可能改变实际处理数量，页面不能承诺只销毁快照里的固定份数；记录并展示原预览与实际差异。指定数量的 Router 路径则冻结已确认数量，不随新增余额自动扩大。

## 3. 从预览到到账的流程

### 3.1 需要准备时

领取所需的合约级持仓 operator 授权与买卖准备分别核对。现有授权已经满足时直接复用；缺少时在领取页说明对象、资产合约及持续权限范围，进入已有账户启用流程，**先由用户明确完成必要准备，再返回刷新领取预览并确认领取**。

复用 `PreviewTradingAccountEnablement`／`SubmitTradingAccountEnablement` 的已确认账户身份和分步恢复，增加受控的领取能力清单；只核准本路径所需授权，不让普通领取调用顺带自动补授权。`setApprovalForAll` 是合约级权限，不能将其描述为仅允许当前市场或本笔领取。准备不表示已经领取，记录仍位于钱包设置。

### 3.2 预览及明确提交

流程为：从持仓进入 → 核对钱包、完整影响范围及兑付金额 → 用户点击确认领取 → 处理／核对 → 展示实际到账。

- 预览沿用 15 秒的本地确认期限，返回时间、依赖版本及不可提交原因；没有买卖价格偏差输入，因为领取依据最终兑付规则。
- 同页显示实际账户、市场、将处理的全部 Outcome／份额、预估兑付、适用费用及到账币种。全余额路径明确写出「领取此市场所列 Outcome 的全部余额」，数量固定路径展示明确数量。
- 用户点击确认后建立独立 `REDEEM` 尝试，沿用当前登录、权限、唯一请求标识、不可变确认和派发门禁；旧 Wallet 是否仍绑定目标不改变领取账户。
- 接收与首次派发前复核余额、结算、授权、费用和范围。过期或事实改变导致原确认不再有效时，核准未发出后结束并刷新，不自动改参数或新建领取。
- 账户启用和当前领取是不同意图；准备完成、市场结算、页面打开和后台同步均不代替领取确认。

### 3.3 与其他操作的占用协调

具体数量路径预留明确份额；全余额路径还要取得该实际账户、condition、相关资产合约／Outcome 的范围占用。此范围内有未终结买卖、其他领取或可能改变余额的本地操作时，先核对原操作；不能只用「余额减掉部分预留」让全余额调用处理剩余部分。

全余额领取未终结期间，后续新到达同范围的份额也不能在 ATHENA 再卖出或领取；它们可能被原调用一并处理。其他市场和独立可核准资产继续使用，pUSD 待到账不能提前花费。该范围占用仍是本地协调，不能拦截外部渠道的转账或交易。

在第二段已确认的账号 → 账户／绑定 → 资源 → 尝试锁顺序内，资源阶段先锁统一的市场范围记录，再按规范资源键锁具体资产；买卖与领取都参加范围检查，避免全余额领取与并发提交互相穿过。锁仅持有至接收／投影事务结束，长期约束保存在占用记录中。

### 3.4 签名、发送与核对

新增目标签名 RPC `SignPolymarketRedemption`，仅给交易服务专用身份；Wallet 验证可信 owner、实际账户、原尝试与步骤、执行路径、已核准目标合约、condition、Outcome／数量或全余额范围、调用值和完整批次。到账对象固定为本次实际交易账户，不能接受任意转出地址，也不能把领取扩展为通用合约调用。

Deposit／Proxy／Safe 使用各自已经核准的调用与 nonce 语义；直接 EOA 单列链上 gas 与 nonce 协调。不能把 EOA 多次独立交易描述为合约钱包的原子批次。首版按上述路径构造最小领取动作，不直接继承 SDK 通用 market 工作流的多次调用、重签或重发副作用。

复用第二段的持久原包和一次派发协议。冻结钱包 nonce、接收范围、完整 calldata／batch、链上期限和费用约束；平台超时、页面关闭、重启或签名期限到期都不自动换 nonce 重发。已有可能发出的请求先查原 Relayer 记录、确切交易与资产影响；无法核准关联的相似领取不能认作本次成功。

Relayer 受理、外层交易成功和账户内领取成功分别核对。不能只凭 HTTP 成功、交易 hash 或外层 receipt 状态宣布到账；须检查该钱包协议的内部执行结果、准确的领取／销毁事件、实际 pUSD 到账和对应最终性。并发外部活动可能改变总余额，因此「余额比之前多了」也不证明本次领取成功。

| 核准结果 | 页面及账本处理 |
| --- | --- |
| 明确未发出 | 保留原因，释放已作废且确未派发尝试的占用；新操作须重新确认 |
| 已受理／链上处理中 | 显示处理阶段、原记录和可核准标识；继续占用相关范围 |
| 请求超时、关联不明或内部结果不明 | 待核对；不自动重发、不因超时释放 |
| 链上失败且已终结 | 显示实际失败、已发生的费用及原记录；重新核准资产后释放 |
| 精确领取成功并最终确认 | 显示实际处理份额、兑付及费用；关联系统记录和链上证据 |
| 成功已证实、资产列表尚未追上 | 显示「领取成功，持仓更新中」；用已确认影响协调占用，不提前或重复计入资金 |

其他渠道先完成了领取时，刷新可显示当前已无可领取份额；这不自动证明 ATHENA 原尝试成功。后续账户重新收到同类资产，也不会触发原尝试再次执行。

## 4. 全部持仓的发现与展示

### 4.1 当前资产与参考数据分开

仓位唯一身份为 `chain + 实际账户 + 资产合约 + asset_id`；市场／Outcome 为核准关联，Wallet 为访问和展示关联。不能只按市场合并不同钱包、合约或协议中的余额。

| 信息 | 使用方式 |
| --- | --- |
| 当前持有份额 | 来源、区块／快照、读取时间与核准状态一起保存；缺失不等于零 |
| 当前可卖／可领取 | 消费实时必要事实和占用账本；列表参考值不作为执行许可 |
| 参考价格、市值、成本或盈亏 | 保留原来源和时间；历史不全时不自行补算完整成本或收益排名 |
| 当前绑定 | 帮助找到钱包；不改变仓位归属，也不把其他渠道的仓位归因于当前目标 |

金额、份额和 ID 保留十进制／整数精度；解析上游 JSON 数字时不得先转浮点数再推回原值。支持金额为 0、未知和极小正数的不同表达。

### 4.2 发现范围与缺口补齐

1. 对已接入的实际账户读取普通持仓 OPEN 和 CLOSED。OPEN 显式包含归档市场；CLOSED 不携带会被拒绝的 `include_archived=true`。全量盘点不加会排除无 `last_event_at` 记录的时间过滤。
2. 小额过滤按已核准接口可表达的最低有效值读取；0 不一概代表取消过滤。两种状态的结果按真实资产身份联合，不按状态名称删掉正份额行。
3. 加入已知历史成交、领取、转移、绑定前记录和链上资产事件发现的候选 asset ID；对已知候选按正确合约核准余额与状态，补足 inactive 或列表遗漏的行。
4. 交易服务的自有账户扫描覆盖已核准资产合约的转入、转出、铸造／销毁事件及相应成交日志，从核准部署起点或更晚且有证据的账户起点开始，保存连续区块覆盖；无法证明起点时不能缩短成绑定日期。分段读取、分页与断点恢复独立于目标 Activity Alerts。
5. 链上扫描发现但暂不能映射市场的持有资产保留为资料待核对，按完整资产 ID 识别；不靠标题、Yes／No 标签或截断／补零猜测市场。

inactive 市场仍被普通列表排除，调小筛选并不能消除这个缺口。链上候选发现和余额核准是设计要求，不是此次已经完成的全量扫描；历史合约注册范围、节点归档能力和事件解码覆盖必须补证。读取历史上实际发生的成交属于当前用户的完整历史需求，不是保留旧 ATHENA 行为的兼容路径。

Combo 使用既有只读数据及映射规则承接，继续展示其已取得持仓／历史和覆盖状态，不新增执行入口，也不因本段未专项补证而伪称历史完整。

### 4.3 页面组织

沿用未结算、已结算、资料待核对三组；未结算优先，已结算组中可领取优先。仍有正份额的小额、零价值仓位保留；已核准余额为零的旧仓位进入历史，不因一个列表快照缺行就移走持仓。

每组都提供分页；钱包筛选包括仍属于用户的已解绑钱包。同一市场不同钱包分别展示。读取失败保留该钱包最后已知结果和时间，不把其他钱包清空。

打开卖出或领取时使用所点行的稳定身份，重新取得执行预览；列表刷新不得在同一个按钮下悄悄换成另一仓位。新数据提示更新，返回后恢复筛选和阅读位置。列表无数据时分别表达「已核准没有持仓」「筛选无结果」「首次同步中」「暂时读取失败」。

## 5. 历史事实、去重与系统记录

### 5.1 页面保持两个视图

「本系统记录」包括 ATHENA 买入、卖出及领取尝试的全部结果；「成交历史」包括该账户实际发生的全部买卖，默认时间范围为全部时间。账户启用仍在钱包设置追溯。

其他渠道的领取、转账、split／merge 等作为资产变动证据保留；仓位详情可查看相关领取记录，但不能冒充买卖或创建一个从未在 ATHENA 提交的系统尝试。本段不新增完整资金流水、收益分析或策略页面。

一条系统尝试可关联多笔真实成交。关联必须基于精确原订单、成交或链上事实，冻结当时来源活动与目标；没有可靠证据的成交显示未关联，不因钱包当前绑定推断来源。费用未取得时独立显示，实际本金或价格不能反推出未经核准的手续费。

### 5.2 三层身份与重复处理

| 层次 | 身份与用途 |
| --- | --- |
| 原始接口观察 | endpoint、账户、查询指纹、扫描代次、请求／响应游标及页内序号；保留原始行和重复行数量，不冒充稳定成交 ID |
| 链上或私有精确事实 | 已核准成交 ID；或 chain、block hash、tx hash、log index、批次元素／经济角色等足以区分事实的标识 |
| 产品记录 | 服务端稳定 ID、canonical 关联及核准状态；跨来源指向同一经济事实时合并展示，保留全部来源 |

当前公开成交样本没有逐笔 ID；游标中的服务端排序锚点也不是响应承诺的可用业务主键。不能按交易 hash、时间＋token、或完整 JSON hash直接唯一去重，同一交易可能产生字段完全相同的多次成交。

每次固定窗口扫描在临时代次中保存完整多重集合，分页重试只替换该请求页；完成后原子替换该来源、该窗口的观察集，不能把重叠窗口简单追加。尚未取得 canonical 关联的行保持来源待核对和实际数量，不与另一个来源重复加入同一产品成交列表。Activity 交叉检查与 Trades 主观察共同提供证据，不能当两套成交相加。

补取收据及核准事件后展开同一交易中的各次成交，匹配账户方向、资产、数量、角色和金额；关联不唯一时保留组级待核对，不任选一个日志。跨市场买卖历史仍按自有账户查询并在本地筛选，不能为了市场筛选切换到带固定三年窗口的上游查询而丢失更早事实。

区块重新组织、索引修正或迟到事实更新原观察的版本和 canonical 关系，回退受影响投影并重算；原用户确认与审计记录不删除。成交核对与资产占用修正使用相同确认依据，防止历史已回退而可用资金仍沿用旧成功结果。

## 6. 同步流程、覆盖与分页

### 6.1 初次和持续同步

1. 接入后优先盘点当前候选持仓、当前操作必要事实及未决尝试；可核准操作不等待旧历史。既有小额、零价值与缺失状态从第一次返回起就保留。
2. 历史以实际账户为锚点，成交显式 `taker_only=false`、完整起点 `start=1`，保留经过验证的小额过滤；Activity 按需要的事件类型取得对照。每轮冻结结束时间，游标翻页始终保留原账户、方向和筛选参数。
3. 数据按较新窗口优先读取，再向更早时间推进；窗口边界处理同秒多条记录，不能简单把最后一行时间减一秒当游标。窗口拆分与重叠回扫通过前述观察代次及精确事实关联去重。
4. 近期同步反复回扫覆盖上游实际滞后和链上最终性的不稳定区间；固定回扫分钟数不足以覆盖任意迟到修正，因此另保留历史分段复查。采集或投影停顿时扩大回扫起点，不能从最新时间直接续上跳过缺口。
5. 已知 asset ID 的余额更新、无时间过滤的周期盘点与连续链上扫描并行承接新增仓位；仅按 `last_event_at` 增量拉取不能发现所有无原生经济时间的记录。
6. 每页数据和对应断点同事务落库，完成后才推进覆盖；重启从持久游标／区块继续。游标失效时回到原窗口重新读取，不跳到下一窗口或清空已展示数据。

源索引到哪个区块、实际返回哪个时间段、当前账户覆盖到哪里分别记录。Data API `/v2/status` 可说明整体服务滞后，但不能充当每个请求都有一致快照的证明；无法取得稳定快照时通过分段重读、链上核对和缺口标记承接，不宣称跨接口原子一致。

### 6.2 覆盖状态不伪造百分比

按实际账户和数据集分别保存已读取时间／区块区间、角色、金额下限、市场状态／协议范围、已完成页、下一游标、来源版本、检查时间、缺口及错误。

| 状态 | 页面含义 |
| --- | --- |
| 首次同步中 | 展示已取得记录、数量及正在读取的范围；未知总数时不编造百分比 |
| 已更新至某时刻 | 说明这份数据的时间，不代表更早历史全部齐全 |
| 存在待核对范围 | 明确缺少的时间、资产、市场状态或来源；已取得记录仍可查 |
| 暂时失败／延迟 | 保留最后成功结果和时间，说明当前来源；后台继续有界重试 |
| 本范围核对完成 | 只有对应范围的查询、连续链上覆盖及关联验证均满足时才成立；不能扩展成任意钱包的全历史保证 |

持仓全集、历史买卖覆盖、当前余额可用性和某次尝试是否结束，是四个不同状态。任何一项不能替其他项宣称完成。没有已核准的完整边界时，不显示「全部同步完成」。

### 6.3 本地阅读分页

API 读取稳定本地投影，返回视图版本与 keyset 游标。分页绑定 owner、筛选、排序和视图版本；保留该版本的必要投影供连续阅读，初始保留期限为 10 分钟。期间的新事实可以提示刷新，但不改变正在翻页的集合；版本过期时保留筛选并明确重新加载，不能静默从新集合中间续接。

服务端默认每页 50、上限 100 条；各分组独立游标和已知数量，不以当前页长度作为总数。前端不显示或解释上游原始游标。列表的旧视图版本不授予交易资格，进入操作仍重新核准当前事实。

## 7. 持久对象、接口与运行边界

交易服务继续拥有自身状态，复用第二段已确认的数据库和资源协调方案；不新增独立资产服务或消息中间件。

| 对象／接口 | 目标职责 |
| --- | --- |
| RedemptionPreview／REDEEM attempt | 保存影响范围、兑付事实、准备要求、费用、确认摘要、期限、步骤、原包和核对结果 |
| PositionProjection／MarketIdentity | 保存真实资产身份、数量、元资料、证据、显示组和状态版本；不覆盖成当前目标来源 |
| SourceObservation／CanonicalFact | 分别承接原始接口观察和精确事件关联，保留多重性、版本和原始证据 |
| SyncCheckpoint／Coverage | 保存完整查询指纹、游标／区块、扫描代次、连续范围、缺口与错误 |
| `PreviewRedemption`／`SubmitRedemption` | 无副作用预览及接收一次明确领取；复用既有幂等、权限和派发协议 |
| `GetTradeAttempt`／`ListTradeAttempts` | 继续统一读取买入、卖出和领取系统记录，不另造含义重复的记录接口 |
| `ListTradingPositions`／`GetTradingPosition` | 返回持仓、核准状态、操作资格及范围内的关联记录 |
| `ListTradingTrades`／`GetTradingTrade` | 返回实际买卖及关联证据，不混入本地失败尝试或领取操作 |
| `GetTradingSyncStatus` | 按账户与数据集提供覆盖、时间和缺口，供页面一致展示 |

RPC 为目标契约，尚无新增 proto。读写沿用当前有效会员身份、Trader Sync 与 Wallet 权限、owner 范围及内部服务身份。权限失效时停止新的用户读取／提交和普通资产扫描；已发出尝试仅以专用后台能力完成原结果核对，不因此开放越权访问。重新授权后先核准当前资格，再从保存断点补齐。

结果核对、当前资产和历史补齐使用独立队列／并发上限，避免长历史挤占执行；调度保留历史工作的处理机会，不因持续出现新记录而永远不扫描旧历史。单次上游读取初始 deadline 3 秒，RPC 接收／预览预算沿用第二段；数据查询按限流退避，重试不触发任何买卖或领取。

区块扫描所需 Polygon RPC、已核准合约／部署范围及分页配置由交易服务自身声明和校验。节点不支持所需归档范围或来源不可用时，记录受影响覆盖，不关闭无关监控／通知服务。API 不持有交易 runtime，也不启动其后台扫描；共享数据库是已知共同故障域。服务停止时先停止新任务入队，有界结束当前请求并保存断点；停止不删除持仓、历史、占用或原始证据。

本段按[服务开发规范](../../developer-guide/service-development-standards.md)的 SDS-R1～R8 承接。代码实施时需提供最小依赖运行、deadline、故障隔离、恢复和停止证据；本次纯设计静态检查不代表这些要求已验证。

## 8. 本段验证与后续交付

本次完成官方文档／固定 SDK 源码核对、既有公开样本字段复查、兑付算术示例和文档检查。未发起真实领取、授权、合约模拟或全链历史扫描。

实施验收至少覆盖：

1. 普通 CTF／Neg Risk 全余额范围、普通独立 position 的明确数量、错误协议及 Combo 执行拒绝；同市场不同合约不误合并。
2. 正额、零额、50/50、精度尾数、结算争议中及未取得分母；领取准备与领取提交的分离。
3. 全余额领取时另一侧有份额、相关未决订单、签名前余额变化、发送后外部转入／转出；其他独立市场资产继续可用。
4. 不同钱包协议的实际内部执行结果、收据／事件／到账一致性、gas、并发 nonce、响应丢失及重启；链上失败不伪装成功。
5. OPEN／CLOSED 小额正余额、inactive／归档、无 `last_event_at`、链上转入新资产、元资料缺失和零余额历史。
6. maker／taker、绑定前及其他渠道成交、三年前窗口、小额边界、同秒多条及同交易多次相同成交；精确关联与观察多重集合不误去重。
7. 分页断点、查询条件保留、游标失效、窗口重叠、迟到修正、链重组、来源滞后和扫描中断；覆盖不能有静默空洞。
8. 稳定页面分页、视图过期、单钱包失败、已解绑钱包可见，以及不同用户／权限变化后的缓存隔离。
9. 已发出领取核对、当前资产和旧历史的资源隔离，长期任务有界停止与恢复。

本段尚需真实验证的关键项是实际 adapter／Router 部署、授权对象、兑付到账、历史合约覆盖和索引缺口补齐；来源不足不能被设计认可替代。本段已确认；[桌面／手机页面方案 v1](../../requirements/web-ui/trader-sync-manual-trading-proposal.md)已获认可；[完整规格](../../superpowers/specs/2026-09-15-trader-sync-manual-trading-design.md)已整合三段契约、验证缺口及页面内容，待整体审阅后编写实施计划。
