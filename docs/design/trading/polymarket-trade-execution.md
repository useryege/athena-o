## 1. 本段采用的方案与依据

采用「不可变报价与提交记录＋按资产记录占用＋原请求持续核对」。相比只依赖浏览器防重复，它能覆盖响应丢失和服务重启；相比冻结整个 Wallet，它保留用户已经确认的剩余资产可用规则。这两项取舍沿用既有确认，不重新作为业务选择。

| 核对依据 | 本段结论 |
| --- | --- |
| [官方下单说明](https://docs.polymarket.com/trading/place-orders)及固定 SDK | 市价买入 `amount` 是未含费本金；`maxSpend` 会调整签名本金。价格保护须落在实际整数金额上；FAK 允许部分成交并结束剩余量 |
| [市场费用字段](https://docs.polymarket.com/market-data/market-details#trading-fees)、[手续费](https://docs.polymarket.com/trading/fees)、[Builder 费用](https://docs.polymarket.com/programs/builders/fees) | 按实际市场和适用的 Builder 规则估算，不能把一个示例费率或 SDK 的预算换算当成费用保证 |

## 2. 用户看到的报价

### 2.1 报价内容及有效期

每份报价关联 owner、Wallet／signer、实际交易账户及映射版本、来源或仓位、市场／Outcome／资产标识、方向、用户输入、费用和协议版本。报价只读取事实，无签名、占用、授权或交易副作用。

页面主要信息：

- 买入：本金、参照卖一价、最高接受价、预计成交份额与均价、预计手续费、预计总支出、本次需要预留的金额、提交后预计剩余可用资金。
- 卖出：当前持有／可卖份额、选择比例及其计算基数、实际拟卖份额、参照买一价、最低接受价、预计收入、费用、净收入和预计余量。
- 盘口深度只能满足部分数量时，说明预计只能成交部分；预计成交额与用户计划本金分别保留。

**已确认报价有效期为 15 秒**，由后端返回 `issued_at`、`expires_at` 和服务器时间。有效期从组成报价的最早必要实时快照计算；不能把读取很久的盘口在返回页面时重新变成新报价。生成时盘口、当前资产与费用检查的读取年龄上限初值为 2 秒；链上区块确认策略另外记录，不能用「刚读取」替代区块时间或最终性。

1. 用户填写完整且有效的输入后取得报价；修改本金、比例、价格偏差或交易对象，原报价立即失效。
2. 报价展示后固定参照价和保护边界。行情更新可以显示为辅助信息，不能自动替换正在确认的内容。
3. 15 秒到期，保留输入，停用提交，显示「报价已过期，请刷新后确认」。刷新取得新的报价，用户再次点击确认；不增加内容重复的弹窗。
4. 服务端在合法接收和首次派发前都检查有效期；排队、签名或依赖读取用尽有效期时，以「未发出，需刷新报价」结束。不能把过期提交排入未来行情的自动执行队列。
5. 有效期内只有盘口价格或深度变化时，仍按原边界尝试；可能少成交或不成交。接收前账户或当前绑定变化，须取得新报价。合法接收后冻结原账户，随后目标换绑不改写这次尝试；仍按原账户复核操作资格。费用依据、协议、tick 或其他必须改变已确认交易内容的事实变化时，返回变化原因并要求新报价，不能替换后继续发出。

15 秒是 ATHENA 的报价确认期限，不是 Polymarket 承诺的成交期限。官方市价订单使用 `expiration=0`，该字段不能承担本地报价过期控制；已派发订单的延迟撮合和结算可继续超过 15 秒。客户端倒计时仅作展示，服务端权威时间及实际派发检查决定是否过期。

### 2.2 价格保护及金额精度

设参照价为 `p`，用户价格偏差为 `s`，价格步长为 `tick`。先计算用户边界，再选取不会放宽它的合法价格：

- 买入：`floor_to_tick(p × (1+s))`，并不高于市场允许的最高价。
- 卖出：`ceil_to_tick(p × (1-s))`，并不低于市场允许的最低价。

合法范围取当前已核准协议；没有可用价格则不构单。`s` 沿用已确认的 0%～99.99%、最多两位小数。参照价 0.53、偏差 2%、tick 0.01 的示例，买入边界收紧至 0.54，卖出边界收紧至 0.52；这是算法例子，不是实时行情或参数推荐。

金额、份额与百分比以十进制字符串接收，以整数／定点数计算和保存，禁止用浮点数直接参与签名金额、余额与占用比较。协议标识及六位基础单位按实际资产核准，不从页面格式反推。

当前已核对 SDK 的市价本金与卖出份额均按两位小数构造；本金表单因此接受最多两位小数，超精度明确报错，不能静默截掉用户本金。卖出比例按可卖份额换算后向下取可表达值，在用户确认前展示尾数；最小数量仍从本次市场取得，不能固定为示例中的 5 份。

对已核准的当前构单规则，令 `P` 为收紧后的价格、`a` 为该 tick 对应的金额精度：

| 方向 | 实际 offered／requested 构造 | 必须验证的保护不变量 |
| --- | --- | --- |
| 买入 | offered 为原本金 `D`；requested 为 `ceil_a(D/P)` 份额 | `offered/requested ≤ P`，且签名本金与确认本金相等 |
| 卖出 | offered 为展示过的拟卖份额 `Q`；requested 为 `ceil_a(Q×P)` 金额 | `requested/offered ≥ P`，且签名份额与确认份额相等 |

以交叉相乘验证不变量，避免再次除法舍入。tick 的精度表来自当前协议适配器；tick 0.0025 等不能仅按小数位判定合法网格。任何 SDK 自动金额调整或构单结果不一致均拒绝进入签名。

100% 表示**本次报价时可卖部分的 100%**，同时展示总持有、其他操作占用和不可卖部分；不声称整个仓位必然归零。例如可卖 5.123456 份，拟卖 5.12 份，至少保留精度尾数 0.003456 份；部分成交还可能留下更多。可卖基数变化时重做报价，不能悄悄改变已确认数量。

## 3. 预计费用与本次预留

### 3.1 预计值如何计算

逐档使用保护范围内的可成交深度模拟数量与价格，再应用该市场费用规则；本段不以「平均价代入一次」替代多档核算。已核对规则的未舍入平台费为 `C × r × [p(1-p)]^e`，Builder 费用另按适用的成交本金费率计算。费率、指数、启用标志、Builder code／费率、币种、计费方及版本都进入报价证据。

官方费用页说明五位小数精度，但具体计费分组及舍入顺序仍需与对应执行版本核准；页面可展示预计值，不能据此声称真实逐笔扣费已验证。缺少任一适用费项显示待核对，不能填 0。平台配置 Builder 凭据的授权也不等于新增 ATHENA 收费方案的批准；接入不能暗中启用新的收费项。

说明性例子：本金 10、单一成交价 0.50、`r=0.05`、`e=1` 且无 Builder 费，预计平台费 0.25，预计总支出 10.25。实际本金、费用及总支出由最终成交证据填入，不能覆盖成原预计值。余额不足以满足本次需要预留的金额时，提示缺口并保留输入，由用户修改本金或在官网入金。

### 3.2 预留上界的证据要求

**预计总支出用于阅读报价，本次预留金额用于协调后续提交，两者可以不同；预留不等于已经扣费。** 买入预留本金和可核准的费用上界，不能把 SDK `maxSpend` 当作独立的链上费用封顶字段，也不能通过它缩减本金。

本次核对的 [V2 Fees.sol](https://github.com/Polymarket/ctf-exchange-v2/blob/ccc0596074f4dfd62c944fbca4de252893b82b4b/src/exchange/mixins/Fees.sol)表明，合约存在可变最大费率，值为 0 时跳过上限检查；源码初值不是线上当前费率。配合 [Trading.sol](https://github.com/Polymarket/ctf-exchange-v2/blob/ccc0596074f4dfd62c944fbca4de252893b82b4b/src/exchange/mixins/Trading.sol)，**在部署一致、完整费用均受该检查约束、且该配置在执行期间成立的前提下**，可用以下保守计算：

- 读取当前非零上限 `m`，以原始本金基础单位 `D` 计算 `fee_bound = ceil(D × m / 10000)`。
- 所有实际成交本金之和不超过 `D` 时，逐次向下取整的合约费用校验支持这个总量上界，不需要假定只成交一档。
- 例如仅假设 `m=500`，本金 10 的费用预留为 0.50，总预留为 10.50；前述预计总支出仍为 10.25。500 不是本设计指定的真实费率。
- 上限为 0、无法读取、代码不匹配、费用另有扣款路径或属于尚未核准的 V3 路径时，不能使用这个公式。须由该路径提供有来源的等价上界，否则相关买入保持待核对。

**这个计算是当前已核准规则下的预留依据，不是用户签名中不可变的最高扣款保证。** 已核对 V2 订单没有独立费用上限，费用在平台撮合时确定；管理员改变上限、外部渠道操作和平台状态变化不受 ATHENA 的数据库事务控制。实施前须闭合实际部署、总费用覆盖及配置变动处理证据，不能仅凭本节公式宣布费用风险已消除。

预览与首次派发之间发现费用规则变化，旧报价失效。派发后发现规则变化或实际影响超过原依据，保留原交易和实际证据，重新核准涉及的可用资产；证据不足时该资产待核对，不自行修改原确认记录或虚构更大的用户授权。其他可独立核准的资产保持原规则。

卖出按所支持结算路径明确费用是从收入扣除还是需额外余额。已核对 V2 卖出结算路径从收入扣费；只有实际部署和完整费项核准后，才能据此只预留卖出份额。其他路径如另需资金，预览须列明并纳入占用。领取与 EOA 链上操作的 gas 等费用在各自预览中单列，不能混成 CLOB 买卖手续费。

## 4. 占用账本与可用资产

### 4.1 占用的范围

资源键使用 `chain + 实际交易账户 + 资产合约／资产标识`，不能只用 Wallet ID；同一实际账户的别名或重复映射不能各算一份余额。占用由交易服务持久保存，关联原尝试、资源、数量、证据和版本。

| 操作 | 需要预留的资源 | 不提前计入可用 |
| --- | --- | --- |
| 买入 | 本次本金及适用费用上界 | 预计买入份额 |
| 卖出 | 对应 Outcome 的实际拟卖份额；经核准另需的费用资产 | 预计卖出收入 |
| 领取 | 实际调用涉及的各 Outcome；若该方法处理全市场余额，则协调完整处理范围 | 预计领取收入 |

普通卖出按份额占用，同一 Outcome 剩余可卖份额可以另行确认交易。领取若实际处理该市场多个 Outcome，不能只锁点击的那一行；其合约参数和实际影响范围在后续领取详细设计闭合。交易完成前不持有整钱包的长期数据库锁。

### 4.2 上游已扣减与本地预留只计一次

一个余额数字不能直接与所有本地 pending 金额相减。每项资产核对保存：区块／快照、来源时间及覆盖范围、确定余额、已反映的成交扣减、上游仍可能执行的订单／成交、ATHENA 尚未被上游完整反映的占用，以及未确认入账。

计算先把同一负债按订单、成交和结算关联合并，再按快照中已反映的金额拆分，之后计算：

`可用量 = 已核准余额 - 尚未反映的可能支出 - 已入账但仍未确认可用的收入`

「尚未反映的可能支出」包含其他渠道订单及本地尝试，两者指向同一订单时取其尚未覆盖的保守总额，不重复相加；已经计入余额的实际扣款不再次扣除。若某个上游接口已返回扣除订单占用的净可用量，适配器必须提供其已覆盖项；没有覆盖证据，不能按字段名称猜测已扣范围。当前 SDK `/balance-allowance` 只有余额和授权字段，不提供足以直接消除此问题的完整覆盖证明。

例：原核准余额 100，尝试 A 预留 30。随后核准实际扣款 12 已反映在余额 88 中，A 还有最多 18 可能发生；此时可用为 70，不能再从 88 减原来的 30 得到 58。若 A 的剩余已经核准不可执行，可用恢复为 88。该例未含其他订单，只解释重复扣减的处理。

资产投影与释放占用须在同一资源事务中更新，检查预览使用的版本；并发提交重读已提交的占用。外部订单、未终结成交、分页缺失或快照冲突使某项资源无法核准时，依赖它的操作等待核对，不推算为零，也不统一关闭其他资产。只读列表可以显示带时间和状态的余额，提交资格不能复用未核准的列表数值。

本地预留不能阻止官网或其他渠道同时花费，提交前仍须刷新上游事实，远端余额拒绝作为原尝试结果记录。无法获得跨来源一致证据时必须暴露差距，不能把本地串行接收宣称为对 Polymarket 全渠道的原子冻结。

### 4.3 何时释放

- 尚未取得派发许可、并已持久撤销签名／派发资格的尝试，核准未发送后可以释放。
- 明确的拒绝须能证明原请求未受理；重复订单错误、代理错误、404 或单次查不到不构成该证明。
- 部分成交按各成交独立核对；只有确定未成交部分不再可能执行，才释放其剩余占用。已撮合但未终结的部分继续保留。
- 结算终态与余额投影分别记录；余额尚未追上时保留防止重复使用的扣减或禁止提前使用的入账标记。
- 超时、重启、关闭页面、切换客户端、达到轮询次数或租约到期，都不自动释放。

## 5. 接收、签名与派发

### 5.1 接收一次明确的用户意图

浏览器为一次明确提交生成稳定请求标识。服务端持久化唯一键 `owner + 操作种类 + client_request_id`，以及不可变内容摘要。相同键、相同内容返回原尝试；内容不同返回冲突。当前有效会话才能调用，旧会话不能用重试标识绕过失效；新会话可查看或取得该 owner 原尝试。

接收事务同时核对当前唯一登录、Trader Sync 权限、Wallet 操作权限、可信 Wallet 归属证据、账户映射／绑定版本、报价有效期及资源版本，并保存接受结果、冻结内容和占用。校验失败也保存有权限接收的业务提交结果；外来 owner、非法身份或无权调用不因此创建对方记录。事务提交结果不明时按原唯一键回读，未证实接收成功不能发出交易。

用户切换客户端与接收事务按同一账号门禁排序：接收先完成，既有尝试继续；新登录先完成，旧会话不能接收新尝试。后续执行凭据关联原尝试和当时的合法接收证明，不要求旧登录继续有效；模块撤权、Wallet 操作权与实际账户控制资格仍独立复核。

### 5.2 原子边界及服务归属

已确认交易服务拥有独立进程和自身表，但将接收、占用、派发许可表放在**账户权威状态所在的 PostgreSQL 数据库**。由受控 adapter 在本地事务内读取授权／会话和当前绑定；账户授权写入方继续使用同一 `txgate` 账号锁。这样接收、撤权与许可有明确原子顺序，符合 SDS-R6；不会通过 gRPC 传递事务。

交易进程管理自己的连接池和 worker；账号状态写入仍由其权威模块负责。Wallet 私钥与 Wallet 数据库保持既有服务归属，签名通过专用 RPC。Wallet 当前不提供删除或转移归属能力；其归属、类型和密钥地址须在读取及签名时独立复核，备注／头像的变化不应冒充控制权变化。若未来新增改变归属的操作，必须补充原子协调，不能拿短时缓存声称覆盖可变归属。

锁顺序固定为：账号门禁 → 交易账户／绑定 → 按资源键排序的资源 → 尝试及步骤。撤权 adapter 遵循同序，只使尚未派发的许可失效，保留已发出尝试的核对能力。后台资源投影若还需账号锁，必须从账号锁开始，不从资源锁反向取得账号锁。网络读取不放在接收事务里；回来后通过版本复查再提交。

最终派发使用与账户撤权同序的短时账号门禁，覆盖最后资格检查、唯一派发记录提交及紧接的首次网络调用。该门禁只保护提交临界区，不等待订单最终结算；同钱包及其他钱包的长期可用性仍由资源占用决定。共享数据库是明确的共同故障域，不能宣传为数据库故障相互隔离。

### 5.3 签名和发送内容固定

| 阶段 | 持久事实与约束 |
| --- | --- |
| 已接收 | 原账户、来源、输入、报价、边界和占用不变；尚不能说明已送达平台 |
| 待签名／已签名 | 原尝试和步骤决定唯一 salt／nonce、协议和字段；Wallet 检查专用服务身份、owner、账户控制与结构化意图；产物加密保存 |
| 派发许可已提交 | 原包摘要、允许端点、请求体、执行类型、worker 与一次性发送资格已经持久记录；其他 worker 只能核对，不接管重发 |
| 已观察到发送／响应 | 保存实际传输观察、平台响应和外部标识；它们与「许可已提交」分别记录 |

Wallet 的订单专用签名目标为 `SignPolymarketOrder`，输入包含受控结构及已接收意图证明，不接受任意 digest 作为全部业务依据。签名前重新计算本金／份额、真实比例边界、市场及账户路由，与确认摘要一致才签名。买卖不能顺带增加授权、部署或换账户。

`orderType=FAK` 等请求外层字段并不全部进入 EIP-712 订单签名，因此交易服务还要冻结和核对**完整发送包**，包括 FAK、owner 凭据关联、端点及必要执行标志，按实际序列化字节生成 CLOB 请求认证。不能只检查签名 digest 后让浏览器或 SDK 改成 GTC。六位金额、salt 的 JSON 表达与协议字段也须与签名一致。

许可提交是 ATHENA 对本次原包的持久授权顺序点，不等于已经观察到 HTTP 送达。撤权在许可前生效则不能派发；已经进入该边界的原包可能送达，后续撤权不能承诺撤回远端交易。门禁丢失或连接异常时停止启动新调用，保存传输证据；不能把数据库锁当成远端也识别的 fencing token。进程在许可后、发送前崩溃时，恢复为待核对，不能仅凭租约到期把发送权交给另一进程。

确定尚未派发且已作废旧许可／签名产物的尝试，可以结束为未发出，由用户刷新后建立新尝试。这里的作废是禁止 ATHENA 继续使用产物；只有能证明它未交给任何发送方时才能据此释放，删除本地签名不能让已泄露或已发出的签名在远端失效。任何可能已发出的买卖都不自动重新 POST 原订单，也不生成新 salt、nonce 或签名订单补发；HTTP 客户端、SDK、代理和任务队列必须关闭这类隐式重试。SDK 返回空成交 ID 的等待函数不能证明完整订单已经结束。

## 6. 原尝试的恢复和结果

后台按原请求标识、已核准的订单 hash／平台订单 ID、成交 ID 及链上证据核对，持久保存每次事实及来源。只有验证过本地 hash 与平台订单 ID 的关系才按它精确查单；不能把任意签名 digest 当成已取得平台 ID。按时间／账户查到的相似订单只作候选，必须核准精确关联；全部分页、账户作用域和时间覆盖不足时不能得出「从未受理」。

| 当前事实 | 页面状态和处理 |
| --- | --- |
| 校验失败、过期或撤权，且未派发证据完整 | 未发出，说明原因；修改后由用户明确新提交 |
| 平台受理，尚在延迟窗口 | 处理中，保持原记录与占用；本地报价到期不取消已受理交易 |
| `MATCHED`／`MINED`／`RETRYING` | 已撮合／结算处理中，尚不能显示最终成交或提前使用收入 |
| 所有成交已终结，订单剩余确定结束 | 按核准实际份额、本金、费用分别显示全部成交、部分成交或未成交 |
| 仅部分成交终结，其余仍未知 | 显示已确认部分和仍待核对部分，不能将整笔标为成功或失败 |
| 超时、断网、进程崩溃、缺少外部标识 | 待核对；保留输入快照与原记录入口，无「重试交易」按钮 |
| 平台订单已结束，但持仓／费用来源滞后 | 显示已知结果及具体同步中字段，历史保留覆盖状态 |

FAK 的未成交部分应结束。若返回 `live`／`unmatched` 等与预期不符的状态，先核准原订单身份及是否确有挂单余量，不能直接当作「未成交已结束」。为兑现本次 FAK 意图，执行器只对已核准属于本次提交的意外活跃余量请求撤销；这属于该提交的收尾，不开放挂单管理或账户级取消全部订单。撤销响应丢失继续核对，已撮合部分不能撤回，未知余量不能释放。

一笔尝试可能关联多次成交和多个结算交易。结果按成交 ID／链上事实去重并保留修正轨迹；平台结算重试不等于 ATHENA 再发一次买卖。订单完成度、原计划本金、实际花费和实际取得份额分别显示，不用「订单完全匹配」推断「用户本金全部花完」。交易结果仍只在页面及历史展示，不新增用户通知通道。

## 7. 接口、超时与故障隔离

以下为目标 RPC 职责，不表示已生成 proto 或可调用接口：

| RPC | 主要职责 |
| --- | --- |
| `PreviewTrade` | 取得无副作用、带有效期的买入／卖出报价；结果包括不能提交的具体原因 |
| `SubmitTrade` | 核对当前登录并原子接收一次明确意图；返回稳定尝试 ID，不等待最终结算 |
| `GetTradeAttempt`／`ListTradeAttempts` | owner 范围读取本系统尝试、原确认、分项成交及核对进度 |
| `GetTradingAvailability` | 按实际账户与资产返回可用、占用、未确认入账及核对时间；不是单一模糊余额 |

受保护读取与写入沿用已确认的 Trader Sync／Wallet 权限，公共 owner、管理员和 API Key 均不能获得新交易路径。后台只凭专用服务身份和原合法接收记录处理，不把浏览器参数当作可信用户身份。

本段已确认的初始预算：接收 API 5 秒、预览 API 8 秒；单次市场／账户上游读取 3 秒、Wallet 签名 3 秒、单次交易发送 5 秒。首次发送资格仍受 15 秒报价剩余时间限制，超时不自动续期。锁等待初值 1 秒；未获派发许可可在有效期内继续处理原尝试，超过期限以未发出结束。

签名／发送使用服务端原尝试生命周期，合法接收后不因浏览器断开立即抹除任务。派发前已明确取消资格的记录不得被后台复活。读取与结果核对可退避重试：初值 1、2、4、8 秒，之后至多每 30 秒一次，加入抖动并服从上游限流；长时间待核对保留记录并进入运维异常队列，频率降低不能转换为自动失败或释放。

服务有界停止时先停止接收新提交和签发新许可，让当前有界调用收尾，持久保存未决状态；重启从原记录恢复核对。历史同步与原交易核对使用独立并发预算，不能让全历史任务耗尽新报价或未知结果核对资源。Builder、CLOB、Wallet 或数据库故障按具体操作暴露，不影响无关 Activity Alerts 与页面服务。

## 8. 实施前的验证清单与剩余设计

本次只执行来源核对、金额示例计算和文档静态检查。没有真实报价接收、私有成交、资产冻结或服务运行验收。

后续必须覆盖：

1. 各受支持账户／市场协议的完整请求和签名一致；FAK 外层字段不能被替换，买入本金不被 SDK 缩减。
2. 全部受支持 tick、0%／99.99% 偏差、非整网格、两位本金、小额最小量及 100% 卖出尾数；真实整数比例不越界。
3. 多档成交、实际计费分组和舍入、平台及 Builder 总费用、目标部署与可变费用上限；补齐 V3 路径证据，不能用 V2 源码冒充。
4. 15 秒过期、服务端／浏览器时间差、签名时过期、有效期内行情变化、费率／绑定／tick 改变和平台延迟窗口。
5. 同键重试、同键改内容、事务提交响应丢失、并发占用竞争与实际账户别名；没有超卖和重复扣减。
6. 新旧客户端切换与接收事务、撤权与派发许可的交错；锁丢失、长暂停、重复 worker 和进程重启不能生成第二次发单。
7. 在签名前、签名后、许可提交后、首次网络写入、平台受理及保存响应各点中断；查询不到不能被错误判为未发送。
8. 多成交部分成功／失败、撮合后结算重试、原订单意外挂单余量收尾、外部订单占用、余额先到／订单先到、未确认入账和重新组织后的证据修正。
9. 旧 Wallet 换绑后原尝试保持原账户，剩余资产能独立交易；全历史未齐不阻断已核准操作，缺失资产事实也不被当作零。
10. 最小依赖独立运行、RPC deadline、停止和恢复，以及桌面／手机相同确认与结果语义。

服务边界按[服务开发规范](../../developer-guide/service-development-standards.md)的 SDS-R1～R8 承接；本次证据仅支持 R7／R8 的设计及静态检查，不代表其他运行时要求已通过。

**待真实验证：**实际部署与费用上界、跨来源可用量覆盖，以及私有执行和恢复。领取／持仓／同步详细设计及桌面／手机页面方案已随后获确认；[完整规格](../../superpowers/specs/2026-09-15-trader-sync-manual-trading-design.md)已整合各段契约和验收要求，待整体审阅后编写实施计划。未核准平台能力不视为已验证；若与既定业务规则冲突，再带具体证据和影响提出取舍。
