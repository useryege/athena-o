# Polymarket 账户接入与首次启用

> 设计状态：本段设计已确认。2026-09-15，用户回复「认可」，确认账户接入与首次启用详细设计。业务选择沿用[手动交易需求](../../requirements/polymarket-copy-trading/copy-trading.md)和[总体设计](polymarket-manual-trading.md)；该确认不表示真实接入、接口或交易功能已经实现，也不代替后续完整执行规格。

## 本段解决什么

用户选择自己的 EVM Wallet 后，应能明确知道：将操作哪个 Polymarket 账户、系统为何判断该钱包能够控制它、本次启用会执行哪些步骤，以及哪些条件仍未就绪。

本段交付账户支持矩阵、身份核验、启用步骤、持久状态、接口职责、Wallet 签名边界、页面信息和验证场景。报价与费用算法、买卖和领取的执行协议、资金占用计算及全量资产同步在后续详细设计中承接；本段给出它们必须消费的账户身份与能力事实。

后续[报价、交易执行与资产占用设计](polymarket-trade-execution.md)已于 2026-09-15 获用户认可，明确共用接收／派发门禁和原请求核对协议；两段设计认可均不代表相关运行时机制已经验证。

第三段[领取与同步设计](polymarket-redemption-and-sync.md#31-需要准备时)已获用户认可，补充领取所需持仓 operator 的核准和主动准备方式，复用本段启用流程；该能力清单仍待真实验证，不在普通领取时隐式补授权。

以下已确认决定直接沿用：优先复用已有账户；核准尚无对应账户后才由用户主动启用创建；平台统一管理 Builder 凭据；首次使用经核准合约的标准长期最大资金额度；钱包归属、钱包操作权限和逐笔确认分别检查；当前必要条件就绪即可交易，完整历史继续后台同步。

## 1. 核对依据与实现差距

| 依据 | 已有证据 | 本段采用方式 |
| --- | --- | --- |
| Wallet 创建、导入、托管与归属 | [Wallet 契约](../../../internal/wallet/wallet.proto)、[服务](../../../internal/wallet/service.go)和[长期设计](../identity-access/wallet-ownership.md)已实现 | 复用 Wallet ID 与现有钱包管理；交易服务不获取私钥 |
| 专用签名算法 | [离线对照](../../requirements/polymarket-copy-trading/signing-feasibility-2026-09-15.md)记录 26 组载荷与 146 组字段改动检查 | 复用算法证据；不能据此把真实账户或权限校验标为通过 |
| 账户、凭据与部署协议 | [官方钱包说明](https://docs.polymarket.com/trading/wallets-auth)和[合约清单](https://docs.polymarket.com/resources/contracts) | 按账户类型、网络与实际部署版本选取协议 |
| SDK 的隐式行为 | [本次源码核对记录](../../requirements/polymarket-copy-trading/evidence/account-onboarding-design-2026-09-15/source-review.json)，固定提交 `983a10a7579c95043d4099f60873ff7ea817e5a0` | 采用显式读取、构造、签名、发送和核对步骤，不以通用初始化代表只读查询 |

本次源码核对发现：

- [账户分类](https://github.com/Polymarket/ts-sdk/blob/983a10a7579c95043d4099f60873ff7ea817e5a0/packages/client/src/wallet.ts)对无法从 signer 推导的地址会回退为 Deposit Wallet 的 Session Key 路径。ATHENA 不把该分类结果当作控制权证明。
- [SecureClient 初始化](https://github.com/Polymarket/ts-sdk/blob/983a10a7579c95043d4099f60873ff7ea817e5a0/packages/client/src/clients.ts)可能请求认证签名、取得 CLOB 凭据和部署未存在的钱包；显式传入账户地址也不使初始化成为纯读取。
- [gasless 流程](https://github.com/Polymarket/ts-sdk/blob/983a10a7579c95043d4099f60873ff7ea817e5a0/packages/client/src/actions/gasless.ts)包含 nonce 错误后的重新签名路径。ATHENA 必须通过原尝试及已确认状态控制恢复，不直接继承该副作用。

这是文档与源码核对，没有读取用户私钥、取得私有凭据、创建账户、发送授权或交易，也没有访问已登录的 Polymarket 网站。

## 2. 四类身份信息分别表达

| 对象 | 含义与保存方式 | 不承担什么职责 |
| --- | --- | --- |
| ATHENA 账号与 Wallet | 服务端可信 owner、Wallet ID、EVM 类型、规范化 signer 地址 | 浏览器提交的 owner 字段不能覆盖当前身份 |
| Polymarket 交易账户 | 链 ID、实际持仓地址、账户类型、控制关系与部署证据 | 不能用 signer 地址代替实际资金和持仓地址 |
| 官网账户资料 | 用户核对的账户地址、可取得的公开资料与关联证据 | 公开用户名或粘贴一个地址不能证明账户控制权，也不证明网站当前登录状态 |
| 官网充值地址 | 用户在官网 Deposit 流程中按币种／网络取得 | 不能把前述任一地址统一标成充值地址 |

[官网入金说明](https://help.polymarket.com/en/articles/13369887-how-to-deposit)要求在对应 profile 下选择充值方式与网络；不同网络的地址可能不同。ATHENA 展示实际交易账户用于核对，并提供官网入口；不生成充值地址、不调用 Bridge 创建地址、不发起转账。返回 ATHENA 后按已核准交易账户读取余额，不能把「我已充值」当作到账事实。

## 3. 账户类型与支持条件

下表定义接入设计应覆盖的类型及通过条件，**不表示任一类型已完成真实接入验证**。某个账户未通过核验时显示具体原因，不切换到另一个空账户。

| 账户类型 | 接入处理 | 必须核准的条件 |
| --- | --- | --- |
| 已有 Deposit Wallet | 复用实际账户；分别识别已部署的 UUPS 和 beacon 形式 | signer 与当前账户的控制关系、受支持部署／实现、CLOB 认证与必要操作路径 |
| 新建 Deposit Wallet | 仅在无已有对应账户的结论可靠、且用户确认本次创建时准备 | 当前 factory 与推导方式、平台创建资格、预期地址、部署结果及官网同账户路径 |
| 已有 Polymarket Proxy | 复用已有资金与持仓；采用相应认证、订单及钱包操作协议 | 官方工厂／实现关系、所选 signer 的有效控制关系、当前平台支持 |
| 已有 Polymarket Safe | 复用已有账户；核对当前 owner 和签名门槛 | 不能只按最初推导地址认定当前控制权；所选 Wallet 的签名须足以完成对应操作 |
| 直接 EOA | 账户地址等于 signer 时单独识别 | 平台准入及直接交易能力明确，链上操作所需 POL 与费用条件可核准 |
| 其他合约、仅 Session Key 或不明映射 | 标明控制关系／能力待核对或暂不支持 | 不根据 SDK 的回退分类推定拥有完整控制权，不静默新建替代账户 |

官方区分[钱包类型与直接 EOA 条件](https://docs.polymarket.com/trading/wallets-auth#advanced-options)。继续接入当前仍在使用的 Proxy、Safe 或 UUPS 账户，是为了满足已有资金与持仓的现行需求，不是为旧 ATHENA 行为保留兼容层。本段不增加 Session Key 管理、多签协作或迁移资金功能。

### 3.1 只读发现与控制关系核验

1. 以可信 owner 读取 Wallet；只接受自有 EVM 钱包。地址规范化后参与比较和唯一约束，显示时保留完整地址。
2. 已保存账户优先作为待复核对象；首次接入收集官方资料映射及已核准工厂可推导的候选。候选包含不同有效账户形式，不只查询当前新账户地址。
3. 分开核对「地址可推导」「合约已部署」「当前控制关系」「平台可使用」。部署查询只证明其接口所表达的部署状态；[官方部署接口](https://docs.polymarket.com/api-reference/relayer/check-if-a-wallet-is-deployed)不证明余额、授权或完整交易资格。
4. 控制关系校验器按识别出的工厂、代理及实现协议验证，保存链 ID、区块号／hash、实现标识与实际返回值。Safe 核对当前 owners／threshold；Deposit 和 Proxy 按已核准实现的控制语义核对，不能假定所有合约都有同一个 `owner()` 接口。
5. 只有一个可核准候选时带入供用户核对；多个候选时列出可区分信息，由用户选择后再次验证。不按余额最高、资料名相同或接口返回顺序自动选择。
6. 查询失败、资料缺失、旧形式未部署但存在资产迹象、控制关系不明或未知实现，均不归为「没有账户」。新建资格须基于完整的已知候选核对；没有可靠结论时保留待核对。

地址推导使用已核准的 factory／implementation／beacon 配置版本。发现地址不等于创建地址；不能用新的 factory 部署路径尝试补建旧推导地址。已有账户即使余额为零也不自动改址。未知合约版本影响该账户或操作的资格，不通过扩大允许列表自动放行。

### 3.2 官网登录与同账户验证

[官网登录说明](https://help.polymarket.com/en/articles/13369877-how-to-sign-up)区分 Google、Email 和外部钱包路径。接入前按用户实际登录方式核对：

- 用户已经使用外部钱包登录时，选用／导入能控制该官网账户的同一 EVM signer；私钥导入使用现有 Wallet 管理入口，交易设置不另收私钥。
- 用户通过 Google／Email 登录时，不能用 ATHENA 的 Google 账号或任意同名 Wallet 替代其 Polymarket signer。实际账户控制关系仍须单独证明。
- Wallet 在 ATHENA 内创建时，链上可部署不证明用户已经能在官网登录该账户。若用户需要将同一 signer 用于外部钱包，应由用户使用既有 Wallet 管理能力完成；[已有私钥查看的独立验证](../identity-access/wallet-secret-reauthentication.md)保持原规则。交易服务不代取、传递或导入私钥到第三方。

ATHENA 无法从自己页面的返回事件证明另一个网站的登录状态。界面可以记录用户已核对的官网账户地址，再验证其与账户映射及控制事实一致，但不能把用户声明标成已观测的网站会话。真实联调须记录同一 signer／官网账户／ATHENA 账户的对应证据和最终余额来源。

新账户路径只有通过官网同账户验证后，才能作为可用接入路径交付。若仅能部署 API 账户而无法复用官网登录与入金，保留该差距并报告具体影响；不以新增站内充值、私钥自动导出或另建网站账户绕开已确认需求。

## 4. 主动启用的步骤

流程：选择 Wallet → 只读核对账户 → 展示本次必要准备 → 用户确认启用 → 分步执行及核对 → 展示准备结果与实际余额。

| 步骤 | 本次执行内容 | 完成证据 |
| --- | --- | --- |
| 核对预览 | 账户候选、控制关系、已有准备与缺少的步骤 | 不签名、不部署、不取得新凭据、不修改链上授权 |
| 接收确认 | 冻结 owner、Wallet／signer、实际或预期账户、账户版本、本次动作清单及配置版本 | 持久化尝试 ID、稳定提交标识与内容摘要；重复请求返回原尝试 |
| 账户准备 | 已部署账户直接复核；仅明确确认的新账户请求调用部署流程 | 原 Relayer 记录、预期地址、实际合约及控制关系一致；不能仅凭 HTTP 成功判断 |
| CLOB 凭据准备 | 检查已有对应凭据；需要时按本次确认取得认证签名与凭据 | signer 对应的认证可用，凭据加密保存并关联正确账户映射 |
| 链上授权准备 | 对本次清单中缺失或需变更的已核准合约设置授权 | 原链上操作结果及最新 allowance／operator 状态共同核对 |
| 核对结果 | 汇总账户、认证、授权等实际状态 | 余额和历史进度独立表达；准备完成不表示已有可用资金 |

首次准备使用已确认的标准长期额度。有效且已满足本次目标的步骤复用；把较小额度提高至最大额度时必须在本次启用清单中说明。pUSD 资金额度与持仓 operator 权限分别展示，不能把后者描述为只覆盖一个市场或一次卖出。

当前普通／Neg Risk 合约按[官方清单](https://docs.polymarket.com/resources/contracts)和实际市场版本核准。允许配置保存具体 chain、token、spender／operator、方法、额度策略与版本；浏览器不能提交任意授权对象。SDK 通用授权中的自动领取、Perps、Combo 或其他与本次操作无关的对象不进入本次清单。新合约需求须先核准其必要性，再让用户看到变化后的准备内容。

当前可交易能力按操作判断：账户身份、认证、该操作所需授权、当前可用资产与市场条件均有效才可提交。认证有效、余额未知、某项授权待核对和旧历史同步中可以同时存在，不能合并成一个含义不明的 Connected。

## 5. 持久状态与恢复

### 5.1 分开保存的对象

| 对象 | 必要内容 |
| --- | --- |
| 交易账户 | owner、Wallet ID、signer、chain、实际地址、账户类型、映射 revision、控制证据、配置版本 |
| 启用预览 | 预览 ID、账户／绑定 revision、动作清单及摘要、依赖事实时间、有效期、变化原因 |
| 启用尝试 | 尝试 ID、owner 内唯一的客户端提交标识、不可变确认摘要、接收时会话／权限事实、来源、阶段、创建与更新时间 |
| 启用步骤 | 原尝试与 step ID、动作类型、精确目标和参数、nonce／截止时间、签名摘要、实际派发状态、远端标识、核对证据、错误原因 |
| CLOB 凭据 | 对应 owner／signer／chain、关联账户、认证 nonce、加密密文、验证时间、凭据版本及实际失效状态 |

一个实际链上账户不能通过多个 Wallet 记录绕过绑定唯一约束。冲突检查覆盖规范化链上账户地址与当前有效绑定；跨用户冲突只返回无法关联的原因，不泄露另一用户的 Wallet 或目标。

预览有明确有效期，并在提交时比较账户、绑定及准备配置的版本；过期或关键事实变化后重新预览。后端不会把已确认的实际账户替换为新的候选。已接收尝试与目标之后的换绑分开，继续核对原账户。

### 5.2 状态不是单一成功／失败

| 状态 | 允许的处理 |
| --- | --- |
| 等待用户确认 | 仅展示；没有相应外部动作许可 |
| 已接收、尚未派发 | 执行前复查当前资格与冻结内容；资格不满足则记录具体原因 |
| 正在派发／远端处理中 | 保存原载荷与标识，持续核对；不创建另一个相同准备任务 |
| 结果待核对 | 核对原记录、nonce、实际部署或授权事实；时间经过不等于失败 |
| 已核准成功 | 保留步骤证据；后续准备可复用当前仍有效的事实 |
| 已核准失败或确定未发出 | 保留原因，重新读取缺少的步骤；由用户确认新的继续命令 |
| 需要重新核对 | 账户、控制关系、必要授权范围或确认内容变化，展示差异后重新确认 |

继续命令使用新的稳定命令标识，并关联原尝试与新的预览；已完成步骤不重新执行。结果未知的步骤不走失败重试分支。一次批准不能覆盖新增账户、不同合约或扩大后的动作清单。

### 5.3 各类超时如何核对

- **部署响应丢失：**有 Relayer ID 时查询原记录；没有时核对确认时的预期地址、实际部署、控制关系及可取得的原提交事实。某次查询未找到记录，不能证明没有提交。发现目标已存在可更新当前准备事实，但不能凭此补造原部署交易 ID。
- **凭据响应丢失：**冻结对应 signer 与认证 nonce，查询／派生同一凭据槽并验证。必要的恢复认证签名必须绑定原启用意图；若原授权已不允许继续则等待用户确认。不能默认换 nonce 创建第二套凭据，也不能撤销官网或其他渠道凭据来解决冲突。
- **授权响应丢失：**按原交易／批次、nonce、回执及实际授权状态核对。看到额度已满足时可以更新当前能力，但不能未经证据把原步骤改写成其造成的成功；原记录仍按事实核对。
- **服务重启或页面关闭：**恢复已有步骤的读取与核对；派发许可已消耗而是否发送不明时进入待核对，不按新任务重新签名。SDK 的自动重签、自动重新发送和普通下单补授权路径不直接启用。

每个会产生外部副作用的步骤先保存意图和完整可重建内容，再取得单次派发许可。进程崩溃、RPC 超时和远端超时分别记录，数据库提交不被表述为跨平台的恰好执行一次。新的 nonce 只能出现在核准原请求不再可能执行、且满足相应用户确认的继续步骤中。

准备步骤按同一实际账户需要共享的 nonce／认证槽协调；这是相关步骤的执行约束，不扩展为整个钱包等待任何上一笔结果的业务限制。后续买卖仍遵循[已确认的资金／份额占用规则](polymarket-manual-trading.md#待处理操作与后续交易已确认)。

## 6. 接口与受限签名边界

### 6.1 交易服务的账户接口

下列是目标 gRPC 职责与名称，尚未新增 `.proto` 或 HTTP 路由；遵循[RPC 命名规范](../../../.codex/skills/grpc-rpc-naming/SKILL.md)。请求中的 owner 由可信服务身份解析，不能采信浏览器传入值。

| RPC | 输入与返回 | 副作用边界 |
| --- | --- | --- |
| `ListTradingAccountCandidates` | Wallet ID；返回候选、控制／部署状态、依据与原因 | 只读发现，无认证签名或部署 |
| `GetTradingAccount` | 账户 ID；返回自身账户、分项准备状态、余额时间和覆盖信息 | 只返回 owner 有权读取的安全投影 |
| `UpdateTradingBinding` | 目标、Wallet、已核准账户引用、预期 revision | 仅修改当前绑定，不启用或划款 |
| `PreviewTradingAccountEnablement` | 账户或待创建候选、映射 revision；返回必要步骤及不可用原因 | 可保存本地预览，无外部准备副作用 |
| `SubmitTradingAccountEnablement` | 预览 ID／摘要、稳定提交标识；返回启用尝试 | 明确确认后的接收边界，执行异步进行 |
| `GetTradingAccountEnablement` | 尝试 ID，或响应丢失时的原客户端提交标识 | 返回原记录，不重建提交 |
| `ListTradingAccountEnablements` | 账户与分页参数 | 查询准备过程，不能冒充买卖成交历史 |
| `ContinueTradingAccountEnablement` | 原尝试、新预览、预期 revision、新命令标识 | 明确确认剩余必要步骤，复用已完成事实 |

读写权限分别声明：私人交易账户的读取要求当前 Trader Sync 权限及 Wallet 读取权限；绑定变更、主动启用和继续要求 Wallet 操作权限及有效交互式会员会话。已有目标提醒继续按原有权限规则工作。账户读取权限不足时不泄露余额或历史，后台对已接收请求的必要核对不因此丢弃。

### 6.2 Wallet 的能力边界

交易服务获得专用内部服务身份，不复用能调用 `RevealWalletPrivateKey` 的通用 Wallet 管理凭据。安全元数据读取与签名分别授权，签名能力仍运行在 Wallet 进程。

本段需要两类专用操作：

- `SignPolymarketAuthentication`：只构造已核准的 CLOB 认证消息，核对 owner、Wallet、派生 signer、chain、固定 domain、认证 nonce、时间和原启用尝试。不能传入任意 message／digest 让 Wallet 签名。
- `SignPolymarketTradingApproval`：只接受已确认清单内的授权意图，由 Wallet 构造或完整解码对应账户协议，核对 token、spender／operator、额度、目标账户、nonce、deadline、网络及配置版本。批次内每一项都须属于本次批准范围；不能夹带转账、任意合约调用或新增 operator。

新账户部署请求若使用平台 Builder 认证而不需要用户钱包签名，仍必须绑定用户已确认的部署步骤和预期 signer／地址；不能由普通查询或服务启动触发。EOA 直接授权还须冻结用户核对的网络费用约束，不能把原生币 `value` 或 gas 参数变成任意支出入口。

Wallet 返回签名及内容摘要、协议版本、原尝试和 step ID；交易服务按完全相同的内容持久化和提交。相同 step 与不同摘要必须拒绝。私钥与原始凭据不进入浏览器，Trader Sync 监控服务和 Notifications 不获得任何签名能力。

买卖订单及领取签名在后续执行设计中分别定义；认证或授权签名接口不能被用来签署这两类操作。现有 Worm 的敏感验证许可也不授权 Polymarket 操作，本段不追加用户未确认的逐笔二次身份验证。

### 6.3 会话、撤权与派发契约

接收启用确认时，用账户权威状态核对当前会话、Trader Sync 权限和 Wallet 操作权限，并冻结该次有效用户意图。[新登录替换旧登录](../identity-access/single-client-login.md)生效后，旧会话不能接收新命令；此前合法接收的原尝试继续按原意图处理和核对。

账号停用、模块撤权或 Wallet 控制关系变化与会话切换分别处理：未派发步骤再次检查独立资格；已发出的外部动作保留核对，不宣称能撤回已发生事实。原尝试不能因新的登录或绑定变化扩大确认范围。

单次派发许可、资格撤销与发送开始的先后，须与后续统一执行规格中的账户门禁采用同一协议，不能各自建立独立的检查后发送路径。该协议是本段实现的明确依赖，必须覆盖[既有账户门禁](../../../internal/accountstate/txgate/gate.go)与同库受控 adapter；账户锁、数据库事务和连接均不通过 RPC 传递。当前文章不把尚未落实的原子派发协议标为已实现。

## 7. 页面承接

用户任务为在目标详情中核准并准备自己的交易账户。沿用[Trader Sync 页面组织](../web-ui/trader-sync-manual-trading.md)和[已确认深色主题](../../requirements/web-ui/visual-theme.md)，不增加独立接入密钥表单。

页面按以下阅读顺序组织，电脑与手机保持一致：

1. **使用的钱包与账户：**Wallet 名称及完整 signer、实际交易账户、当前目标；多个候选只有在必要时展开选择。
2. **本次准备：**是否创建账户、已有有效步骤、需要取得的认证及具体授权对象／额度；主要按钮为确认启用或确认继续。
3. **执行结果：**逐步展示已确认、处理中、待核对或失败；一个步骤失败不清空其他成功证据。
4. **资金与操作资格：**显示实际账户余额及更新时间、明确的不可用原因和官网入口；历史同步进度独立展示。

用户无需理解 SDK 或服务内部错误码。页面显示可行动的原因，例如「账户控制关系待核对」「平台接入暂不可用」「授权结果待核对」；诊断详情按需展开。平台凭据异常归为服务问题，不能归为用户余额不足或要求用户填写平台密钥。

返回官网、刷新页面或切换设备时保留原账户与尝试上下文；账号切换后先重新核验可见性。绑定发生变化时，新操作显示新关系，已接收尝试始终显示原账户。手机错误提示与主要操作不被固定栏遮挡。

本段确定页面需要承接的事实与状态。正式视觉稿会与其他 Trader Sync 交易页面成组交付，不将文字设计标为视觉验收。

## 8. 服务、配置和故障范围

本段属于已确认的独立 Polymarket Trading 服务，Wallet 继续独立运行。内部接口默认 gRPC；API 只负责会话、协议和安全投影，不持有交易执行 runtime。适用[服务开发规范](../../developer-guide/service-development-standards.md) `SDS-R1`、`SDS-R2`、`SDS-R7`。

| 所有者 | 自身配置与依赖 | 故障影响 |
| --- | --- | --- |
| Polymarket Trading | 本服务数据库、内部调用身份、Builder／Relayer 配置、CLOB 凭据加密配置、官方端点、Polygon 只读 RPC、已核准合约配置版本 | 按账户发现、创建、认证、授权、资产读取分别报告能力；Builder 不可用不自动使全部公开读取失败 |
| Wallet | 自身密钥加密配置、归属存储、专用调用身份、签名协议及核准配置版本 | 签名不可用时不发起依赖签名的新步骤；原远端结果仍由交易服务核对 |
| API／账户权威边界 | 当前会话、模块权限与命令接收资格 | 失效会话拒绝新命令；已合法接收记录不丢失 |

初版各外部调用及内部 RPC 均设置可配置的有界 deadline，超时按是否可能已发出分类；具体数值与统一执行规格的时限表一起确定，不能由 SDK 默认重试次数决定资金操作语义。读取核对可有界退避，外部副作用发送不能因通用 HTTP 自动重试而重复。

部署时只校验本服务及声明依赖的配置；服务自己的后台队列和连接池由其 runtime 持有。停止接收新任务后，有界结束当前派发并保存未知状态，重启从持久记录恢复核对。局部账户接入组合需要交易服务、Wallet、API 及必要数据库；涉及目标绑定时加入 Trader Sync，Notifications 不成为账户启用的强制运行依赖。真实命令、监听地址和资源收尾由实施计划落实，当前没有新增可运行服务。适用 `SDS-R3` 至 `SDS-R6`。

## 9. 验证场景与本次结论

### 设计与实现须覆盖的场景

| 场景 | 需要观察到的结果 |
| --- | --- |
| 仅打开设置、查候选或刷新预览 | 无认证签名、凭据创建、账户部署、链上授权或入金请求 |
| 已有 Deposit、Proxy、Safe 或符合条件的 EOA | 实际账户、控制关系、协议选择正确；已有资金与持仓不改址 |
| UUPS／beacon 候选不同、多个账户、未知实现 | 不按默认 SDK 路径静默选择或创建；原因与候选可核对 |
| 错误 Wallet、他人账户地址、Session Key 回退 | 拒绝未经证明的控制关系，不泄露其他用户记录 |
| 新账户创建 | 明确确认先于外部请求，实际地址与预期一致，官网可操作同一账户 |
| 重复点击或提交响应丢失 | 同一提交返回同一尝试；查询不创建账户或步骤 |
| 某些步骤成功后中断 | 已确认步骤复用；未知步骤先核对；用户继续只覆盖剩余已确认内容 |
| 凭据或授权响应丢失、nonce 变化 | 核对原意图与原标识，不自动换 nonce、重签或扩大授权 |
| signer、账户、chain、目标合约、额度或摘要被修改 | Wallet 拒绝与批准内容不符的签名请求 |
| 新登录、模块撤权、绑定变化、服务重启 | 新命令资格正确；原步骤按既有意图及撤权边界处理，未知结果保留 |
| 官网入金后返回 | 核准相同交易账户的实际余额；不把充值地址与账户地址混用 |
| 当前条件就绪但旧历史未齐 | 当前操作按自身条件可用，历史持续显示实际覆盖 |
