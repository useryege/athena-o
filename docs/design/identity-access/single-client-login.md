# 单客户端登录：目标技术设计

> 设计状态：设计中。单客户端登录及新登录替换旧登录的业务规则已确认；本文整理目标契约，具体存储、接口和交易接收顺序继续细化，尚未实现。现有凭据能力见[账户凭据](account-credentials.md)。

用户已经确认[单客户端登录需求](../../requirements/identity-access/single-client-login.md)：同一个账号只保留一个有效客户端登录，新登录生效后旧登录立即失效。这是账户凭据层的目标能力，覆盖受保护业务入口，不局限于 Trader Sync。

## 现状与目标差距

当前差距已通过源码核对：`IssueLoginSession` 生成登录 JWT，登录分支的 `ValidateCredential` 核对身份绑定；`CreateExternalLogin` 随后记录登录审计。`RecordLogin` 更新登录时间等身份审计字段，没有保存唯一有效登录 JTI。`AuthenticateToken` 检查访问权限和逐令牌撤销，但未核对该登录是否仍为账号当前会话。因此不能把当前已实现的 JWT 和撤销机制描述为已经支持单客户端登录。

源码依据：[会话签发与凭据核验](../../../internal/accountcredentials/manager.go)、[登录与请求认证](../../../util/session/sessionmanager.go)、[登录审计存储](../../../internal/accountstate/store/sql_store.go)、[令牌撤销缓存](../../../util/session/state.go)。

## 目标契约

建议在账号权威状态中维护当前登录标识及必要的生效版本，登录凭据继续使用独立 JTI。具体存储字段和接口留给实施规格；目标契约如下：

| 边界 | 目标处理 |
| --- | --- |
| 新登录完成前 | 验证 provider、realm、账号绑定与当前登录资格；失败不替换旧登录 |
| 新登录生效 | 原子更新唯一有效登录并记录审计；先准备可用凭据，再完成切换，成功后返回新登录。并发登录按服务端生效顺序确定唯一当前会话 |
| 后续身份校验 | 登录凭据必须匹配账号当前有效登录；旧 JWT 即使签名和过期时间仍有效也拒绝，不依赖客户端主动退出 |
| 登录响应丢失 | 若替换已生效，不能恢复旧登录；恢复需维持同一账号至多一个当前会话 |
| 旧客户端退出 | 只撤销它自己的 JTI；仅当它仍为当前登录时才能清除当前会话，不能清掉新登录 |
| API Key 与其他账号 | 沿用各自权限及凭据校验，不因浏览器登录切换错误撤销独立账号或把 API Key 当作登录会话 |

当前撤销缓存通过订阅和定期同步更新，不能单靠缓存通知承诺账号级立即替换。后续请求须依据能够反映已生效替换的权威会话状态；多个入口或进程不能继续接受过期的本地「当前登录」副本。浏览器会话及派生敏感凭证要在实际操作边界验证有效登录，不能只在进入页面时检查一次。

旧客户端得到可辨识的会话替换原因后清理对应缓存、草稿执行许可及敏感状态，停止旧请求，并提示重新登录。服务端失效不等待页面重绘；长连接收到后续业务消息时同样校验当前会话。共享同一登录状态的标签页属于一个客户端，不能用每个标签页不同的临时 ID 把它们互相踢出。

## 与交易接收和后台执行的顺序

交易请求的合法接收与会话替换需要明确先后：切换生效前已经基于当时有效登录取得用户明确授权、并由后端合法接收的提交，按原记录继续处理和核对；生效后旧会话不能再取得新的提交许可。客户端切换不会取消或复制已发送的交易。

这项会话替换不等同于账号模块撤权或钱包控制权变化。已接收操作仍复查这些独立资格，沿用既有撤权门禁与服务边界；具体接收事务、可信调用凭据及发送许可的原子顺序须在交易执行规格中落实，不能仅凭 API 最初的一次 JWT 校验放行后续旧请求。

## 后续验证与实现状态

后续验证至少覆盖新旧客户端替换、并发登录、替换前失败、提交响应丢失、旧端迟到退出、敏感凭证复用、服务重启、过期缓存、不同账号隔离，以及切换前后交易接收与幂等。当前仅完成需求及目标契约整理，没有修改会话签发、验证或存储实现，也未进行真实多客户端登录验收。
