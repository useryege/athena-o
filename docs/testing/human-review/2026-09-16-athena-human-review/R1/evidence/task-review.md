## 发现

### [P2] 既有 Git 授权被“原始版本”条件错误收窄

位置：`/home/yege/work/athena/.codex/skills/publish-multi-repo-prs/SKILL.md:132`

该规则要求修复轮只有在原授权的“version”覆盖后续版本时才能复用发布或合并授权；同样的限制还写入 `/home/yege/work/athena/.codex/skills/athena-human-review/SKILL.md:77` 和 `/home/yege/work/athena/AGENTS.md:82`。人工报告触发的修复必然产生新版本，因此按字面执行时，先前针对同一开发任务、仓库和交付动作的明确授权几乎总会因版本变化失效，代理会把修复保留在本地或再次请求用户授权。这个结果与实施契约“第六步的既有 Git 授权保持有效”、已确认设计 `/home/yege/work/athena/docs/superpowers/specs/2026-09-16-post-delivery-human-review-design.md:45` 中“修复产生新的提交或 PR，并按已有授权处理”，以及不重复确认未改变决定的项目规则冲突。

应按原授权实际表达的仓库／分支或 PR 范围、动作和显式限制判断；只有原授权明确绑定某个不可变版本，或后续动作、目标、范围发生变化时，才因版本要求新的决定。三处规则需要同步修改，避免一处仍把修复版本默认视为越权。

### [P2] “必查项已通过”阻断了用户明确接受例外后的合法最终交付

位置：`/home/yege/work/athena/.codex/skills/athena-human-review/SKILL.md:77`

最终入口要求所有“必查项已通过”，同时又说问题或例外可以已有处置。已确认设计 `/home/yege/work/athena/docs/superpowers/specs/2026-09-16-post-delivery-human-review-design.md:247` 至 `:250` 明确区分：受阻、未执行或不确定项目不能自动算通过，但遗留项在用户明确接受例外、调整范围或批准设计变更后可以结案；`human-report-template.md:55` 也专门保留了用户接受例外的字段。若用户明确接受某个失败或无法执行的必查项为例外，该项仍不可能成为“已通过”，当前技能因此要么错误阻止最终交付，要么诱使代理把例外伪写成通过。

应改为要求每个必查项都有真实结论，未通过、受阻或未执行项不能自动算通过，且只能在用户明确接受例外／范围调整／设计变更并记录范围后结案；仍须保留准确轮次和版本、AI 证据、问题处置及环境状态条件。
