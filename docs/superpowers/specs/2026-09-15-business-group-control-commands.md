## 1. 方案选择

已确认采用**请求去重、状态版本校验和持久操作记录**。同一请求只产生一次决定，冲突操作必须基于最新状态重新发起；停止生效还需要确认所有受控入口已关闭。

| 命令方案 | 处理方式 | 判断 |
| --- | --- | --- |
| 请求去重＋状态版本校验（已采用） | 重试返回原操作；新请求核对管理员看到的状态版本；同向操作可复用，冲突不自动排队 | 可以解释谁基于什么状态作出决定，防止旧页面和迟到请求覆盖新决定 |
| 按点击顺序排队 | 将相反命令排队，前一个结束后执行下一个 | 后续可能执行管理员已经不再需要的启动，不采用 |
| 后到命令覆盖 | 后收到的目标覆盖先前目标 | 网络延迟可能让旧启动覆盖新停止，不采用 |

单纯广播停止或等待缓存过期，不能证明全部入口已拒绝新工作。停止流程采用下文的关闭确认；代价是收到请求与停止生效之间存在可见的确认阶段，失联时可能无法完成生效确认。

## 2. 请求身份和状态版本

每个请求关联环境、业务组、可信管理员身份、请求编号、动作及管理员看到的控制版本。请求编号由调用方在首次提交前生成，重试沿用同一编号和内容；服务端另返回持久操作编号，供查询进度。

- 去重范围为环境、管理员身份和请求编号，内容包括组、动作与预期版本。同编号不同内容直接拒绝，不能改写原请求。
- 每次调用先验证当前身份与权限，再查询去重记录；去重不能绕过撤权。原请求已存在时返回其原决定及关联操作，不重新进行启停；同时提供当前组状态，避免把历史启动成功显示成当前仍运行。
- 新编号请求才检查控制版本。版本不匹配则返回冲突与最新状态，不自动改版本重试；管理员刷新后重新决定。
- 通过校验的新编号请求都消耗一次控制版本，包括复用进行中的操作和“已经运行／停止，无须再次执行”的请求；这记录本次管理员意图，阻止并发旧版本的相反命令随后生效。相同编号重试和拒绝请求不消耗版本。运行开放、故障、成员身份变化与收尾完成等影响判断的变化也递增版本，普通心跳不递增。每次实际启动使用新的运行代次，复用或无须执行的请求不增加运行代次。
- 操作及去重记录由控制服务持久保存。本阶段不设计删除去重记录的策略；历史编号不得因进程重启或记录归档而变成可重新执行的新命令。
- 身份、版本或依赖校验拒绝的请求记录明确拒绝结果，不自动排队。后续条件变化后必须使用新请求编号，表达一次新的管理员决定。

## 3. 同一业务组的命令规则

下表处理通过身份、去重及版本检查的新请求。完全相同编号的重试始终先按原记录处理。

| 当前状态或操作 | 新请求 | 已确认处理 |
| --- | --- | --- |
| 已停止，停止证据有效 | 启动 | 检查依赖与成员，创建一次启动操作，进入启动中 |
| 启动中 | 再次启动 | 返回正在进行的启动操作，不重复初始化、不延长原时限 |
| 运行中且控制依据有效 | 启动 | 返回已运行，无须再次启动，不增加运行代次 |
| 启动中或运行中 | 停止 | 通过依赖检查后预约停止；使本次启动后续开放决定失效，进入关闭确认流程 |
| 正在关闭入口，或已进入停止中 | 再次停止 | 返回同一停止操作及进度，不重新计时、不重复创建收尾任务 |
| 正在关闭入口，或仍有未确认收尾 | 启动 | 拒绝并说明尚未完成停止，不排队等候自动启动 |
| 已停止，停止证据有效 | 停止 | 返回已停止，无须再次执行；保留以前失败的历史记录 |
| 无法确认当前状态 | 启动 | 拒绝，先恢复状态确认；旧页面不能用于启动 |
| 无法确认成员执行状态 | 停止 | 控制服务仍能校验当前控制版本和依赖时，可以建立或继续停止确认；连控制记录都无法核对时返回不可用或提交结果未确认，不能宣称停止已生效 |

重复操作在审计中保留本次调用者与所复用的操作编号。“启动中允许停止”不豁免依赖检查；需要取消的准备工作仍计入收尾。停止超时也不能用新请求重置时限或跳过未确认工作。

两名管理员同时提交时，以服务端持久裁决顺序为准，不按浏览器点击时间排序。例如 A 基于版本 12 启动，B 同样基于版本 12 停止：先完成控制版本变更的一方生效，另一方收到版本冲突；B 若仍要停止，取得最新状态后重新发起。故障触发的系统停止不依赖过期页面版本，但必须在同一控制顺序内执行并使旧启动失效。

即使 B 看到的组已经停止，B 的新停止请求返回“已停止，无须执行”时仍把版本推进到 13；迟到的版本 12 启动不能在此之后开启业务。这只记录控制意图，不重新运行停止任务。

## 4. 跨组依赖与事务边界

控制服务用本环境 PostgreSQL 的一个控制协调记录串行化短暂的命令裁决。在短事务内完成版本、成员身份、依赖和既有操作检查，并保存新决定或停止预约。成员变更、启动完成与故障停止也遵守这一顺序，不能绕过命令检查更新状态。

环境级串行化仅用于控制状态变更，不把业务请求、外部 HTTP、成员准备或收尾放进该事务。事务提交后再执行带操作编号的成员调用，并以新短事务条件更新结果；可重发控制消息，不能因此重新发送业务请求。PostgreSQL 的行锁在事务结束时释放，本方案用持久操作记录承接跨事务协调。[PostgreSQL 16 锁规则](https://www.postgresql.org/docs/16/explicit-locking.html#LOCKING-ROWS)

若 A 必需依赖 B：

- 启动 A 必须确认 B 当前运行且没有停止预约；A 从接受启动到完成停止收尾期间均占用依赖关系，包括启动中、停止中和结束未确认。
- 停止 B 与启动 A 使用同一控制顺序。A 先获得依赖占用，B 的停止被拒绝；B 先预约停止，A 的启动被拒绝。不会出现双方都检查通过后分别提交。
- 依赖占用仅在 A 的收尾结束证据成立后释放，不能因请求超时或某成员失联释放。B 故障时按 R14 停止 A，故障恢复不自动重开。
- 依赖配置和控制成员集合的版本同样受协调。执行中的操作不得通过临时删掉未响应成员或依赖来凑齐成功条件。

## 5. 启动的接受、开放与完成

1. 校验通过并持久记录启动操作、依赖占用和新运行代次，是启动接受点。目标为运行，阶段为启动中，入口仍关闭。
2. 成员依据匹配的环境、操作、代次与本次进程身份准备资源，管理通道常驻；准备结果只能用于本次启动。
3. 全部必需成员与依赖具备约定就绪证据，且没有新的停止预约、成员变化或故障决定时，控制服务条件提交整组开放决定，转为运行中，启动操作完成。业务只能凭匹配该决定的有效控制依据开放；广播已经发出不是就绪证据。
4. 任一准备失败或启动被有效停止预约取代，旧启动不得再开放；停止本次工作并保留失败／被取代原因。启动失败后的实际阶段按 D02 的收尾规则显示。

本段不承诺多个进程在同一物理时刻开始执行。它要求任何业务开始前，整组所需能力已经就绪且当前开放决定有效；成员之后丧失能力时进入既定故障停止流程。

## 6. 停止：先确认关闭入口，再报告生效

### 6.1 三个时点

| 时点 | 对外可声明的事实 | 组状态与业务行为 |
| --- | --- | --- |
| 请求已收到并预约 | 已保存请求及操作编号，正在关闭和核对入口 | 不报告停止已生效；停止预约阻止新启动与新的依赖占用，已收到关闭指令的入口立即关闭 |
| 停止已接受／已生效 | 本次所有受控入口已关闭，旧许可不能再发起新工作，控制服务已持久提交确认 | 此时目标变为停止、阶段为停止中；这是 R09 的停止接受点，从此不允许新业务；R20 的页面最多 5 秒更新从此计算 |
| 停止已完成 | 业务执行及全部必要收尾已取得结束证据 | 阶段为已停止，停止操作完成；依赖占用可释放 |

“请求已收到”只表示收到提交，不等于后台已接受停止决定。预约阶段使用操作进度“正在关闭业务入口”；不新增 D02 的业务执行阶段。原阶段只能作为最近确认信息，页面在这一阶段也隐藏该组业务数据，不能将部分入口已关闭的组仍显示为正常可用。

上表描述管理员主动停止。已确认故障或重启触发的系统停止，仍按 R08／R11／R14 直接设置停止目标并立即关闭可控制入口，不受手动停止的依赖方先停条件约束；缺少全组关闭或收尾证据时展示未确认范围，不提前报告全组停止已生效或完成。

### 6.2 关闭确认机制

1. 先在控制事务中校验身份、版本和依赖。校验拒绝时不关闭任何入口。通过后持久预约停止，冻结本次受控入口集合、推进控制版本，禁止旧启动完成和新的开放决定；后续不是被拒绝请求的自动排队。
2. 给集合中的每个适配器发送绑定环境、组、操作、代次和进程身份的关闭指令。集合包括业务服务、核心 API 中对应的业务入口，以及 Notification 等核心服务中的该组代办工作；核心自身能力不关闭。
3. 各适配器先锁定本组的关闭状态，拒绝新的业务读取、写入、任务领取与外呼启动；关闭结果在本次进程中保持，旧消息不能重开。首次启动或进程重启默认关闭；新进程身份使本次集合发生变化，控制服务必须重新核对，不能沿用旧进程确认。
4. 关闭必须与本地业务开始路径使用同一个同步边界。已经拿到许可但尚未进入执行路径的工作，必须在开始前再次经过该边界；不能把数据库中的许可或发送时间字段当作它已执行的证明。
5. 通用保守实现中，本地执行守卫覆盖一次业务读取／短事务或一次实际外部调用，直到该调用退出才释放；停止先关闭新守卫申请，再取消并等待已进入的守卫退出，才报告入口关闭。守卫属于本组，不持有跨 RPC 的数据库事务，不锁住其他业务组或核心自身工作。外呼退出但结果未知时保留未知与收尾记录；不自动重发。
6. 后台长任务不在一个守卫内持续执行多个业务步骤。领取及每次新业务动作分别经过控制边界；停止后的必要收尾使用已登记工作身份和受限收尾路径，不能取得新的业务执行权限或派生新任务。内部子调用和后台协程不能逃出所属适配器的控制与结束核对。
7. 适配器只有在旧启动路径不再可能发起动作时才回报关闭，并列出还需收尾的既有工作。控制服务收齐当前集合的有效关闭证据，再用短事务复核没有新身份或冲突变化，提交停止生效记录；此后继续收集收尾结束证据。

控制入口集合来自已核对的服务声明与实际消费者，不能漏掉未登记入口或用空集合报告成功；尚未完成控制接入的业务组不具备启动条件。核心代办工作的来源组从可信服务身份和持久工作关系核验，不能让请求方自称核心业务绕过控制。

保守守卫可能让停止生效等待一次正在执行的请求退出；不能先释放守卫，再把尚未发出的 HTTP 当作“已开始”来提前确认。对某条路径若要缩短等待，必须另行证明其真实开始边界与取消／结束语义，当前方案不依赖这一优化。

**通知的现状核对**：[发送工作者](../../../internal/notification/worker.go)先提交许可，再调用 Sender；[Telegram transport](../../../util/telegram/send_transport.go)的 started 回调发生在包装层进入 RoundTrip、调用下层 transport 之前。该回调可记录现有发送观测，但不能单独证明严格停止边界。新控制必须覆盖许可后等待、实际调用及其退出；原有账户撤权与许可事务保持自身原子性，不把 HTTP 放进它们的事务。业务消息因本次停止尚未发送时按 R10 暂停保留，不能由通用取消错误误写成永久失败；具体存储映射由 Notification 接入设计补齐。

### 6.3 缺失证据和超时

- 任一可能执行本组业务的入口无法确认关闭，就不能写停止生效时间。显示“停止生效未确认／需处理”、已关闭范围、未确认成员和最近证据；保持停止预约，禁止新启动，已关闭入口不自动重新开放。
- 心跳过期、RPC 超时、端口释放或新进程上线，都不能替代旧进程已无执行能力的证据。不通过结束进程或排除故障成员来强行完成管理员业务停止。
- 确认超时和生效后的收尾超时分别记录，不能靠不断重试延长原时限。相同停止操作可继续核对既有证据；这不重新执行业务，也不自动启动。
- 进程或控制服务重启后，从持久记录恢复停止与收尾义务；旧启动操作不得作为重新开放的依据。控制存储不可用时不得报告已生效或完成，能够确认关闭的入口保持关闭。完整启动批次、租约与故障探测参数在下一段设计。

上述边界选择了“不能证明就不报告成功”。有限超时并不保证停止必然完成，只保证不会无限隐藏未确认状态或用超时伪造完成。

## 7. 响应丢失、旧消息和审计

请求提交前就保存请求编号。RPC 超时后用相同编号查询或重试；若已持久预约／接受，返回同一操作，控制服务按持久记录继续推进，不以浏览器在线作为操作存活条件。关闭页面只结束页面等待，不撤销已经持久记录的控制流程；真正改变目标仍通过新的合法控制命令。

成员调用的取消与结束必须由适配器配合确认。gRPC 取消通常无法直接中断应用处理函数，因此“取消信号已发送”不能作为任务结束证据。[gRPC 取消说明](https://grpc.io/docs/guides/cancellation/)

所有成员消息绑定环境、组、操作编号、运行代次和进程身份；不匹配的响应可记录诊断，但不能改变当前状态。已关闭适配器拒绝旧开放消息。接收新开放指令时仍核对当前控制依据，不能只比较数值大小。控制实例失去当前协调身份后不能继续提交决定；其旧消息不能绕过成员核对。

审计保存发起人、请求内容摘要、原状态版本、裁决与拒绝原因、复用的操作、依赖占用、成员身份、收到／生效／完成时间及未确认证据。请求记录、原操作结果和当前组状态分别展示；不通过审计返回停止组的业务正文。

## 8. 验证场景与本段边界

| 后续必须验证的场景 | 判定依据 |
| --- | --- |
| 同编号重复提交、内容被改、响应丢失后重试 | 同内容只创建一次决定；改内容被拒绝；历史启动不会重新执行 |
| 两个管理员同版本发相反命令 | 一个取得新版本，另一个冲突；无自动覆盖或排队 |
| 已停止组收到新停止请求，随后旧版本启动迟到 | 新停止虽无须执行仍推进版本，旧启动被拒绝 |
| 新编号的重复启动／停止 | 复用进行中的操作，不重复创建任务或重置时限 |
| 启动准备完成与停止预约并发 | 预约先提交则旧启动不能开放；开放先提交则停止按最新版本重新裁决 |
| A 启动与被依赖 B 停止并发 | 依赖占用和停止预约不能同时获准 |
| 已获许可的通知暂停在 HTTP 前，再发停止 | 守卫未退出前不得报告生效；关闭后不得再使用旧许可发送 |
| 收齐确认前出现旧成员失联、新身份注册或迟到确认 | 不使用过期集合确认成功，已关闭入口保持关闭 |
| 生效确认或结果提交响应丢失、控制服务重启 | 按原编号和持久事实恢复核对，不能重开业务或重发外部动作 |
| 一个组停止时核心通知和其他组继续工作 | 同步边界按组隔离，核心功能不被业务守卫一同锁住 |
| 停止确认超时、收尾超时、外部结果未知 | 各阶段如实展示，不误报生效／完成，不自动重发 |
