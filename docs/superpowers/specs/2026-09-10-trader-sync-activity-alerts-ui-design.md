# Trader Sync / Activity Alerts UI 设计规格

> 日期：2026-09-10。状态：已确认待实现；用户已整体确认完整书面规格。
>

## 1. 目标、范围与决定

用户能够确认并订阅人工挑选的低频 Polymarket 目标，持续查看跨目标成交，理解监控与 Telegram 的分别状态，并从 Telegram 返回同一份站内详情。管理员只读了解订阅和运行概要。桌面优先，手机完整覆盖添加、阅读、绑定衔接和订阅管理。

设计阶段形成书面规格、可丢弃的交互线框及长期文档；实现范围由已确认的联合计划承接。后端的同库事务、两进程、共享 WSS、最终确认、无历史回补、发送许可、普通/摘要分配与未知不重发等决定继续有效。首期 10 人、每人 10 个未取消订阅；不增加交易执行、跟单参数、高频准入、收益持续刷新、手动重发、逐订阅渠道设置或整站改版。

| 已确认选择 | 收益与代价 |
| --- | --- |
| 桌面优先，手机完整可用 | 桌面便于对照资料；手机从 Telegram 进入后可完成操作，需要适配长内容和折叠目标栏。 |
| 交互线框，沿用 ATHENA | 可实际验证路径与状态；线框不代表像素级成品或真实业务联调。 |
| A：主页活动与目标同屏 | 同时看到活动和监控健康；桌面列表稍窄，手机折叠侧栏。比较过“先选目标”和“Activity/Subscriptions 标签页”两种方案。 |
| 独立添加页 | 完整身份、六区间 P/L 和手机阅读空间充足；离开主页，需保留返回位置。比较过宽抽屉。 |
| 管理集中在列表和目标详情 | 主页便于扫读；暂停、备注等操作多一次进入详情。 |
| 独立活动详情与摘要页 | 与 Telegram 深链接共用，完整表达事实和多条结果；返回列表需恢复上下文。 |
| 新活动提示后点击载入 | 阅读、复制与历史位置稳定；查看最新活动需一次点击。状态仍每 5 秒刷新。 |
| 复用 Notifications；管理员概要与 Service Status 分工 | 沿用已有绑定及运维入口；诊断时可能需要跨页，提供相互链接。 |

这些选择已逐节确认，无需再次选择。以下接口细化由技术核对得出，已随完整书面规格整体确认；不是已实现事实。

## 2. 信息架构与导航

会员应用在 Markets 分组增加 `Trader Sync`，仅当前具有 `trader_sync` READ_WRITE 的会员可进入。管理员应用在 System 分组增加同名概要入口。会员与管理员页面、service、DTO 和权限判断分开，不以隐藏按钮实现隔离。

下表为应用内路由；实际 URL 由既有 deployment base / application base 组合，兼容 `/athena/` 等部署前缀。

| 应用 | 路由 | 页面 |
| --- | --- | --- |
| member | `/trader-sync` | 跨目标活动主页与当前目标侧栏 |
| member | `/trader-sync/add` | 解析、确认与创建 |
| member | `/trader-sync/subscriptions` | Current / Cancelled 订阅列表 |
| member | `/trader-sync/subscriptions/:subscriptionId` | 目标状态、备注、操作与观察历史 |
| member | `/trader-sync/activities/:activityId` | 成交事实及本活动通知结果 |
| member | `/trader-sync/summaries/:batchId` | 冻结摘要的全部分条与关联活动 |
| member | 既有 `/notifications` | Telegram 绑定、解绑及重绑 |
| admin | `/trader-sync/subscriptions`、`/:subscriptionId` | 独立只读概要列表与详情 |
| admin | 既有 `/service-status` | 增加 Trader Sync 运行健康区域 |

主页、详情、Telegram 链接使用相同资源 ID，不接受 URL 中的 account_id 来覆盖 owner。登录后通过既有 returnTo 返回原站内路径，保留合法 query/hash；不接受外部返回地址。详情入口没有列表上下文时，返回到本模块主页或对应订阅列表。普通详情与管理员概要不能互相复用深链接。

## 3. 活动主页

桌面在现有应用壳内采用活动主区、右侧目标区。页头显示 `Trader Sync`、简短能力说明和 `Add trader` 主操作；Telegram 状态及 `Manage subscriptions` 为次级入口。目标区展示配额 `n / 10`、全部目标筛选、每个未取消目标的身份/备注、六态状态及异常提示，不塞入暂停/取消按钮。

活动主区包含订阅筛选、结算时间范围、更新时间、新活动提示、活动列表和游标翻页。默认读取 owner 全部历史，包括已取消订阅形成的活动。点击侧栏目标按该 subscription_id 筛选；同钱包取消后重新订阅形成新 ID，不把两段历史混为一个订阅。清除筛选回到全部活动。筛选仅影响阅读，不修改监控或通知资格。

首期不增加方向、市场或收益排名筛选。日期输入按 UTC+8 解释，转换为 UTC 的结算时间区间 `[from,to)`；未指定范围表示全部。活动按形成顺序显示，新收到但结算较早的记录也可成为新活动，不能把列表标题写成“按结算时间排序”。具体稳定排序与刷新协议见第 10 节。

| 每条活动的信息 | 展示规则 |
| --- | --- |
| 目标 | 形成时备注快照、目标显示名及钱包识别；可进入原订阅。当前备注改变不回写历史。 |
| 成交事实 | 市场标题或可靠 Position ID、真实 Outcome、BUY/SELL、成交额及币种、份额、明确标注的 `Settled at`。 |
| 通知 | 仅站内 / 普通 / 摘要及各自状态；不把监控健康和 Telegram 结果合并成一个徽标。 |
| 资料状态 | 缺失信息有独立标记；无可靠链接时不能提供猜测的市场地址。 |
| 操作 | 明确的站内详情入口，与市场外链分别可聚焦；外链新标签页，点击不触发行跳转。 |

手机先展示页头及全局异常，再展示折叠的目标面板和活动卡片；面板收起时仍显示所选目标、配额和异常数量。信息的先后顺序与桌面一致，钱包/长标题允许换行，金额不可通过截断丢失数值。

空态必须区分：没有订阅（引导添加）；监控正常但尚无活动（说明开始边界和不补历史）；筛选无结果（清除筛选）；只有暂停/异常目标（引导查看状态）。网络失败不显示成无活动或未绑定。

## 4. 添加目标与确认卡

独立页面分为输入、解析结果、确认三个阶段。输入接受合法地址或获准的 Profile URL；不接受只填名字。回车提交解析，加载时保留输入。重新解析前不自动创建，确认按钮始终是明确的 `Confirm subscription`。

1. 解析成功先展示身份：头像、名称、认证标记、完整规范钱包、可验证 Profile 链接及资料查询时间。钱包始终可见、可复制，不能只以缩写代替确认身份。
2. 展示加入时间、持仓价值、最大盈利、原始口径 Predictions；每项按自己的可用性显示，不以其他统计替代。辅助失败不阻止确认，身份失败则没有有效确认按钮。
3. P/L 恰好六个区间 `1D / 1W / 1M / 1Y / YTD / ALL`，默认 1Y。切换读取本次返回快照，不另发请求。区间标题值与曲线独立判断可用性；缺失区间仍可选择并看到原因，不静默回退到另一区间。真零、负值与未知分别显示。
4. 曲线提供轴、单位、时间范围与可访问的文字摘要；悬停不是取得关键数值的唯一方式。图形坐标可在保留精确原值后做有限视觉归一化，tooltip/复制仍取原字符串，不能由浮点绘图值反推金额。
5. 私有备注显示 owner 对该钱包保存的当前值；计数按 Unicode code point，最多 20，超限展示错误并禁止提交，不静默截断。输入按纯文本，不渲染 HTML/Markdown。
6. 创建前显示低频定位提醒，不增加勾选确认。未绑定 Telegram 可继续创建，说明将保留站内活动并提供 Notifications 入口。
7. 创建成功返回原主页筛选上下文并突出新目标；若原筛选不包含新目标，不擅自重置，只在侧栏定位它并提供切换操作。新目标显示 `Preparing monitoring`，取得成功基线后才能显示 `Monitoring` 与生效时间。

确认 token 有效 5 分钟，过期禁用确认并提供重新解析；保留用户输入及同目标备注草稿。输入修改立即废弃旧卡和 token；解析出另一钱包时载入该钱包保存的备注，不能把上个钱包草稿静默沿用。已存在未取消订阅时显示现有状态和详情入口；配额已满说明所有五种未取消状态均占位，提供管理入口。

Resolve 返回的配额/重复提示只作快照，Create 在事务中最终判定。Create 期间禁止重复点击；响应未知时保留原 request_id 和完全相同 payload 进行结果重取。服务端复核当前权限后，先返回已经提交的幂等成功，再判断 token 是否过期/已消费；不能因为响应丢失生成新创建意图。重新解析使用新 token 时生成新 request_id。

## 5. 订阅管理与观察历史

完整列表默认 Current，另有 Cancelled。Current 包含 pending_baseline、monitoring、paused、error、permission_disabled，全都占名额；Cancelled 默认隐藏，不占名额。列表展示当前备注、身份、状态、生效/最近可靠观察、旧通知概要并进入详情。取消历史使用游标，不要求所有历史一次加载。

详情从上到下为身份及完整钱包、当前状态与原因、备注、可用操作、观察历史、活动和旧通知入口。状态及操作如下：

| 后端状态 | 英文展示 | 允许操作（当前有 grant） |
| --- | --- | --- |
| pending_baseline | Preparing monitoring | 编辑备注、取消 |
| monitoring | Monitoring | 编辑备注、暂停、取消 |
| paused | Paused | 编辑备注、恢复、取消 |
| error | Monitoring interrupted | 编辑备注、暂停、取消；依赖恢复由后台自动建立新观察边界 |
| permission_disabled | Disabled by access change | 编辑备注、手动恢复、取消；重新授予权限不自动恢复 |
| cancelled | Cancelled | 编辑钱包保留备注、查看历史、进入添加页重新订阅；不能恢复原订阅 |

暂停和恢复直接执行；操作附近及成功状态明确提示“已排队通知仍可能稍后到达”。恢复先进入 Preparing monitoring。取消只确认一次，弹窗展示完整目标身份，并说明不可恢复、释放名额、保留历史和旧队列继续完成。取消后的再次订阅走完整解析确认流程。

同一资源写操作进行中禁用其他冲突动作。成功以服务端结果更新状态及 revision，不乐观显示已经监控。Aborted 重新读取最新状态并提示变化，不自动把旧动作套用到新状态。备注冲突保留本地草稿，展示服务器最新值，用户再次保存时使用新 revision。其他可确定失败保持草稿，错误对应可操作原因。

备注按 owner-wallet 保存，当前值与活动快照分开。未修改时 Create 省略 note 表示沿用，清空用显式空字符串。已取消详情编辑的是该钱包保留备注，可影响当前/未来同钱包订阅；文案明确它不会改写历史活动。

观察历史提供分页时间线，分别显示成功生效区间、中断起止/恢复、原因及可能遗漏。未知起止保留未知；无证据不显示遗漏条数。自动恢复不删除中断。它不是历史成交补查入口，也不因为最近无成交就判断监控异常。

## 6. 活动详情：事实、资料与精度

独立页面与 Telegram 普通提醒共用，主体先呈现“发生了什么”，随后单列通知结果，末尾展开来源与时间证据。

- 标题区：市场/组合、BUY/SELL、真实 Outcome、目标身份及形成时备注；提供原订阅入口。
- 成交区：完整钱包、结算时间、成交额及币种、份额、费用及费用币种。本条成交价标 `Fill price (value ÷ shares)`，由本条成交额除以本条份额计算，不包含费用，不称整单均价。
- 市场区：已核验链接与公开资料。缺资料仍展示真实 Position ID 和缺失原因。异步补全只更新显示资料，不生成活动、不改快照、不补发通知。
- 证据区：source_record_id、链/合约版本、交易/日志位置、原始整数及 decimals、接收/形成时间、公开时间证据等。按字段解释缺失，不用一串无说明的横线代替。

当前已核验三 Exchange 抵押币为 pUSD、6 decimals，份额亦 6；实际展示依 DTO 的币种和精度，不把 `usdcSize` 字段名当成 USDC 证明。成交额与费用分开；BUY 费用额外支付、SELL 费用从所得扣除，不能把成交额叫现金净变动。

业务数值和资源 ID 全程字符串/精确十进制；不用 JS Number 处理钱包、position、原量、金额或 revision。金额可以移除无意义尾零，不能缩写成 K/M、把微小值舍入为零或让复制值来自格式化后的浮点数。成交价分母非正/不可用时显示不可用；有限显示需要舍入时加 `≈`，证据保留完整输入和精确比值。列表过长数值换行或进入详情，不用省略号冒充完整值。

Combo 永远是一笔活动。组合 YES 表示所有腿条件满足；组合 NO 表示“并非全部条件满足”，不能把每腿各自取反。BUY/SELL 属于组合，不表示每腿分别成交。已知 N 条腿但 M 条资料缺失可显示 N/M；getLegs 整体不可用时腿数也未知，不显示“0 条”。长组合折叠为条件列表，用户可展开全部，保持逻辑关系和组合标识。

## 7. 通知结果与摘要详情

活动形成时固定 `notification_mode`，与当前账户绑定状态分开：

| 模式/阶段 | 界面解释 |
| --- | --- |
| in_app_only | 形成时未绑定，仅站内；以后绑定也不补发。 |
| ordinary | 展示本活动普通 delivery 结果。 |
| summary / waiting | 等待汇总，尚无冻结批次，不制造详情链接或发送成功。 |
| summary / frozen | 展示关联批次及本活动涉及的全部部分；进入独立批次页。 |
| summary / cancelled_before_freeze | 因旧资格失效终止，展示原因；没有空的成功批次。 |

| delivery / part 状态 | 文案语义 |
| --- | --- |
| pending | 排队中，可包括等待明确暂时失败的重试时间。 |
| sending | 已获单次发送许可；提交证据和结果尚需分别读取。 |
| sent | Telegram 已确认接收，不代表用户设备送达或已读。 |
| failed | 已确定最终失败，显示原因。 |
| unknown | 可能已被接收，结果无法可靠确认，不自动重发。 |
| cancelled | 未获新许可的旧工作已终止，显示撤权/解绑等原因。 |

缺少 started_at 不等于“还未调用”：sending 显示缺少提交起点证据；sent 仍显示已确认接收，并将提交时间标为未能记录、相关耗时不可判定。authorized_at、started_at、result_at 分开，不补造起点，不把许可当成功。

活动关联多个摘要部分时，展示所有相关部分的状态计数与分页列表；另外显示整个批次的进度，不能把一部分 sent 当作活动全部发送成功。每部分只显示状态、序号、原因和时间，不需要在首期增加 attempt 历史浏览器或原始消息正文查看器；保留持久证据，详情给最近 attempt 及总次数。

独立摘要页展示覆盖范围、活动总数、各目标计数、最老成员时间、批次首条实际提交时间，以及 pending/sending/sent/failed/unknown/cancelled 的分别数量。批次部分按序号翻页，关联活动按同批次过滤查看；两者分页状态独立。冻结后成员、分条序号和原始消息不变。只有全部部分 sent 才显示整批成功；未知、失败和待发不能合成模糊的单一成功状态。

普通提醒和摘要必须生成对应站内深链接，不能链接占位页面。摘要覆盖活动不再逐条补发；界面没有重发按钮。排队时延如实显示，前 10 条普通提醒不因同用户集中成交自动改成摘要。

## 8. Telegram 衔接与管理员页面

复用会员 Notifications 的二维码、deep link、待绑定/过期/失败、connected/unreachable 与既有轮询，不复制状态机。主页和确认卡可显示当前绑定摘要并链接该页；绑定状态与活动形成时资格分别解释，unreachable 不等于未绑定，不能据此改写历史为仅站内。

从添加页进入 Notifications 后，返回保留同 owner 的输入、备注与位置。草稿限当前会话内存，不把 token/备注放 URL；换账号、退出或撤权清空。恢复草稿不延长 token 的 5 分钟，过期需重新解析。直接关闭/重载页面不承诺恢复未保存草稿。

既有解绑/重绑确认文案补充：未获许可的旧队列终止，已获许可单条可能稍后收到，新绑定不补历史。沿用原有一次确认和重绑流程，不新增重复确认。

管理员概要列表支持账户、规范钱包和状态过滤，默认当前未取消，可选择包含已取消；分页不展示虚构总数。列为用户身份、完整钱包、订阅状态/关键时间、健康、活动数与关联投递状态计数。详情只展开相同安全概要、中断统计和时间，不提供私有备注、完整活动、消息正文、逐条投递，亦无暂停/取消/恢复/重发操作。

Service Status 增加连接状态与新鲜度、目标/关系数量、接收/确认/投影积压、元数据缺失、待发与结果数量及最近异常概要。沿用该页 10 秒可见轮询；与订阅概要互相链接。运行数据有 `as_of`，各积压明确单位；不能把 raw record、candidate、activity、delivery 混成一个总数。

管理员活动数按单个订阅全生命周期。投递数按关联的 distinct 逻辑 delivery（普通消息或摘要部分），不是 attempts；一部分关联多个订阅时在各订阅各计一次，明确标“Associated deliveries”，不得跨行求和当全局总数。全局数量单独按 distinct delivery 聚合。当前 gauge 与窗口计数区分，窗口项返回 window_start/window_end，进程累计项说明 service_epoch；不显示来源不明的“累计”。

## 9. 刷新、权限和异常交互

会员 Trader Sync 页面可见时每 5 秒发起一次去重刷新；隐藏时停止，恢复可见立即刷新。详情更新状态和资料，主页重读当前页并查询新活动标志，不轮流对每行发送 GetActivity。Notifications 保留既有 3 秒绑定轮询，管理员 Service Status 保留 10 秒；前台周期均不影响后台采集、通知或时效统计。

有新活动时显示 `New activity available`，不报无法证明的精确条数，不自动插入、移动行或切换筛选。点击后载入当前筛选的最新第一页，清除旧游标链并将焦点移至列表标题。未点击时持续更新旧行状态，保持选中文本、焦点、展开项和滚动位置；使用稳定 ID 的局部更新，状态变化不重挂载整行。

页面返回保留当前会话内的筛选、游标和滚动位置；不同 owner 不共享缓存。相同筛选的当前页刷新失败保留最后成功数据，标明过期、最后更新时间和重试入口。首次加载用骨架；失败显示明确错误，不能填入 0、空表或未绑定假状态。

服务端拒绝权限或会话已确认失效时，立即中止请求、递增页面 generation、清空模块数据及草稿，进入既有登录/access 路径。先前获准读取的响应可能晚到，必须按 owner/generation 丢弃，不允许恢复被清理内容。“立即”指前端获知撤权时；无推送协议时发现撤权可能等待下一次可见轮询/请求，后台在撤权提交后即拒绝新读取。重新授权可读取历史，permission_disabled 仍需逐个手动恢复。

跨 owner 与不存在资源使用相同 NotFound 页面；有权限但资源不可用不显示其他账户信息。InvalidArgument 定位输入/游标问题，游标无效提供返回最新；FailedPrecondition 提示重新解析；AlreadyExists 给自己现有订阅入口；ResourceExhausted 给配额和管理入口。不可确定的写结果只使用原幂等请求恢复，不用自动刷新触发新的写入。

## 10. 前后端契约补全

所有新增 RPC 使用动词开头 PascalCase，列表默认 50、最多 100。member owner 来自认证上下文；资源、游标、刷新标记在同一权限事务中校验。管理员只用独立安全 DTO/SQL。现有后端计划的接口表须按本节更新，不能仅新增前端页面。

| 接口 | 本轮补全 |
| --- | --- |
| ResolveTarget | savedNote 的存在性、noteRevision；现有未取消订阅 ID/状态/revision；配额 used/limit；六区间标题值与曲线的独立 evidence。 |
| CreateSubscription | 保持可选 note 存在性；当前权限检查后优先重取已提交成功，再判断 token 到期/消费。 |
| ListSubscriptions / GetSubscription | Current/Cancelled 查询；配额、当前状态及旧队列概要；详情只内嵌最近观察概要，全部历史分页。 |
| ListSubscriptionHistory | 新增 owner 内订阅观察时间线读取，含生效区间与中断、明确种类/时间/原因/不确定性，游标按时间与稳定 ID；GET `/api/v1/trader-sync/subscriptions/{subscription_id}/history`。 |
| ListActivities / GetActivity | 明确 notification_mode、summary phase、普通结果/相关部分计数；最近 attempt 时间证据及总次数；无界 attempts/parts 不内嵌列表。List 增加 summary_batch_id、刷新协议。 |

| ListSummaryParts | 新增冻结部分分页，可用同 batch 的 activity_id 过滤；序号、状态、原因、时间、关联活动数量；GET `/api/v1/trader-sync/summaries/{batch_id}/parts`。 |

| ListSubscriptionSummaries / GetSubscriptionSummary | 增加钱包/包含取消过滤、as_of、sending 等完整状态数量与非可加的关联计数定义；不加入 member 正文。 |

GetSummaryBatch 和 ListSummaryParts 均重新检查当前 grant 与 owner；batch/activity 不匹配与不存在均不可泄露。单活动可涉及多部分，批次所有部分都可读；不增加全局摘要列表。普通消息最近 attempt 已足以解释首期状态，完整 attempt 继续持久化供故障核验，不要求无界下载。

观察历史、取消订阅和分条使用有界分页。当前最多 10 个目标可一次取得；普通活动列表不可无限加载。ResourceTable 复用表格与 compactRender，省略 total/数字分页，外置 Previous/Next 游标控制器和已访问页栈；只有真实 next_cursor 才允许下一页，不虚构总页数。

### 活动列表稳定读取协议

本轮修订原后端 `(recorded_at,id)` 活动分页草案，改为数值 `id DESC`。复用计划中的 bigint activity ID，在持有 owner account gate 的活动插入事务内，通过持久 PostgreSQL sequence 分配，限定正向递增、CACHE 1、NO CYCLE，不允许预取 ID、回填旧 ID 或运行中回拨 sequence。读取也在同 owner gate 下取得已提交 `max(id)`（无记录为 0），不使用 sequence.last_value。它在同 owner 内提供形成顺序，不宣称所有 owner 的全局提交顺序；允许回滚造成空号。无需新增第二个顺序字段。

这是本轮技术设计修订，既有源码没有提供该保证。数据库 wall-clock 即使在 gate 内取值也可能回退，不能单独证明后续 recorded_at 更晚；recorded_at 仍保存真实时间用于时效与诊断，不人为修改它制造单调。PostgreSQL 明确说明 CACHE 大于 1 的跨会话预分配可能乱序，因此固定 CACHE 1 并结合现有 owner gate，而不是仅靠自增字段猜测提交顺序。[PostgreSQL sequence 文档](https://www.postgresql.org/docs/current/sql-createsequence.html)

首次 ListActivities 返回该 owner 已提交水位 `snapshot`、当前页 `refresh_cursor`、下一页 cursor、`has_newer=false` 和 `as_of`。snapshot 为签名的不透明标记，客户端不计算或改写其内部 ID；页游标包含版本、身份、过滤摘要、snapshot、页大小、页边界和签名，下一页保持同一 snapshot。初始空列表也保存水位。刷新当前页只能更新固定成员的显示资料/投递结果，不能扩充本页成员；同时判断 snapshot 后是否出现符合原过滤的新活动并返回 has_newer。后续刷新不自动推进 snapshot。

ListActivities 请求的 page.cursor 与 refresh_cursor 互斥；两者皆空读取最新第一页。刷新游标直接携带原始浏览水位，不要求客户端再拼接独立 latest_marker；原页为空时刷新仍保持空页、只提示新活动。更改 page_size 视为重新浏览，不能复用旧游标。as_of 只表达数据检查时刻，不承担一致性或新活动水位职责。

点击载入新活动不携带旧 cursor，取得新 snapshot。切换筛选重建快照与页栈；会员切换、非法签名或过滤不匹配不能复用游标。排序、同刻并发、时钟回退、事务回滚、初始空页、翻到历史页后发现新活动，以及活动过滤与摘要冻结的关系须有集成验证。

摘要成员在冻结后不可变，可按固定批次成员直接分页，无需参与主页新活动提示。以状态为条件的订阅管理列表允许操作后移出当前视图，界面明确反馈；它不适用活动固定成员契约。

## 12. 视觉、交互与验收
