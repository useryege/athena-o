## 业务目标与已确认方向

- 在 Token 领域提供独立的“钱包战绩”子板块，以用户输入的钱包地址为查询起点。
- 首版仅支持 Ethereum Mainnet（chain ID `1`），查询钱包的代币交易记录、逐代币表现、持仓与盈亏；胜率暂不接入。
- 统一以美元（USD）展示供应商提供的收益、成本和收支金额；可取得的原币种与数量用于核对明细。
- 数据来源确定为 **Nansen API**。交易解析、成本与盈亏结果采用供应商提供的数据和定义，ATHENA 负责接入、组织查询和展示结果。
- 展示 Nansen 返回的交易记录与资产信息，名称和说明依据实际字段；授权明细不作为本板块展示内容。不沿用旧方案自行定义买入、卖出、转入、转出的识别或结算规则。
- 初期预计 3–5 个用户，查询频率较低；本地开发也使用免费额度验证。每日查询量没有指定，调研报告中的频率和费用是估算假设。
- 沿用推荐的 **Free API 起步、额度不足时按需购买 credits** 的使用方向，无须为接入 API 订阅网页 Pro。用户已自行注册、提供新 Key 并充值 10 美元；最新 Key 的账户认证已通过，充值后复查余额为 10,000 credits，仍为 Free 套餐。余额为验证时快照；此前摘要实测与新 Key 账户验证分别见下文记录。

选择 Nansen 和直接展示供应商数据的方向已经确定。字段对应、格式化和运行管理由工程侧落实，已确认的业务不重复提问；不因接口缺少某个字段而增加自研计算补齐。

### 展示清楚的具体要求

- 标明数据来源为 Nansen，显示实际查询范围、每部分上次成功获取时间及缓存／刷新状态；获取时间不等于链上数据已更新至该时刻。
- 已实现与未实现盈亏分开，金额注明 USD，数量带代币标识；名称缺失时保留供应商符号和合约地址，不猜测完整名称。
- 逐币买入／卖出金额标明采用 Nansen 口径，可能包含普通转入／转出，不包装成只统计 DEX 的现金收支。交易明细展示上游已有资产与类型信息，不额外推导买卖分类。
- 保留供应商的金额、数量和精度语义；格式化不能把未知值或微量持仓写成确定的零，也不能给已有负号的转出数量重复加负号。具体小数位、缩写及时间展示格式在设计中确定。
- 展示当前结果的覆盖范围、分页状态及对应筛选条件；已加载条数不代表钱包全部历史。字段含义尚不明确时保留不确定性，不能将单位成本标成总成本，或将持仓擅自解释为只属于所选窗口内的买入。

以上是清楚呈现数据的工程要求，不增加分析指标、原始 JSON 页面或费用明细。下方映射保留已核对的字段事实，供开发直接使用，不再逐项要求用户确认。

### 钱包总览字段映射与说明

用户已确认钱包总览的展示安排。本节依据仓库内保存的摘要响应细化数据来源及展示含义，尚未确定页面布局、内部 API 数据结构或最终数字与时间格式。总览使用 `POST /api/v1/profiler/address/pnl-summary` 的结果及与之绑定的查询上下文；响应字段不带 `data` 前缀，样本文件的 `response` 只是研究记录包装层。

| 展示名称 | 数据来源 | 单位与含义 | 缺失或状态处理 |
| --- | --- | --- | --- |
| 钱包地址 | 对应结果的请求 `address` | 本次查询的 Ethereum 地址，摘要响应本身不回传该字段 | 从结果绑定的查询上下文读取；不能用输入框里尚未查询的新地址标注旧结果。 |
| 网络 | 对应结果的请求 `chain=ethereum` | 固定显示 Ethereum Mainnet，帮助识别当前查询范围 | 首版固定主网，不从 Top 5 代币或地址标签推断链。 |
| 查询范围 | 用户选择的 7／30／90 天及实际请求 `date.from`、`date.to` | 显示所选时间选项及该结果对应的实际起止时间 | 缓存或失败回显沿用原结果范围，不能随当前时间滚动改写；时间展示须明确时区。 |
| 已实现盈亏（USD） | 响应根字段 `realized_pnl_usd` | 直接展示 Nansen 对当前钱包及所选范围返回的已实现盈亏，保留正负值 | 缺失或 `null` 显示“暂无数据”，有效零值正常显示；不累加已加载的逐币明细来替代。 |
| 交易过的代币数量 | 响应根字段 `traded_token_count` | 单位为“种”，表示 Nansen 在当前查询范围内统计的代币数量 | 缺失或 `null` 显示“暂无数据”，有效 `0` 显示 0 种；不从当前持币数、交易笔数、Top 5 或分页列表重新计数。 |
| 数据来源 | 本功能已确定的供应商 | 显示 Nansen | 不将该标识解释为 ATHENA 已独立核算全部收益。 |
| 上次获取时间 | ATHENA 成功取得并接受该份摘要时记录的时间 | 表示该份摘要成功获取的时刻；与链上数据覆盖时间分别理解 | 缓存命中或刷新失败不更新；没有成功结果时不生成虚假的成功时间。 |
| 数据状态 | 本地查询、缓存及刷新结果 | 按已有规则区分加载中、成功取得、缓存复用、刷新失败后保留旧结果及首次失败 | 仅影响当前摘要区域；失败原因和重试入口沿用已确认规则，不将失败转换为零收益。 |

总览说明文案应表达：“数据由 Nansen 提供，按其统计口径展示；普通转账可能参与统计。”不把已实现盈亏等同于银行账户实收现金、全部历史总收益，或承诺其已扣除／未扣除全部费用。该说明也不改变“金额直接采用供应商结果”的决定。

选择或搜索代币只影响逐币战绩和相关交易，总览仍对应同一钱包、同一时间范围的整体结果。摘要响应即使附带 `win_rate`、`realized_pnl_percent`、`traded_times` 或 `top5_tokens`，也不因此新增胜率、收益率、交易次数或 Top 5 卡片；总览的两个统计值为已实现盈亏和交易过的代币数量。

### 逐币表现字段映射与说明

本节细化首版已选择的逐币展示内容，依据为 `POST /api/v1/profiler/address/pnl` 的已保存样本。以下字段均位于上游响应的 `data[]` 每一项中；钱包、网络、查询范围、筛选与分页条件来自该结果绑定的请求上下文。具体列布局和数字格式仍在后续设计中确定。

| 展示名称 | 每项的供应商字段 | 单位与含义 | 缺失或边界处理 |
| --- | --- | --- | --- |
| 代币 | `token_symbol` | 供应商返回的代币符号，用于辨认资产 | 当前样本无完整名称字段；保留符号与地址，名称缺失不猜测。同名资产不能仅凭符号合并。 |
| 合约地址／资产标识 | `token_address`，结合请求网络 | Ethereum 下该资产的标识；ERC-20 使用其合约地址 | 不能从符号推测地址；原生 ETH 的供应商标识按下文单独说明。 |
| 买入金额（USD） | `bought_usd` | 所选时间范围内 Nansen 统计的买入美元金额，可能包含普通转入 | 缺失或 `null` 显示“暂无数据”；有效零值按零展示。不将其解释为期末全部持仓的总成本。 |
| 卖出金额（USD） | `sold_usd` | 所选时间范围内 Nansen 统计的卖出美元金额，可能包含普通转出 | 缺失或 `null` 显示“暂无数据”；有效零值按零展示。不将其解释为银行卡或交易所实际到账金额。 |
| 持仓数量 | `holding_amount` | Nansen 返回的持仓数量，附对应代币标识 | 缺失或 `null` 显示“暂无数据”；有效零值保留。非零微量余额不能直接写成确定的零。 |
| 持仓价值（USD） | `holding_usd` | 与该记录一起返回的供应商持仓美元估值 | 与数量独立处理空值，不在本地用数量乘报价补齐。不能称为可保证成交或提现的金额。 |
| 已实现盈亏（USD） | `pnl_usd_realised` | Nansen 返回的该币已实现盈亏，采用供应商统计口径 | 正值、负值与零值分别保留，缺失或 `null` 显示“暂无数据”。不以卖出金额减买入金额代替。 |
| 未实现盈亏（USD） | `pnl_usd_unrealised` | Nansen 返回的该币未实现盈亏，与已实现盈亏分开展示 | 不将其当成已兑现收益；缺失或 `null` 显示“暂无数据”，不从持仓或单位成本重新计算。 |

持仓数量与持仓价值共同呈现已有的“当前持仓”信息，但在时间语义完全明确前以“Nansen 返回的持仓”说明来源，不承诺实时余额或精确的区间末余额。所选日期限定查询，不能据此断言持仓仅由该窗口内的买入形成。各部分上次成功获取时间、来源及刷新状态沿用既定规则。

当前样本中的原生 ETH 使用 `0xeeeeeeeeeeeeeeeeeeeeeeeeeeeeeeeeeeeeeeee` 标识，展示时明确为“ETH（原生资产）”；该值不是 ERC-20 合约地址，不将其包装成合约链接。WETH 继续按自己的合约地址作为独立资产。此处识别供应商返回的资产，不恢复原基础币白名单或本地交易对筛选。

`cost_basis_usd`、`token_price`、收益率、买卖次数、最大持仓等附带字段不自动增加为本轮展示指标，也不从保留字段新增本地合计盈亏。保留原始精度用于核对，列表中的具体小数位、数量缩写及微量值表达随后统一设计。

## 查询失败与部分结果（已确认）

用户已确认按各部分的实际取得情况展示结果：

| 情况 | 展示方式 |
| --- | --- |
| 首次查询失败，没有对应旧结果 | 显示失败原因并提供重试入口，不展示伪造的零值或空交易结论。 |

## 旧结果保留时间（已确认）

用户已确认每份成功查询结果从成功获取时起最多保留 **24 小时**：

## 接入后的职责

Nansen 提供交易与战绩数据。ATHENA 将这些数据接入现有系统，承担钱包查询入口、参数校验、结果展示及必要的访问控制和调用管理。

以下为接入设计需要覆盖的事项，具体机制尚待确定：

- 服务端通过环境变量加载 API Key 并发起上游调用，不把供应商密钥放入浏览器；实际接入归属、内部接口和环境注入位置在技术设计中确定。
- 将供应商返回的统计与交易明细组织成钱包总览、逐币表现和交易明细；展示供应商来源、查询范围与更新时间。
- 落实已确认的时间窗口、分页、刷新及结果留存规则，在接入设计中明确重复请求合并和缓存机制，避免每次界面更新都重复消耗上游额度。
- 区分无交易、字段缺失、部分结果、数据尚未准备好、余额不足、限流与调用失败；不能用零收益或空列表代替未知或失败。
- 按已确认规则记录调用用量、额度消耗与失败信息，支持本地样本调试和必要的真实接口验证；首版不设平台或每用户每日查询次数上限，刷新沿用既定规则，并提供低于 1,000 credits 的页面提醒。

本段尚未确定数据库、缓存存储、任务队列或服务边界；已确认的缓存有效期和结果保留期限继续作为设计依据。新服务或服务边界改造时遵循[服务开发规范](../../developer-guide/service-development-standards.md)，不为单纯 API 适配提前创建额外服务。
