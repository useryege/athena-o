## 筛选、排序与分页证据

### 代币搜索与交易分页

- A 钱包 CATE 合约 `0x712f3378cd1a0476b53f0e29b1a9586e00d78683`：逐币过滤返回 1 项，交易过滤返回 1 项。该笔交易不在原交易第一页，证明本次搜索覆盖了第一页之外的结果。
- A 钱包 USDT 合约过滤返回 1 笔，结果资产地址匹配；该币的交易存在不保证逐币 PnL 一定有对应行，两个接口的覆盖范围应分别说明。
- A 钱包交易第二页返回 20 条，与首轮第一页合并为 40 条，无重复哈希且跨页时间倒序；第二页仍标记有下一页。没有把这 40 条称为钱包全部历史，也不把它当作摘要统计的全部依据。
- B 钱包逐币 `show_realized=true` 的完整样本有 3 项。将页大小从 20 改为 2 后，第一页为 2 项且非末页，第二页为 1 项且末页，拼接后与完整样本一致。这是分页机制的小样本验证，不是超过 20 个代币的大集合验收。

请求和完整结果见第二轮目录的 `pnl-cate-filter.json`、`transactions-cate-filter.json`、`transactions-usdt-filter.json`、`transactions-page2.json`、`active-pnl-true-page1-size2.json`、`active-pnl-true-page2-size2.json`。官方支持的参数见[钱包交易接口](https://docs.nansen.ai/api/profiler/address-transactions)。

### `show_realized` 与排序异常

每次均显式传入 `order_by=[{"field":"pnl_usd_realised","direction":"DESC"}]`，避免默认排序不同干扰比较：

| 钱包／参数 | 返回代币与已实现盈亏，按响应顺序 |
| --- | --- |
| A，`true` | 空列表 |
| A，`false` | 10 个代币，已实现盈亏均为 0 |
| B，`true`、DESC | PEPE：53,399.36；WETH：8,216.04；SHIB：2,815.15 USD |
| B，`true`、ASC | SHIB → WETH → PEPE，符合反向排序 |
| B，`false`、DESC | SHIB：2,815.15 → PEPE：53,399.36 USD，**不符合请求的降序** |
| B，`false`、ASC | SHIB → PEPE，与上述 DESC 的 `data` 完全相同 |

B 的 WETH 持仓为 0，在 `true` 中存在、在 `false` 中缺失，两组均报告末页。PEPE 已有卖出且仍持仓，在两组中都存在；SHIB 买入数量与卖出数量相等，但残留约 `0.0000018158` 枚，亦在两组中存在。不能把微量余额自行改成严格零，或据此推断供应商采用的仓位阈值。相交的 PEPE／SHIB 行字段相同。

因此，不能将 `true` 解释成“所有代币”，也不能将 `false` 解释成“不包含已实现盈亏字段”。当前两次 `false` 请求并未证明全局固定采用何种排序规则，只证明该样本的显式已实现收益降序未生效。官方参数描述及默认排序说明不足以解释这一差异。[官方 PnL 接口](https://docs.nansen.ai/api/profiler/address-pnl-and-trade-performance)

首版“全部代币按已实现收益排序后分页”的需求保持不变。不能用只取已实现结果、只排序本地第一页或静默截断结果来声称满足需求。2026-09-14 的[后端草案](../../superpowers/specs/2026-09-14-token-wallet-analytics-backend-design.md)采用收齐 true／false 两组返回、保留整行来源并排序分页的方案，不引入本地 PnL 计算；这解决的是结果组织方式，供应商跨页非原子、大集合耗时等限制仍需实现阶段验证，不能记为已经完成全量验收。

## 胜率、次数与成本

### 胜率存在文档与样本差异（保留证据，接入暂缓）

本节记录调整方向前的核验事实，不构成当前首版的指标要求。只有以后重新讨论接入胜率时，才需要继续澄清这些定义；当前摘要仍可用于已实现盈亏与交易过的代币数量。

Nansen 的[官方产品方法文章](https://nansen.ai/post/understanding-nansens-pnl-tracking-a-guide-for-crypto-traders)发表于 2024-11-14，其中以“10 次卖出、7 次盈利，胜率 70%”解释网页产品。它并未直接定义当前 API 原始字段的缩放和分母。

| 样本 | `win_rate` 原值 | `traded_times` | 逐币买入／卖出次数之和 | 总盈亏为正的代币数／样本代币数 |
| --- | --- | --- | --- | --- |
| A，30 天 | 0.6 | 27 | 27／0 | 6／10 |
| B，30 天 | 0.6666666666666666 | 79 | 63／16 | 2／3 |
| B，90 天 | 0.3333333333333333 | 136 | 105／31 | 1／3 |

三个样本的 `traded_times` 均等于买入与卖出次数合计，不能标为“卖出次数”。`win_rate` 恰好与逐币“已实现加未实现盈亏为正”的比例一致；**这是有限样本相关性，不是已确认的公式**。尤其 A 样本逐币卖出次数为 0，摘要仍返回 0.6，不支持直接套用网页产品文章的说明。

官方 CLI 的[测试样例](https://github.com/nansen-ai/nansen-cli/blob/793e9d428009f635ee10789bccc8d6c2100b2dbb/src/__tests__/api.test.js#L154-L157)包含 `win_rate: 0.65`，但对应测试只验证透传；[数值格式化](https://github.com/nansen-ai/nansen-cli/blob/793e9d428009f635ee10789bccc8d6c2100b2dbb/src/cli.js#L257-L271)没有专门的百分比换算。这只能补充比例形式的线索，不能替代接口定义。开发时不自行计算胜率，不自行除以 `traded_times`，不将其解释为纯 DEX 盈利卖出概率。

### 成本与转账

上述官方产品方法文章将 Cost Basis 解释为每枚代币的加权平均成本，并说明普通转账会影响成本与已实现收益。这是供应商产品说明；ATHENA 继续采用供应商结果，不恢复本地成本账本。[官方成本与转账说明](https://nansen.ai/post/understanding-nansens-pnl-tracking-a-guide-for-crypto-traders)

A 钱包的 CATE 样本是普通转入 30,000,000 枚，交易 `method=transfer(address,uint256)`；逐币结果却记 `nof_buys=1`、`bought_amount=30000000`、`bought_usd≈540.18`。其 `cost_basis_usd≈0.000018006`，数量乘该值约等于买入美元额，支持“单位成本”解释。A 的 10 项和 B 的 30／90 天各 3 项还满足 `holding_usd - holding_amount × cost_basis_usd ≈ pnl_usd_unrealised`。这些算式仅用于离线核对字段单位，不能据此建立本地结算逻辑或证明全部历史成本算法。

还需供应商明确 API 字段与产品成本方法的对应关系、转入转出的计价及费用处理。现有结果不提供可独立核对的 Gas 明细，不能声称已经排除或包含全部费用。`bought_usd` 是所选范围的买入金额，也不能与期末总持仓成本混用。

## 交易方向、时间与空值

第二轮补充调用一次官方 `POST /api/v1/profiler/dex-trades`，取得 20 条明确的买入／卖出资产记录；与一般交易第一页有 19 个相同哈希。一般交易接口把这 19 条全部标为 `source_type=transfer`。例如 `0xc3aa921eb0a0cf365fec51b5f5b795097deb62e35fb9e23862cebcd466b246b4`：DEX 接口明确为卖出 DAI、买入 PEPE，而一般交易接口 `method=0x4a7cf362`。所以 `transfer` 并不等价于“不是 DEX 买卖”。[官方钱包 DEX 接口](https://docs.nansen.ai/api/profiler/address-dex-trades)

DEX 专用接口探针仅作研究证据；本版直接展示选用接口的返回，不为补充分类新增 DEX 页面、必用接口或多跳关联任务。一般交易样本中 `tokens_sent.token_amount` 为负数，DEX 的 sold amount 为正数，映射时须保持所用字段的数量与方向含义。

一般交易返回无时区后缀时间；19 笔同哈希 DEX 记录的时间均相同但带 `Z`。另对 A 钱包 CATE 交易，通过公共 RPC 获取交易所在区块，其 Unix 时间对应 `2026-08-22T03:08:23+00:00`，与 Nansen 的 `2026-08-22T03:08:23` 一致。[独立区块时间证据](research-data/2026-09-13-wallet-analytics/nansen-semantics-132128/ethereum-timestamp-crosscheck.json)

这些样本支持将无后缀时间解释为 UTC，但未得到供应商全局契约。请求日期为闭区间 `[from,to]`，技术设计要明确时区归一化；不能直接将无后缀时间当成本机时区。[官方日期约定](https://docs.nansen.ai/guides/data-methodology-and-technical-reference)

7／30／90 天请求均得到成功结果，窗口变化确实改变摘要和明细。B 的 7 天摘要为零交易、零盈亏、原始胜率 0，逐币为空；90 天已实现盈亏为负，与 30 天为正不同。A 的 7 天交易为 9 条，90 天第一页为 20 条，按 UTC 解读均在请求范围内。仍需区分空结果、供应商真实零值与字段未知。首轮交易中 `volume_usd`、资产价格存在空值，不能填零；逐币只提供 symbol，完整名称的来源也尚未落实。

摘要可能存在约一小时供应商缓存，本地 10 分钟缓存不能保证每次取得最新链上结果。即使查询结束时间相同，当该日期是今天时，上游报价仍可能变化；不能仅凭浮动未实现收益差额判定两次筛选不一致。[官方 PnL 更新说明](https://docs.nansen.ai/api/profiler/address-pnl-and-trade-performance)

## 历史研究问题及当前适用范围

下列问题与完整请求、响应及 `x-request-id` 已保存，尚未向外部发送消息。它们保留此前研究背景：第 1、3 项及第 4 项中的分类、多跳问题不再安排本版专项调查；第 2 项的列表范围和排序、第 4 项的时间处理，只按实际展示需要在接入中解决，不要求先获得全部供应商答复。

1. **暂缓，留待以后接入胜率时参考：** `win_rate` 是否为 0–1 比例？分母是卖出次数、发生交易的代币数还是其他范围？采用已实现还是总盈亏？为何 A 的卖出次数合计为 0 时仍为 0.6，而三个样本都匹配正总盈亏代币占比？相关的 `traded_times` 是否实际统计买入加卖出？该次数字段也不自动增加为首版指标。
2. `show_realized` 的准确行集条件是什么？如何完整覆盖无卖出、部分卖出及已清仓代币？为何 B 的 `false` + 已实现收益 DESC 返回 SHIB→PEPE，与 ASC 完全相同？是否有支持全部代币全局排序再分页的请求方式？
3. `cost_basis_usd` 是否是每枚代币的美元成本？它是否使用官方产品文章的加权平均方式，如何处理转账、历史窗口和费用？持仓字段对应 `date.to` 还是调用时刻？
4. transactions 的无后缀 `block_timestamp` 是否统一为 UTC？`source_type` 的完整语义是什么？一个哈希下多个 DEX 成交段应如何关联展示？

当前直接落实已选数据的展示名称、字段来源、单位、范围与空值处理，不再把字段映射提交逐项业务确认。排序和完整范围差异仍影响已确认的列表目标，由接入工作处理；未选用指标、供应商内部公式及旧分类规则不作为展示前置，必要的补充核验仅针对实际展示问题。

## 复核方式

第二轮目录保存 `batch1.json` 至 `batch5.json` 和每次完整响应，`analysis.json` 汇总实际消耗、请求编号和核对结果。

从仓库根目录运行以下命令只复核已存证据，不访问网络、不消耗额度：

```bash
python3 docs/requirements/token/research-data/2026-09-13-wallet-analytics/nansen-semantics-132128/analyze.py
```

`probe.py` 是本次研究的显式请求脚本，运行会使用开发 Key 和额度；不会自动重试，拒绝覆盖已有响应。因此不把它放入日常测试或默认执行流程。本轮只维护需求与研究证据，尚未完成后端／前端设计、运行配置或系统接入。
