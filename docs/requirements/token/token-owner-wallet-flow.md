# Token owner 钱包获取与研究流程

> 需求状态：讨论中
>
> 细分状态：目标设计草案，尚未实现。本图记录已确认的 AI owner 读取方式分析、Go 链上读取与关联钱包研究范围；具体执行细节仍待设计。

首版仅研究 Ethereum Mainnet，相关 Etherscan 请求使用免费 Key；后续扩展其他链时统一替换为付费 Key。owner 由 Go 执行只读链上调用取得。

## 入口与目的

对已识别为 Token 的项目，由 AI 分析合约源码是否提供可用的 owner 读取方式；有可用方式时，由 Go 程序按该方式读取当前合约的链上 owner。将取得的 owner 作为 L1 直接关联钱包，继续采集其普通交易和已追踪代币余额，分析历史部署、代币交互及资金来源，并逐层研究由此发现的 L2–L5 地址。owner、部署者、初始接收钱包和税费接收钱包是不同角色；地址相同时也应保留角色关系。各层研究的完整范围见 [多层关联钱包研究流程](token-wallet-research-flow.md)，展示方式见 [钱包资金来源关系图](token-wallet-funding-graph.md)。

同一份源码的 AI owner 分析结论与读取方式只生成一份，通过运行时字节码 `code_hash` 匹配源码并复用。AI 负责确定如何读取，Go 程序负责执行只读链上调用；各部署实例的 owner 地址分别读取和保存。未取得源码、AI 未识别可用方式或实际调用未取得地址时，保存对应结果及原因，仅跳过无法定位地址的 owner 钱包采集，继续其他资料采集与展示。未取得地址不代表已经确认合约没有 owner。

当前 owner 与关联钱包板块只执行资料采集、事实解析和展示。取得的多重角色、历史项目、资金来源、余额及未取得资料的结果都不触发项目筛选或排除；本流程不输出项目通过／不通过结论。源码 AI 同样只输出事实报告，见 [AI 静态质检流程](token-contract-review-flow.md)。

owner 的读取入口统一由 AI 对源码的分析结果决定，例如 `getowner()`、`owner()` 或源码中实际提供的其他读取方式，不预设函数名单，不保留固定函数探测作为兜底。没有共享分析结果时，源码是进行 AI 分析的前置资料；已有结果则直接复用。整体资料范围见 [研究资料整理流程](token-research-materials-flow.md)。

    lookup --> cached{"是否已有分析结果？"}
    cached -->|"有"| method{"分析是否给出可用读取方式？"}
    cached -->|"无"| source{"是否已取得对应源码？"}
    source -->|"有"| analyze["AI 分析源码能否读取 owner<br/>可读取时给出函数签名、必要参数及返回类型<br/>或记录未识别可用读取方式及依据"]
    analyze -->|"分析完成"| saveMethod["保存同源码共享的分析结论与读取方式<br/>关联源码及 code_hash"]
    saveMethod --> method
    method -->|"有可用方式"| read["Go 程序按 AI 确定的方式执行只读调用<br/>读取当前链、当前合约的 owner<br/>使用本次采集时最新区块"]
    read --> result{"是否取得 owner 地址？"}
    result -->|"是"| related["保存 owner 读取结果与来源区块<br/>加入 L1；已有钱包追加 owner 标签<br/>保留部署者、初始接收钱包、税费接收钱包等标签"]
    related --> history["按链和地址去重，通过 Etherscan 采集普通交易<br/>区块 0 至部署区块减 1<br/>从新到旧取第 1 页，最多 300 笔"]
    related --> assets["在同一最新观察区块读取余额并估值<br/>原生 ETH、WETH、USDT、USDC、DAI、WBTC<br/>逐项保存原始余额与 USDT value"]
    history --> behavior["补充同批交易的回执与日志<br/>分析成功直接部署合约、交互代币及资金来源"]
    behavior --> indirect["按项目门槛快照逐层查找直接 ETH 入账来源：L2 至 L5<br/>仅单笔成功且达到门槛的顶层入账形成资金边<br/>交易所 / 跨链地址完成本层分析后停止向上追溯<br/>去重复用、保留关系；L5 分析后不扩展 L6"]
    behavior --> materials["保存钱包资料、历史分析及资金来源图<br/>关联项目、钱包与交易证据"]
    indirect --> materials
    assets --> materials
    result -->|"否"| unavailable["保存实际结果与未取得 owner 原因<br/>仅跳过无法定位地址的 owner 钱包采集"]
    source -->|"无源码"| unavailable
    method -->|"未识别可用方式"| unavailable
    analyze -->|"调用或解析等技术失败"| failed["记录分析失败及原因<br/>不保存为未识别可用方式的结论"]

    materials --> collected["将已有 owner 资料或未取得结果<br/>纳入项目研究资料"]
    unavailable --> collected
    collected --> display["展示 owner 结果、多重标签及 L1 至 L5 资料<br/>折叠只影响显示，不触发后台采集<br/>本阶段不筛选或排除项目"]

图中实线表示当前确认的唯一 owner 获取路线及取得地址后的资料依赖。缓存命中包括“可读取”和“未识别可用读取方式”两类已完成的源码分析结论，均不按项目重复调用 AI。AI 调用失败或返回内容无法作为有效分析结果解析时，只记录技术失败，不伪造“不可读取”结论，也不把该失败当作可复用的完成结果。最终 owner 地址来自 Go 程序对当前合约的实际链上读取，AI 不生成或猜测本次 owner 地址。

## 已确认的数据范围

| 内容 | 采集范围与时点 |
| --- | --- |
| AI owner 分析 | 分析源码是否提供可用 owner 读取方式，保存结论与源码依据；可读取时保存足够 Go 程序执行的只读调用描述，包括函数签名、必要参数及返回类型。函数名称由源码确定。 |
| 共享分析结果 | 与对应源码及运行时 `code_hash` 关联，复用已完成的“可读取”或“未识别可用方式”结论；技术失败单独记录，不作为上述分析结论。 |
| owner 地址 | Go 程序按 AI 给出的读取方式调用当前链、当前合约，使用本次采集时最新区块，逐合约保存实际调用方式、输入、返回结果及来源区块与时间。 |
| 关联钱包关系 | 取得 owner 后将其与部署者、最多 5 个初始接收钱包及已取得税费接收钱包一同纳入 L1。若地址已存在，给该钱包追加当前项目的 owner 标签，保留部署者、初始接收钱包、税费接收钱包等其他角色，不创建重复节点；L1–L5 历史交易按链和钱包地址去重查询，同一窗口的资料与分析复用。 |
| 普通交易 | 原样保留部署前最近最多 300 笔的规则：对每个去重钱包，通过 Etherscan `account/txlist` 查询区块 `0..部署区块-1`，按 `desc` 排序，仅取第 `1` 页、每页上限 `300`；不足 300 笔保留实际数量。保留查询范围和采集结果，不包含部署区块内及之后的交易，不以采集时最新区块为截止。 |
| 历史行为与资金来源 | 补充同批交易的回执与日志，分析成功直接部署过的合约、识别其中的 Token 并匹配已有项目报告，识别代币交互并区分主动调用、授权、转出和被动收款。项目开始时保存原生币资金门槛快照；ETH 默认 `0.01 ETH`。仅当前层样本中单笔成功、直接转入且金额大于等于该快照的顶层 ETH 交易形成资金边和上游节点，多笔小额不累计。首版不纳入代币入账和内部转账来源。 |
| L2–L5 历史研究 | 各层资金来源地址按同一项目部署区块减 1 截止，获取最近最多 300 笔普通交易及同批回执日志，使用同样的部署与代币交互分析。L5 对应从 L1 向上查找四轮，仍开展历史分析，不向 L6 扩展。所有层按链和地址共同去重；重复来源只分析一次并保留全部关系，已属任一层则复用分析，循环转账保留连线且不重复展开地址。任一节点命中管理员维护的交易所／跨链地址库时仍完成本层历史与行为分析，但不再发现它的上游来源。 |
| 资金来源图 | 按距任一 L1 的最短路径分层，底层保存有向图，保留共同来源、循环边和全部角色。展示后台自动采集的 L1–L5 五层结果及各层实际状态；展开、折叠只影响显示，不触发采集或删除资料。连线按来源、接收地址及资产聚合，点击查看去重后的交易依据。 |
| L1 资产与估值 | 仅 L1 钱包固定读取原生 ETH、WETH、USDT、USDC、DAI、WBTC。余额、固定 DEX 现货路径所需池状态和价格使用同一最新观察区块；逐项保存原始余额、独立 USDT value、路径、池、区块、时间和失败原因，并计算已知 USDT 小计。非零资产无法估值时保留其他结果，把总值标记为不完整并列出缺失资产。L2–L5 不采集余额。 |
| 未取得 owner | 区分未取得源码、已完成分析但未识别可用方式、AI 技术失败和链上读取未取得地址，保存实际结果及原因供展示与排查；仅跳过无法定位地址的 owner 钱包采集，不因此阻塞其他资料采集或否决项目，也不等同于确认没有 owner。 |

owner 读取与 L1 资产采集分别选择各自执行时的最新区块，不要求两类资料共用同一区块；但一次 L1 资产快照中的六项余额、池状态和价格必须统一使用该次观察区块。owner 为合约地址时也纳入上述采集，不预先限定为无代码地址。资产估值采用按链、按资产配置的固定可信 DEX 现货路径，支持直接或最多两跳；ETH 复用 WETH 估值路径，USDT 按自身精度直接计值，其他资产不得固定按 1:1 USDT 处理。完整规则见 [多层关联钱包研究流程](token-wallet-research-flow.md#l1-资产余额与-usdt-估值)。

例如项目部署在第 `30000` 区块，即使 owner 在之后才取得，owner 及 L2–L5 各层资金来源地址的历史交易仍查询 `0..29999` 区块内最近最多 300 笔普通交易。该数量上限按每个去重钱包计算，补充回执和日志不扩大交易范围，也不代表完整钱包或代币交互历史。跨项目复用分析时需匹配链、地址、截止区块与采样规则。

资金来源图保存样本内的历史关系。追溯某笔入账的连续来源时，需要核对各跳交易先后顺序，不能以较晚的上游入账解释较早的转出；核对过程不改变部署前最近 300 笔的查询范围，也不直接证明各跳是同一笔资金。后台自动采集与分析 L1–L5，展示五层已经取得的结果及实际未取得原因；展开或折叠不决定是否采集。没有来源的分支按实际结果结束，不补造节点。

图中的交易与余额分支只表示取得钱包地址后的数据依赖，后台独立执行本流程及五层钱包研究，具体子任务并发或串行调度另行设计。该块识别结果、项目资料与研究任务可靠保存后即可推进区块，不等待上述采集完成，也不建立全部资料到齐的研究完成条件。owner 读取不是部署者、初始接收钱包、税费接收钱包及其他研究资料采集的前置条件；即使未取得 owner，其他已知关联钱包仍按既定范围采集。

owner 只可被管理员配置为具有续期资格的目标 Token `Transfer` 所触发的刷新组；`Approval` 和部署者／当前 owner 主动交易不得触发 owner 刷新。刷新使用执行时最新区块，只保留最近成功的当前 owner，失败另存最近时间与原因。发现新当前 owner 时，新地址替换 owner 角色的当前值并自动完成其固定 `0..B-1` 历史、六项资产余额与估值及 L2–L5 研究；旧地址失去当前 owner 标签，但若仍有部署者、初始接收方或税费接收方等角色则继续保留。

当前 owner 成功读取后，从该次读取的观察区块开始把它加入项目主动交易监控；再次读取到不同地址后，停止把旧 owner 的后续交易作为 owner 活动，并从新观察区块开始监控新 owner。部署者从部署交易之后开始监控且始终保留。只有监控地址作为 `from` 发出的成功顶层交易有效，包括零 ETH 合约调用；收到的交易、失败交易和内部调用无效。地址与部署者重合时，同一项目中的同一交易只处理一次并保留全部角色。期限资格、源码补查和覆盖规则见 [项目事件监控流程](token-project-activity-flow.md)。

项目因首次已识别 Swap、不活跃超时或管理员手动操作停止时，owner 与钱包任务按统一规则处理：未开始任务取消，已开始任务按原有限重试规则收尾，停止后不启动新下游任务；在途任务结束后冻结项目专属 owner 与钱包事实，不允许手动刷新或恢复。共享 owner 分析与读取方案仍始终展示最新有效版本，但不触发已停止项目重新读取。详见 [项目事实研究流程](token-research-flow.md)。

## 分析复用与执行边界

按当前合约的 `code_hash` 先查询数据库，匹配对应源码及其已完成的 AI owner 分析结果。命中“可读取”结论则将读取方式交给 Go 程序；命中“未识别可用方式”结论则展示该结论及依据，继续其他资料采集。仅在没有已完成分析结果且已取得对应源码时，才由 AI 分析并保存结论。源码获取规则见 [合约源码获取流程](token-contract-source-flow.md)。

AI 输出的是源码支持的读取说明，不能只返回一个不足以执行的模糊方法名。以无参 getter 为例，读取说明可以明确为 `getowner()`，返回类型为 `address`；如读取需要参数，还应给出参数类型及可确定的取值或取值依据。Go 程序据此构造调用、只读查询链数据并解码结果。需要但无法确定的参数或无法执行的描述不算已提供可用读取方式；不自动补猜参数或执行 AI 生成的任意程序。

源码审阅中的“是否使用代理”和“是否存在外部未知依赖”当前只作识别与展示，不触发 owner 流程额外解析代理实现地址或获取、分析外部依赖源码。若现有源码不足以确定可执行的 owner 读取方式，按未识别可用方式保存结果，继续其他已知钱包资料采集；已经明确的 Go owner 只读调用仍按本流程执行。

源码的 [AI 静态事实报告](token-contract-review-flow.md) 采用相同共享原则：通过 `code_hash` 匹配到对应源码后，已有完成报告直接复用；没有报告且有非空源码时生成并保存，管理员也可手动重新检测。报告事实与依据、owner 分析结论及读取方式都属于源码层共享结果，所有关联项目始终展示最新有效版本。AI 不评级，owner 读取方式用于取得当前合约实际地址；两项分析无需合并为一次 AI 调用。

复用的是分析结论与读取方式，各部署实例的 owner 地址仍分别读取。每次都对当前链、当前合约按采集时最新区块读取 owner，不将其他合约的地址或历史 owner 快照作为本次结果。缓存命中不保证本次链上读取成功；未取得地址时保留实际结果与原因，继续其他资料采集和展示。

[税费接收钱包获取](token-fee-recipient-wallet-flow.md)同样复用源码分析，但还允许直接提取源码中确实固定的地址，并支持多个接收钱包。其分析结果单独保存，与 owner 分析及静态质检互不作为完成前提；税费接收地址与 owner 相同时只追加角色标签，复用该钱包的资料。

[税率读取](token-tax-rate-flow.md)也采用 AI 确定读函数、Go 读取当前合约的方式，另行保存税率原始值与换算依据。税率分析与 owner 分析分别复用，读取结果互不作为前置条件，也不进入静态质检的链上核实。

## 待设计事项

- AI 读取说明的具体数据结构、支持的调用描述格式、多个可用入口的选择与结果冲突处理、分析更新及版本管理仍待设计；当前不再预设 `owner()` 与 `getowner()` 的固定调用顺序或兜底。
- 零地址等特殊返回值的解释、具体调用错误分类，以及合约 owner 的额外分析仍待设计；本轮不自行规定排除条件。不同角色地址相同时，历史交易按地址去重查询并保留各角色关系。
- AI 分析、owner 链上读取及后续钱包采集的重试次数、间隔和通知等机制仍待设计，不沿用源码请求重试次数作为这些采集的规则。未取得 owner 后记录原因并继续其他资料采集的基本处理已经确定。
- owner 刷新的任务、版本与数据结构仍待技术设计；新地址替换当前 owner 角色、自动成为 L1 并完成初始研究、切换主动交易监控目标，以及旧地址保留其他角色的业务语义已经确定。

本文件只补充 owner 关联钱包流程。研究阶段不开展通用底池深度、LP 或流动性风险研究；除首次已识别 Swap 所需池身份与 token 映射外，只允许为 L1 六项资产 USDT 估值读取管理员固定路径中的可信池现货状态。Ave 仅采集持币地址总数与前 100 名分布，不采集其市场、池或风险标签；`simulation_result` 第一版完全移除。
