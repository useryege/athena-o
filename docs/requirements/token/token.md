## 业务目标

Token 的核心目的是发现区块链上的新代币项目，从合约部署后开始捕捉和研究项目信息，判断项目是否值得关注、是否具备买入价值。

系统争取在项目尚未开启交易时完成研究和筛选，持续关注筛选出的项目，并在其开启交易且满足买入条件时及时买入。尽早参与是寻找盈利机会的业务动机，不构成盈利保证。

## 已明确的实施顺序与前端范围

Token 先完成后端业务逻辑，再重新设计和实现前端 UI。现阶段删除原有 Token 项目、源码、黑名单、节点状态、链处理及采集任务页面，以及它们的路由、前端服务、专用组件、样式和资源；文中研究资料的展示要求作为后续前端设计依据，不要求保留原有页面。

成员端保留 `Token & Risk` 分组。`Token` 父菜单保留原名称、图标及 Token 读取权限可见性，显示为禁用项，无子菜单、跳转路径或占位页面；独立的 `Wallets` 保留。桌面侧栏与移动端抽屉采用相同结构，访问 `/token` 或 `/token/*` 使用现有通用 404 页面。成员端默认首页继续为 Active 账户的个人资料页或 Pending 账户的权限页，不再将 Token 作为获得权限后的自动跳转目标。

管理员权限编辑器及账户中心不展示或编辑 Token 权限项，相应展示统计也排除 Token。完整九项权限模型、后端鉴权及已有 Token 授权继续保留；编辑其他权限时必须保留原有 Token 值，不得遗漏或重置。仅持有 Token 授权的账户仍按原规则判定为 Active。

本阶段不删除 Token HTTP/gRPC 接口、采集服务、数据库或 API 文档。管理员通用服务状态中的 Token API 健康信息、Etherscan 管理、独立钱包、Worm Trading 和账户 API Key 功能保留。后续业务逻辑开发遵循“确认需求 → 确认后端技术设计 → 另行派发实现 → 设计一致性审查”的顺序。

## 项目的典型阶段

| 阶段 | 项目侧的活动 | 系统关注的业务问题 |
| --- | --- | --- |
| 合约部署 | 发起者发布合约和代币 | 如何尽早发现项目并开始收集信息？ |
| 交易开放前的准备 | 发起者准备交易条件，包括添加流动性等操作 | 项目是否值得关注，能否在开放交易前完成筛选？ |
| 开放交易 | 项目开始允许交易 | 关注项目是否已经开放交易，当前是否满足买入条件？ |
| 普通交易者参与 | 链上交易者开始买卖项目代币 | 如何在符合条件的前提下及时参与？ |

这些阶段用于说明业务目标，不是已确定的程序状态枚举，也不假设每个项目都严格按此顺序经历独立的阶段。添加流动性与开放交易分别描述：添加底池本身不作为已经开放交易的充分判据；首次 Swap 截止规则已经确定，具体事件适配及第二板块买入条件仍待设计。项目第一次实际 Swap 是研究截止事件；出现时结束该项目的研究，不以所有资料齐备为条件。

## 已明确的两个业务板块

| 板块 | 核心问题 | 输入 | 主要工作 | 输出 |
| --- | --- | --- | --- | --- |
| 项目发现与研究 | 这个新项目是否符合研究筛选规则、值得关注？ | 开发阶段范围内的顶层部署候选及可获得的项目资料 | 从部署后开始发现并识别 Token，采集资料、开展研究，按规则筛选项目并保存结论与原因 | 符合规则的关注项目及研究结论与依据；被过滤项目的未通过规则、原因和依据记录，供后续人工排查 |
| 交易监控与执行 | 这个关注项目现在是否满足买入条件？ | 第一板块交接的关注项目及研究信息 | 持续检测是否开放交易，在开放交易且满足条件后及时买入 | 买入执行结果，具体结果分类与处理规则待细化 |

“值得关注”是第一板块按研究筛选规则得出的结论；不符合规则的项目被过滤，并保留具体原因和依据供后续人工排查。“满足买入条件”是第二板块执行买入前的条件判断，进入关注范围不直接等于执行买入。

第一板块在项目首次实际 Swap 前收集研究资料，首次 Swap 出现即结束研究。第一板块使用按链共享事件监控，通过实时订阅和历史补查接收 Approval/Transfer 与跨协议 Swap；前者只触发无源码项目更新，后者用于识别研究截止。不采集池深、流动性估值或 LP 风险；池与代币的身份映射只用于正确匹配 Swap。第二板块的买入条件仍独立设计，研究结束本身不构成买入授权。

图示见 [Token 整体业务流程](token-overall-flow.md)，表达已明确的两板块业务主线，并注明尚未决定的异常分支与执行细节。

两个板块目前是业务职责划分；链扫描、共享事件监控和外部采集已确定采用下文的单链实例运行方式，板块内部其余服务数量与通信技术仍待设计。项目身份、研究结论与依据是描述交接所需的概念信息；本轮不定义字段结构、API 或事件协议。

## 已明确的开发阶段发现范围

当前开发阶段只开发和使用 Ethereum Mainnet（chain ID `1`），不启动其他链的 Token 业务。源码和普通交易查询继续使用现有免费 Etherscan Key；以后扩展其他链时，用户会将现有免费 Key 全部更换为付费 Key，届时再核对目标链与接口权限。持币地址总数与前 100 名明细改由 Ave 获取，不再预留 Etherscan PRO Key 或完整分页持币名单。

当前开发阶段仅关注区块内满足 `transaction.To() == nil` 的顶层合约创建交易，使用交易发送者和 nonce 推导候选合约地址。该范围沿用当前扫描入口，便于先推进项目研究和交易监控的业务设计。

- 工厂合约内部通过 `CREATE` 或 `CREATE2` 创建的合约暂不纳入发现范围；即使内部创建发生在顶层部署交易中，也只跟踪顶层候选合约。
- 项目发现暂不接入 Bitquery 或 Allium，也不在本阶段增加内部调用追踪或工厂事件扫描来扩展创建路径覆盖。
- `transaction.To() == nil` 只用于确定部署候选，不代表候选一定是代币或项目已经值得关注。发现地址后，由聚合合约内部先检查代码是否存在，再按下文已明确的条件识别 Token；不设置独立的部署结果确认环节，也不通过交易回执判断交易是否成功。项目研究筛选标准后续细化。

因此，本阶段的发现结果不代表区块内创建的全部合约。内部创建路径的扩展可在后续重新讨论，不作为当前开发的前置条件。首版链范围已限定为 ETH。DEX 的 Swap 事件覆盖用于研究截止识别；不以项目已存在池子作为顶层发现或启动研究的前提。

## 已明确的单链实例运行方式

同一职责使用同一套代码和同一个构建产物，每个链任务实例通过启动配置选择唯一的 `chain_id`。ETH 与 BSC 分别运行、独立启停和恢复；首版只运行 ETH（`1`），以后扩展 BSC（`56`）时使用同一程序增加实例。运行 ETH 不要求填写 BSC 配置，扩链仍遵守前述付费 Key 要求。

- 区块扫描与共享项目事件监控仅处理实例所属链；Approval/Transfer 与首次 Swap 的实时订阅、补查进度、池与代币映射均有明确链范围。
- 外部采集器按实例所属链领取和处理源码、钱包历史、链上状态及持币任务；资料汇总和 AI 静态分析可以共享运行，不要求全部研究步骤合并进扫描进程。
- 项目、钱包、任务、扫描与日志进度共用数据库，按链区分身份和来源；相同非空源码及已完成分析继续按 `code_hash` 跨实例复用，实际链上地址和值逐合约读取，查询 API 保持统一。
- 实例只加载、校验和连接自己负责链所需的配置，分别提供健康状态、日志和指标。系统链启用状态与实例负责链分开，启动或停止某个实例不得覆盖其他链的启用状态、运行状态或进度。
- 每块完成 Token 识别并可靠保存结果、项目资料和研究任务后推进，源码、AI 及五层钱包继续在后台独立执行。拆分不改变扫描调度、研究截止及首版不处理区块替换的规则。

详细边界、运行关系图和当前启动逻辑需要调整的部分见 [单链实例运行设计](token-chain-runtime.md)。本节属于已确认目标，具体启动参数与部署配置尚未实现；共享数据库和 API Key 的容量限制仍需统一管理。

## 已明确的区块扫描调度（目标规则、尚未实现）

扫描采用主动查询最新区块的有界流水线。每轮固定最多 100 个区块的范围，在范围内并行预取区块数据到有界内存缓冲，同时按高度严格串行处理、保存和推进游标。下一应处理区块一旦取得就开始处理，不等待整批预取完成。轮末重新查询最新高度；追平后等待 1 秒再查询。历史补扫和新区块扫描沿用同一条连续扫描流水线。

### 启动与扫描进度

- 数据库已有该链的扫描进度时，从已保存位置继续，不重新按三天回看窗口初始化。
- 数据库没有该链的扫描进度时，读取当前最新区块，定位向前回看三天所对应的起始区块，从该区块开始扫描。三天是时间范围，不固定换算成某个区块数量；具体定位方式后续设计。
- 本文将扫描游标 `C` 定义为最后一个已成功处理并保存进度的区块高度，下一块为 `C + 1`。首次确定起始区块后，将初始扫描位置设为该区块之前，以包含起始区块。
- 每个区块成功处理后保存进度；没有部署候选的区块也需要记录扫描完成。每轮 100 块是调度上限，不是要求整批完成后才保存进度。

### 每轮执行规则

1. 查询本轮最新区块高度 `H`。
2. 若 `H > C`，确定本轮范围为 `C + 1` 到 `min(C + 100, H)`，两端均包含；本轮上限确定后不随新块产生而延长。
3. 对本轮范围并行预取区块数据，完成一块即按高度放入有界内存缓冲，允许乱序到达。处理端只等待当前应处理的 `C + 1`；该块取得后立即开始处理，不等待整批预取完成。本轮最多 100 块是范围和缓冲上界，不表示必须同时发出 100 个节点请求；实际并行数、限流与背压后续技术设计。
4. Token 识别、结果/项目/研究任务保存和游标推进按区块高度严格串行。成功处理一块后立即保存该块进度、释放对应内存数据，再处理下一块；没有部署候选的区块也需保存完成进度。
5. 某个区块获取失败时，本轮其他区块仍可继续预取并缓冲；但处理和游标停在最早未取得的高度。区块获取、处理或保存的每次失败都通过通知组件通知管理员，并持续重试对应区块，不设次数上限。后续区块即使已在内存中，也不得越过失败块进行处理或推进为已完成。
6. 本轮全部区块成功处理后立即回到第 1 步，重新查询最新高度，再计算下一轮范围；仍有积压时不额外等待 1 秒。
7. 若 `H == C`，说明按当前高度已追平，等待 1 秒后回到第 1 步。等待应允许程序停止时退出。
8. 若 `H < C`，进入异常分支，保留已保存的扫描进度，通过通知组件向管理员发送异常通知，交由管理员人工处理。该分支不按正常追平处理，也不自动回退或重新初始化扫描进度。

例如，已成功处理到 1800，最新高度为 2000，下一轮范围为 **1801–1900，共 100 块**。预取端并行获取这些区块；1801 一旦到达，处理端立即按 1801、1802……1900 的顺序逐块识别和保存，不等待其余区块全部到达。完成 1900 后重新查询最新高度，再从 1901 继续。若 1805 获取失败，1806–1900 可继续预取，但处理和游标在 1804 之后等待 1805，直到它成功。若游标为 1900 且最新高度为 1950，则这一轮范围只有 1901–1950，共 50 块。已处理到 2100 且最新高度也为 2100 时，等待 1 秒后重新查询。

图示见 [Token 区块扫描流程](token-block-scan-flow.md)，包含启动、批次、进度保存、追平等待、失败通知与无限重试，以及 `H < C` 人工处理分支。

本节确定正常扫描的启动、预取、顺序处理、批次和等待规则；不采用新区块订阅作为扫描触发方式，也不增加实时优先与历史补扫的独立处理流程。预取可并行、完成可乱序，但单块处理和提交顺序不变：单块完成需完成候选 Token 识别并可靠保存识别结果、项目资料和研究任务；后续源码、AI 及五层钱包研究不阻塞扫描。

区块获取、处理或保存失败的每一次尝试都产生一次管理员通知，不因同一区块或同类错误重复发生而去重、合并或抑制，也不设置只通知首次失败的规则。每轮最多 100 个区块限制的是本轮预取和处理范围，不限制同一区块的重试次数；预取可继续向后进行，但失败块成功后才继续串行处理本轮的下一块。重试间隔及通知提交失败时的处理方式后续细化。

预取缓冲仅是运行时加速手段，不构成扫描进度。进程停止或重启时可直接丢弃尚未处理的内存数据，并从数据库已保存的 `C + 1` 重新预取；只有区块的识别结果、项目资料、研究任务和扫描游标可靠保存后，该块才算已完成。

区块处理失败后的持续通知与重试，以及 `H < C` 时通知管理员人工处理，均复用仓库的 [系统通知组件](../../design/notifications/system-notification-operations.md)。`H < C` 的人工处理分支独立于区块失败重试循环；该分支的重复通知控制、异常期间扫描控制及人工恢复方式仍待细化。具体告警内容、通知接入方式与接收配置后续设计；本轮不改变通知组件自身的投递和重试机制。

当前明确不考虑区块被替换或链重组，不设计自动回滚、重组修复或因区块替换恢复研究。`H < C` 的既有异常通知与人工处理保留。区块处理采用已选择的 A 边界：完成该块 Token 识别并可靠保存结果、项目资料与研究任务后推进；源码、AI和五层研究独立后台执行，见 [扫描与研究衔接](token-block-scan-flow.md#已确认的扫描与研究衔接)。本轮只更新目标文档，尚未接入异常通知或修改扫描代码，现状见 [Token 链扫描与项目初始化](../../design/token-intelligence/chain-processor.md)。

## 已明确的 Token 识别与逐项诊断

图示见 [Token 候选发现与识别流程](token-discovery-identification-flow.md)，从顶层创建交易推导地址开始，展示单个与批量判断能力、区块批量识别、代码检查、六项检测、识别结论与原因的持久保存。

### 聚合合约同时支持单个与批量判断

聚合合约必须同时支持单个候选合约判断和多个候选合约批量判断，两种调用形态共享完全相同的代码检查、六项检测、结论与逐项诊断语义。这里确认的是能力和行为；具体 Solidity ABI 方法数量、方法名及返回结构后续技术设计。

区块扫描处理当前区块时，先汇总该区块全部顶层部署候选，再统一使用批量判断形态，不在 Go 中逐个调用单个判断。即使区块只有一个候选也沿用批量路径；没有候选则跳过判断。一次批量输入只属于同一条链、同一个区块，结果与输入一一对应并保持顺序。单个候选不通过只影响自己的识别结论，不中断其他候选；只有节点请求或整个聚合调用失败才使当前区块进入失败重试。

单次批量最大候选数和超限后的拆分方式由技术设计确定；需要拆分时仍使用批量判断形态，并在当前区块全部候选完成识别、结果可靠保存后才推进游标。单个判断能力供区块扫描以外需要判断一个指定合约的调用场景使用，具体调用入口后续确定。

### 合约内部先检查目标地址代码（待实现）

Token 识别入口在聚合合约内部先检查目标地址的 `code.length`：

- `code.length == 0`：直接判定为 **不是 Token**，返回并保存原因“地址无合约代码”，不继续执行后续六项调用。
- `code.length > 0`：继续执行下述现有筛选条件。

不单独检查部署交易是否成功，也不把交易回执的 `status` 作为识别前置条件。诊断原因记录查询时的实际事实“地址无合约代码”，不将其直接推断为原始部署交易失败。回执中的转账日志仍可作为初始接收钱包等研究资料的来源，具体研究采集范围按相关章节设计。

### 保留现有六项检测条件

Token 识别保留当前全部筛选条件，不放宽元数据、精度或供应量要求，也不以其他识别建议替换现有规则。以下五组业务条件对应六个独立调用。

**识别结论只有两种：是 Token、不是 Token。** 目标地址有代码且六项全部通过时判定为 Token；目标地址无代码或任意一项未通过时判定为不是 Token，并返回对应原因。不设置“暂时无法判断”“待进一步识别”等第三种识别结果。

| 检测项 | 通过条件 |
| --- | --- |
| `name()` | 能读取且非空 |
| `symbol()` | 能读取且非空 |
| `decimals()` | 能读取且大于 0 |
| `totalSupply()` | 能读取且大于 0 |
| `balanceOf(零地址)` | 能正常返回并按现有要求解码；允许返回 0 |
| `allowance(零地址, 零地址)` | 能正常返回并按现有要求解码；允许返回 0 |

读取和解码要求沿用 [当前 Token 探测逻辑](../../../pkg/abi/ATHENA/ATHENA.sol) 的 `_getToken` 及相关 `_safe*` 方法。名称或符号为空、精度或总供应量为 0，均按现有规则判定该项不通过；余额和授权额度不增加大于 0 的要求。这一步记录项目采用的 Token 筛选结果，是否值得关注仍由后续研究判断。

### 返回并保存逐项检测结果（待实现）

本次新增要求是在“是 Token / 不是 Token”的整体识别结论之外，让调用方能够明确知道哪些检测未通过。识别结论、未通过的检测项及对应原因必须随结果返回，并关联到对应链和合约持久保存，供后续人工查询排查。判定为不是 Token 的合约也要保留这份记录，不能仅返回原因或输出日志后丢弃。

- 记录合约内部的代码存在检查结果；目标地址无代码时返回不是 Token 及“地址无合约代码”的原因，不把未执行的六项调用伪造为已经检测失败。
- 目标地址有代码时，分别返回六个调用对应的检测结果；`name` 与 `symbol` 各自记录，不合并成一个无法定位的失败项。
- 对未通过项说明原因，区分调用失败、返回数据无法解码，以及成功读取但值不满足条件。这些情况均判定对应检测项未通过，整体为不是 Token。例如，`balanceOf(零地址)` 调用失败和 `decimals()` 返回 0 是不同原因。
- 单项不通过时，继续完成其余可执行检测，并列出所有已发现的未通过项，避免只保留第一个失败原因。
- 已取得的返回值可作为诊断依据；底层失败原因只能记录实际取得的信息，不能把“调用失败”直接断言为“方法不存在”。
- 若节点请求或外层聚合调用整体失败，按实际情况记录执行错误，不伪造逐项检测结果，也不新增第三种 Token 识别结论。此类外层执行错误按区块失败规则通知并重试，不推进当前区块；目标合约的单项检测不通过仍作为业务识别结果保存。

以下为目标地址有代码时的诊断内容示意，不定义实际返回字段或错误码：

| 检测项 | 检测结果 | 排查信息 |
| --- | --- | --- |
| `name()` | 通过 | 返回非空名称 |
| `symbol()` | 通过 | 返回非空符号 |
| `decimals()` | 不通过 | 调用成功，返回 0，不满足大于 0 的条件 |
| `totalSupply()` | 通过 | 返回值大于 0 |
| `balanceOf(零地址)` | 不通过 | 调用失败，未取得余额结果 |
| `allowance(零地址, 零地址)` | 通过 | 正常返回 0 |

该示例的整体识别结论为 **不是 Token**，未通过项为 `decimals()` 和 `balanceOf(零地址)`，两项原因均应返回并保存，后续人工能够按对应合约查到该结论和原因。具体返回结构、错误码、存储结构与人工查询入口、检测资源限制及异常传播方式后续设计。本轮只记录目标要求；当前筛选条件继续保留，逐项诊断能力尚未实现。

## 已明确的未添加流动性阶段采集范围

图示见 [Token 研究资料整理流程](token-research-materials-flow.md)，单独展开基础信息、源码、源码中的公开资料链接、税率、持币地址和关联钱包资料的依赖及汇集关系；具体源码获取继续见对应独立流程图。

本节针对合约部署后的早期项目发现与研究，以尚未添加流动性的项目为业务场景。第一板块不研究池深、流动性估值或 LP 风险，不要求通过底池状态证明项目属于该阶段；为识别首次 Swap，允许取得必要的池身份与代币映射。以下为已确定的目标安排，尚未修改当前六源采集代码；首次 Swap 的截止识别归第一板块；第二板块另行设计买入所需的底池状态与交易条件。

### 链上状态的拆分

链上状态是研究的重要依据，需要将现有 `chain_state` 中的代币基础信息与底池信息拆开，保留前者作为本阶段资料，底池相关内容由后续交易监控与执行板块另行设计。税率作为新增的独立研究资料，按源码确定的读取方式采集，不扩充 Token 识别的六项条件；具体采集任务和数据结构后续设计。

| 数据部分 | 内容 | 归属与采集时机 |
| --- | --- | --- |
| 代币基础信息 | 合约地址、ERC-20 探测结果、名称、符号、精度、总供应量、合约 `code.length`（链上运行时代码的字节数）及对应区块与时间 | 项目发现与研究阶段采集，不依赖项目已经建立交易池或添加流动性 |
| 合约税率 | 源码识别的税率类型与分项、读函数、当前返回值及换算依据 | 项目研究阶段按 AI 确定的方式读取当前合约，保存实际区块与时间，不作为 Token 识别条件 |
| 底池信息 | 候选池地址、池合约是否创建、是否添加流动性，以及池内资产余额、池深、LP 供应与持有情况、锁定情况和流动性估值等 | 研究阶段不采集池深、流动性和 LP 风险；首次 Swap 识别所需池地址、真实协议身份及币种映射单独取得，其余由第二板块设计 |

代币基础信息、字节码信息、合约 owner、需要链上读取的税费接收地址、税率及钱包资产等链上状态，明确以各自采集时的最新区块作为数据源，保存实际读取的区块号及对应时间。不同采集不要求使用同一个区块；同一税率的相关读函数及动态分母如需多次调用，则固定使用该次税率采集的区块。同一数据时点已取得的信息可以复用，旧识别快照不能直接当作本次最新状态。部署资料仍保留实际部署区块，钱包历史仍采集部署前交易；Etherscan 源码查询记录查询时间与资料来源，不视为指定区块的源码快照。直接从源码提取的固定税费接收地址保留源码依据，不记成链上读取结果。

持币地址总数和 Top 100 明细来自 Ave 的两次独立查询，分别记录查询时间、接口来源与取得状态；接口未提供对应区块时，不填写推测区块，也不将总数、排名、数量和占比视为同一区块的一致快照。Top 100 是有界排名，不表示完整持币名单。该时点范围独立于部署区块及关联钱包部署前 300 笔窗口。

代币基础信息需要获取并保存目标代币合约地址在查询区块的 `code.length` 具体数值，以字节为单位，关联对应链、合约、区块与时间。该值描述目标地址上已部署的运行时代码长度，不是源码文本长度或部署交易输入长度。识别入口已有的 `code.length == 0` 检查继续保留；本次补充要求保存实际长度，不能只保留“有无代码”的判断。长度数据先作为基础事实采集，具体研究用途待用户后续明确，本轮不增加长度阈值、评分或筛选规则。该采集与保存要求尚未实现。

启动研究不以池子已经存在或已取得底池状态快照为前提。首次 Swap 识别按协议取得必要的池身份与币种映射，不采集池深或 LP 风险；没有匹配到事件不表示已证明项目无池或没有交易。第一笔实际 Swap 结束研究，具体买入条件仍由第二板块设计。

这里先确定数据职责与阶段边界，不预先确定拆分后的任务名称、服务数量、采集频率、接口或数据库结构。当前基础信息、池信息和模拟字段的实现背景见 [ATHENA 聚合查询](../../design/token-intelligence/athena-contract.md) 与 [现有采集数据定义](../../../internal/token/collection/payload.go)。

### 合约源码按字节码哈希复用

源码采集以目标合约的运行时字节码哈希 `code_hash` 查询数据库，不是对源码文本计算哈希。相同哈希已有非空源码时关联并复用；没有可复用源码时，使用当前合约所属链和地址调用 Etherscan。其他地址此前返回空源码不阻止当前地址查询，只有哈希记录也不代表已取得源码。

必须区分三类采集结果：

| 结果 | 处理 |
| --- | --- |
| 成功取得非空源码 | 保存源码、来源链与地址、查询时间及哈希关联，进入 AI 分析或复用已完成报告。 |
| 请求成功但源码为空 | 记录本次查询无源码、合约可能尚未开源；等待管理员手动补采，或由按链共享事件监控接收目标 Token 后续 Approval 或 Transfer 活动并触发再次查询。处理时仍在研究且仍无非空源码才发起补采，不设置定时轮询。 |
| 请求失败 | 保存技术错误与次数，重试并通过系统通知组件通知管理员处理；不能标记为未开源，也不能当作正常空源码结果。 |

请求失败的既有次数口径先保留：首次请求之外最多再重试三次，总计最多四次；重试耗尽后通知管理员，保留请求失败状态及人工处理线索。请求成功返回空源码不消耗技术失败重试预算；它属于另一个需要再次查询的分支。重试间隔、通知提交失败时的处理和人工恢复入口待细化。研究截止后不再自动发起项目研究补采，已启动调用的收尾边界另行设计。

图示见 [合约源码获取流程](token-contract-source-flow.md)。源码不可得不自动产生风险等级；未取得源码时的其他资料仍保留。源码后来取得后，可以补充共享源码与报告，不沿用别的未取得源码地址发起查询。

按 `code_hash` 定位的实际源码共享 AI 静态质检报告、owner 分析与读取方式、税费接收钱包分析、固定地址与读取方式、税率分析与解释方案，以及公开资料链接和出处。需要链上读取的 owner、税费接收地址与税率逐合约读取。复用源码不将新地址标记为在 Etherscan 独立完成源码验证，也不将不同初始化参数或链上状态视为相同；链接保留实际提取源码及出处，不宣称已经核实新项目的官方归属。

当前实现 `ContractSourceProcessor.Process` 在缓存记录 `Fetched` 为真时复用，包括空源码；当前采集任务在第三次失败时结束。这与目标中的空源码再次查询、请求失败独立记录及首次加三次重试存在差异，后续实现时调整。参考 [源码处理器](../../../internal/token/collection/application/processors.go)和[当前采集任务设计](../../design/token-intelligence/collection-profile.md)。

### AI 静态质检、程序风险判断与报告复用（待实现）

AI 只阅读实际取得的源码并生成质检报告，不给出风险等级，不判断项目是否满足管理员筛选标准。报告先保存并供管理员查看；后续管理员维护筛选标准，由程序根据报告内容匹配规则并生成风险等级。当前不定义哪些情况属于高风险，也不在没有规则时默认判为低风险或研究通过。图示见 [合约源码静态质检流程](token-contract-review-flow.md)。

报告至少明确包含下列能力判断，并附对应源码位置、函数、权限、触发条件和影响：

| 必含检查项 | 源码分析要求 |
| --- | --- |
| 是否可以无限增发 | 说明增发入口、权限与供应量约束，是否存在可绕过或修改的上限。 |
| 是否可以修改余额 | 说明谁可以改变哪些地址的余额以及所需条件，区分正常转账记账与额外修改余额的能力。 |
| 是否可以限制转出 | 说明是否存在限制转出、禁止转账或针对地址施加转出限制的能力及条件。 |
| 是否使用代理 | 识别源码中的代理转发结构并保存依据，不读取或分析实际代理实现。 |
| 是否存在外部未知依赖 | 指出本次源码未提供或无法确定具体实现的外部逻辑；已完整提供的库或父合约不因 import 自动判为未知。 |

前三项是报告的明确内容要求，不直接等同于高风险规则。正常业务输出始终是基于所提供源码的质检报告；AI 请求失败、超时或响应格式无效单独作为技术异常处理，不保存为报告，也不伪造否定结论。源码范围限制与触发条件在报告中说明，不宣称已经核实当前链上角色、开关或参数。

本阶段不接入静态分析工具、不执行合约、不读取链上状态核实报告，也不继续获取或分析代理实现或外部依赖。owner、税费接收钱包和税率的 AI 分析及 Go 读取属于独立研究资料流程，不是静态报告的完成前提。

同一份源码默认只生成一份共享报告，按 `code_hash` 匹配到其实际源码后直接复用，多个部署不重复调用 AI。默认按 AI 报告准确的前提使用，不增加自动复核或多模型评审。管理员可以针对某一份源码报告人工触发重新检测，例如提示词调整后需要重新分析；不是所有新项目都重新检测，也不自动批量重评。重新检测成功后形成新的有效结果，具体替换、在途读取与失败保留机制待实现设计。

报告与后续程序风险判断分别表达：重新生成 AI 报告改变的是源码分析结果；管理员规则变化后的程序重新判断使用报告匹配规则，不天然要求再次调用 AI。程序风险结果需要关联实际使用的报告与规则，已有项目是否自动重新判断及交接后如何处理另行设计。后续程序命中管理员高风险规则时，沿用排除项目并保存依据的方向；当前只生成、保存和展示报告，不执行尚未维护的评级规则。

公开链接、owner、税费接收钱包、税率与静态报告分别复用已完成分析，不要求同一次 AI 调用或共同完成。并发去重、报告输出结构、提示词、Go 消费格式、技术重试和人工重检接口待细化，不改变已经确认的职责分工。

### 研究证据与完成条件

项目首次实际 Swap 是研究截止事件，资料是否齐全不改变截止时间。以下采集适用于研究仍在进行的项目；后续程序按管理员规则判为高风险时可提前排除。当前 AI 报告不评级，已启动任务在研究截止时如何收尾仍待设计。

部署交易、部署者、代码哈希、初始接收钱包及分配线索等发现阶段已经取得的信息，应一并作为研究材料。目标设计的 L1 直接关联钱包包括部署者、最多 5 个初始接收钱包、取得的合约 owner 及一个或多个税费接收钱包，四类角色对应的地址均纳入普通交易与代币余额采集。初始接收钱包沿用部署交易内该代币的转账日志，按净接收量从高到低排序，在净接收量为正且查询时无合约代码的地址中最多选取 5 个。该上限仅针对初始接收钱包，不限制税费接收钱包数量；owner 和税费接收钱包也可为合约地址。相同地址保留多个角色标签并去重采集。后台从 L1 的资金来源自动发现 L2，再逐层查找 L3、L4、L5，自动执行所有已发现分支的历史研究，不等待前端展开。

钱包历史交易的查询规则已确认原样保留：对每个去重后的关联钱包，通过 Etherscan 普通交易接口 `account/txlist` 获取项目部署区块之前、距离部署时点最近的最多 300 笔交易。L1–L5 各层钱包均沿用这一规则；300 笔是每个钱包的上限。

| 查询项 | 已确认规则 |
| --- | --- |
| 起始区块 `startblock` | `0` |
| 截止区块 `endblock` | `项目部署区块 - 1`，不包含部署区块内及之后的交易 |
| 排序 `sort` | `desc`，从新到旧 |
| 页码 `page` | `1`，只取第一页，不继续翻页补充更早交易 |
| 每页数量 `offset` | `300`；不足 300 笔时保留实际返回数量，无交易时保留空结果 |

例如项目部署在第 `30000` 区块，则 L1–L5 查询范围均固定为 `0–29999`，倒序取每个钱包最近的最多 300 笔普通交易。即使实际采集时链已推进到更高区块，截止高度仍为 `29999`，也不改为某笔资金转入前的区块。该范围是普通交易的历史样本，不包含内部交易或完整代币转账事件历史；为分析代币交互补充的是这批交易的回执与日志，不扩大 300 笔范围。

这些交易用于整理并展示各层钱包直接部署过的合约、交易或交互过的项目，以及多层资金来源和地址间的交易联系。钱包资料当前只采集、解析和展示，不据此筛选或排除项目。层级范围、资金来源定义和分析内容按下节执行；具体行为解析仍待细化。

当前代码已经实现上述区块范围、排序、页码及数量规则，本轮原样保留。当前钱包范围仍只覆盖部署者和最多 10 个初始接收钱包；初始接收钱包缩减为最多 5 个、owner 与税费接收钱包的获取及纳入采集、L2–L5 来源发现、多层历史分析与资金来源图均待实现。详见 [钱包历史交易现状](../../design/token-intelligence/wallet-normal-transactions.md)及对应的[截止区块计算](../../../internal/token/collection/application/processors.go)与[Etherscan 查询参数](../../../internal/token/adapters/normaltransactions/provider.go)。

现有 `simulation_result` 是六项独立的 `transfer` / `transferFrom` 调用探测，当前仅记录调用是否报错，不是完整的买入、卖出模拟。因此不将现有结果直接作为项目安全、增发能力或买卖可执行性的结论。辅助合约探测与后续买卖可执行性检查的目标和方式仍需分别设计。实现依据见 [当前模拟调用](../../../internal/token/adapters/evm/project_state_reader.go)。

研究阶段不再以现有六类采集任务全部结束作为完成条件；项目第一次实际 Swap 出现时结束研究并保留截至当时的资料、进度及未取得原因。本阶段未采集底池信息、未取得 Ave 持币资料，或没有取得非必采的模拟结果，不应仅因此阻塞研究或将研究结论标为不完整。owner 由 AI 分析源码确定读取方式，再由 Go 程序读取链上结果；税费接收钱包由 AI 提取固定地址或提供方式交由 Go 读取。未取得或只取得部分地址时记录实际结果与原因，保留成功结果并继续使用已有资料研究，不将取得全部 owner 或税费接收地址作为研究完成的必要条件。研究截止不保证所有资料完整。交接条件、活动更新合并及资料部分取得时的程序规则处理仍待细化；遇到相同哈希但未取得源码时，按前述已明确规则使用当前合约重新查询。这不代表可以跳过必要的项目研究直接买入。

## 已明确的多层关联钱包研究与资金来源图（尚未实现）

当前阶段的职责为“采集钱包数据 → 解析事实与关联关系 → 保存并展示”。多重角色标签、L1–L5 资金来源图、历史部署与交易项目清单、交易依据和 L1 代币余额均用于查看，不设置基于这些钱包数据的风险评级、通过／不通过判断或项目排除逻辑。采集失败、结果为空或解析未完成按实际情况记录并展示，也不转为项目筛选结论；钱包数据驱动的进一步筛选暂不设计。

独立图示见 [多层关联钱包研究流程](token-wallet-research-flow.md)与[钱包资金来源关系图](token-wallet-funding-graph.md)。L1 为部署者、最多 5 个初始接收钱包、已取得的 owner 及全部已取得的税费接收钱包；从 L1 交易样本发现资金来源形成 L2，再依次查找 L3、L4、L5。L5 对应从 L1 向上查找四轮来源；各层统一使用当前项目部署区块之前最近最多 300 笔的窗口，L5 仍开展历史行为分析，但不继续发现 L6。

当前持币地址属于独立分布资料。可按链和地址匹配已知的钱包角色及资金来源关系供展示，但不会仅因持币而自动成为 L1，也不自动触发该地址的 300 笔历史、资金来源扩展或其他资产余额采集。已属于 L1–L5 的地址继续沿用其原有采集范围。

首版资金来源定义为：当前待展开钱包的交易样本内，成功向该钱包直接转入 ETH且金额大于零的发送地址。L1–L4 使用相同规则发现上一层来源，保留来源地址、接收钱包、原生币种类与金额、交易哈希、区块、区块内交易序号和时间，以及钱包角色和样本来源。失败交易不形成实际资金转入依据；USDT 等代币资金来源和内部转账不纳入首版扩展，样本不能代表完整资金来源。

L1–L5 每个钱包均整理两份清单：

| 分析内容 | 需要保存的结果 |
| --- | --- |
| 直接部署过的合约 | 成功的顶层创建交易对应的合约地址、部署交易、区块与时间；进一步识别是否为 Token，匹配已有项目及研究报告，保留引用和依据 |
| 交易或交互过的项目 | 按链和代币合约地址关联项目，保存具体行为、交易哈希、区块与时间；识别有证据的买入、卖出，并与授权、普通转账、被动收款和其他交互分别记录，失败调用按实际结果记录 |

对已选定交易补充回执与日志，并结合调用数据识别代币交互。普通交易的 `to` 可能是路由合约，不能直接当成交互代币；创建出的合约地址可从 Etherscan `contractAddress` 或创建交易回执取得。当前 Token 交易模型尚未保存创建出的合约地址及本流程所需的回执日志，这部分随历史分析实现。

钱包“交易过什么项目”的识别不限定为 PancakeSwap V2 或 Uniswap V2。目标覆盖当前研究链范围内不同 DEX、协议版本、聚合器、通用及自定义路由、多跳与组合交易。采样入口仍为既定的全部 300 笔普通交易，不先按 V2 事件、固定 Router 或少量方法名筛选。先保留有证据的钱包代币关系，再结合对应协议的调用内容与执行日志识别买卖；按链和代币合约地址统一关联项目，不因交易入口不同而拆成不同项目。

授权、普通转账、被动收款和实际买卖分别记录，不单凭 `Transfer`、净收支或顶层方法名推断买卖，也不把路由中间经过的全部代币都归为钱包主动交易过的项目。协议尚未识别时保留原始证据及能够确定的关系，不丢弃交易或据此断言没有交易过项目。具体解析覆盖及必要补充数据后续细化，详见 [交易项目识别的协议覆盖](token-wallet-research-flow.md#交易项目识别的协议覆盖)。这项历史研究范围独立于现有 V2 底池查询和 Swap 索引，不增加研究阶段的底池状态采集。

同一项目内按链和钱包地址去重，共同来源只保存一个节点并分析一次，钱包角色与所有资金关系完整保留。同一钱包可以同时具有“部署者”“owner”“初始接收钱包”“税费接收钱包”等多个角色标签，各标签并存且不互相覆盖，相同标签去重。角色关联具体项目及证据，不能把其他项目中的身份直接套用到当前项目。一个钱包有四个标签仍计为一个钱包，同一历史窗口只采集一份最多 300 笔交易并复用分析，同一数据时点的余额按地址复用；具体示例见 [多重身份与标签](token-wallet-research-flow.md#同一钱包的多重身份与标签)。

来源已在图中时连接已有节点，保留跨层、循环和回流关系，避免重复采集或无限展开。L1 保持为直接关联入口，其他节点按已发现关系中距离任一 L1 的最短上游追溯距离分层；层级与角色标签分别记录，不因多个角色复制钱包或资金连线。发现更短路径时更新层级，复用已有分析并按新层级判断扩展边界。跨项目复用需匹配链、地址、截止区块和采样规则，不能永久复用某钱包的一次历史样本。

后台自动采集并分析 L1–L5，展示时也提供五层结果，不以用户点击展开作为取数触发。底层保存有向关系图，以分层资金来源树呈现；允许折叠控制显示，折叠不删除数据或暂停后台采集。五层限制深度，当前不增加额外金额门槛或每层来源数量上限；并发、限流、进度保存与局部重试待细化。首次 Swap 可能在五层完成前出现，此时研究结束，保留已经取得的部分与未完成原因，不等待五层完成才结束研究。

资金连线按链、来源、接收方和资产合并，显示金额、笔数、首次与最近交易时间；点击查看每笔交易依据。同一交易出现在多个钱包样本中时按链和交易哈希去重，样本关联分别保留，汇总不重复计数。点击任一层的钱包可查看其历史部署合约、交互代币及已匹配的项目、研究报告。显示筛选与完整资料分开，连线汇总与其交易明细使用相同范围。

历史关系图中存在连续连线，不自动代表同一笔资金连续流动。例如 L2 在 `25000` 区块向 L1 转账，L3 在 `28000` 区块才向 L2 转账，两笔虽都早于项目部署区块 `30000`，后一笔仍不能解释前一笔的来源。查看某笔入账的上游路径时，按区块与区块内交易序号逐跳核对上游入账早于下游出账；这只筛选已取得的证据，不改变 `B - 1` 和最多 300 笔的查询规则，也不单凭时序判断混合资金中的金额归属。

最终将各层历史项目、代币交互与资金关系关联当前项目，保存交易证据供展示与核对。共同来源本身不直接等同于同一团队；即使关联历史项目已有风险报告，也只展示关联和报告引用，不据此排除当前项目。图上的显示筛选、折叠和路径核对仅影响查看范围，不属于项目筛选。这一资料流程独立于源码 AI 静态质检，自身不执行项目排除或关注项目交接。L1 继续采集已追踪代币余额，L2–L5 仅新增历史交易、行为研究及资金关系。

数据组织参考 GraphSense，节点展开与交易明细参考 MetaSleuth 和 Arkham，Etherscan 多层遍历实现可参考 chainmap。资料链接与适用边界见 [资金来源图参考方案](token-wallet-funding-graph.md#参考方案)。沿用自己的采集和数据库能力承载地址、资金关系及证据，具体技术结构与接口后续设计。

## 已明确的项目研究与筛选目标（待实现）

项目研究从通过 Token 识别开始，收集源码质检报告、基础事实及钱包等资料，直到链上出现该项目的第一笔实际 Swap。图示见 [项目研究流程](token-research-flow.md)。

当前 AI 只输出并展示质检报告，至少包含无限增发、修改余额和限制转出的能力判断及依据。管理员以后维护筛选标准，程序按报告匹配规则生成风险结果；当前不预设任何高风险阈值，不将未配置规则解释为已通过。钱包、税率、持币与公开资料继续只采集、解析、保存展示，不增加基于这些资料的自动筛选。

后续程序判为高风险的项目可提前结束研究并排除，关联项目保存实际报告、匹配规则、结论与依据。Token 识别结论、质检报告、程序风险结果和研究是否结束是不同事实，不能相互覆盖。关注项目交接及买入条件另行设计，不直接由 AI 决定。

## 已明确的研究截止：项目首次 Swap（待实现）

每条链使用一套共享事件监控，动态覆盖本链所有仍在研究的项目，不为每个项目分别建立一套订阅。首版仅运行 ETH；通过实时订阅降低发现延迟，并以历史日志补查覆盖启动、断线、重启、动态目标变化及项目登记时差。Swap 通常由 Pair、Pool、Vault、PoolManager 等交易场所合约发出，必须通过协议事件解析、可信发出方或池归属与实际交换币种映射，识别项目的第一笔实际 Swap；不能只订阅 Token 合约地址。不限定 Uniswap V2、V3、V4，也不限定某一个 DEX；首批协议事件目录及适配范围见 [ETH Swap 事件调研](token-swap-events-research.md)，该文档中的接入优先级为建议，尚未视为已实现覆盖。

- 识别到项目首次 Swap 后结束研究，不继续自动采集新资料；保留已有资料及截止的交易、区块、交易顺序、日志位置和协议依据。
- 研究结束表示研究窗口已经截止，不表示报告或五层钱包全部完成，不表示高风险，也不表示可以买入。未完成资料按实际情况保留。
- 第一笔 Swap 按链上发生顺序判断，不以不同事件处理任务的到达顺序判断。项目部署区块内也可能发生 Swap，因此研究截止查询不能沿用钱包历史的 `B - 1` 上限。
- 新项目或新监控目标先开始实时接收，再固定补查终点 `H`，从项目部署区块 `B` 补查到 `H`，两端包含。实时与补查允许重叠，至少按 `chain_id`、交易哈希和 `logIndex` 去重；首笔按 `blockNumber`、`transactionIndex`、`logIndex` 确定。
- 断线或重启后从已经可靠保存的连续覆盖进度补查；只有完整取得并保存整个区间后才推进覆盖进度，没有匹配日志的区块也可形成已覆盖范围。内存缓冲不是覆盖完成依据。
- Swap 识别需要池或管理合约的真实身份与代币映射。为此取得的 token0/token1、poolId 或币种列表属于事件匹配资料，不扩展为研究底池深度、流动性或 LP 风险。
- 单纯同名事件、相同 topic、转账日志或添加流动性都不能单独当作实际 Swap。未知协议没有被识别到，不等于已经证明项目尚未交易；具体覆盖说明随适配器保存。
- 可信 Swap 一经识别就立即停止继续研究；如该事件之前仍有未覆盖范围，继续补查以确定链上最早 Swap。若随后找到更早事件，更新最早证据，但不改变研究已经停止的事实。项目登记前到达的日志不能仅因当时尚无项目而永久丢弃。
- 首次 Swap 时尚未交接给交易板块的项目结束研究并放弃本轮参与，不用部分资料临时补交接。已经交接项目与第二板块的协作继续设计，研究截止不是买入指令。

首次 Swap 结束研究与后续程序风险规则提前排除是两个独立停止原因。管理员显式触发共享报告重检属于维护动作，不自动恢复已结束项目的研究。

### 项目活动触发源码更新

除 Swap 截止监控外，同一按链共享事件监控还动态维护“仍在研究且尚无非空源码”的项目目标，通过实时订阅与从部署区块开始的历史补查接收目标 Token 合约自身发出的 ERC-20 `Approval` 与 `Transfer` 日志。这些活动去重后触发项目更新事件，处理时再次确认项目仍在研究且仍无非空源码，再重新执行源码查询；管理员也可以手动补采。项目取得非空源码后退出活动目标，但 Swap 监控继续到研究结束。已有非空源码继续按哈希复用，不因每笔活动重复下载源码或调用 AI。

活动检测只表达发生了相关事件，不将 Approval 当作交易已经开放，也不将 Transfer 当作 Swap。第一版不要求保存研究期全部 Approval/Transfer 历史，只保存已经接收并用于活动触发的证据；同一项目多个活动与正在进行的源码请求如何合并、请求失败与后续新活动的协作待细化。首次 Swap 或后续规则排除使研究结束后，不再由活动自动启动源码采集。完整的共享接收、覆盖恢复与去重规则见 [项目事件监控、源码更新与研究截止](token-project-activity-flow.md)。

## 已明确的合约 owner 与关联钱包研究（尚未实现）

本节属于钱包资料的采集、解析与展示阶段，owner 的取得、缺失及其钱包历史结果均不触发项目筛选或排除。源码质检只生成报告，风险判断由后续管理员规则与程序负责。

合约 owner 是项目的关联钱包。取得 owner 地址后，连同部署者、初始接收钱包及税费接收钱包一并纳入普通交易与资产余额采集，并保留各自的角色关联；不同角色可能对应同一地址，也可能对应不同地址。图示见 [合约 owner 获取与关联钱包采集流程](token-owner-wallet-flow.md)。

### AI 分析源码，Go 读取链上 owner

owner 获取统一采用“AI 判断源码是否提供可用读取方式，Go 程序按该方式读取链上数据”的流程。读取方式依据实际源码确定，不限定为 `owner()`、`getowner()` 或其他固定函数名，也不设置预先尝试固定函数的流程。

AI 对每一份源码分析 owner 能否读取，并在可读取时给出 Go 可以执行的读取说明。例如源码提供 `getowner()` 并返回地址，则说明函数签名、所需参数及返回类型，由 Go 程序编码调用、解码结果。分析依据应指向源码中对应的字段或函数，不能只凭函数名称推断其返回值就是 owner。AI 输出读取方式，实际 owner 地址通过当前合约的链上读取取得。

每次获取 owner 时，按以下流程处理：

1. 使用当前合约的运行时字节码 `code_hash` 查询数据库，匹配对应源码已完成的 owner 分析结果。
2. 命中时复用“可读取及读取方式”或“未识别到可用读取方式”的结论，同一份源码不因新部署地址重复分析。
3. 没有已完成结果时，取得或复用对应的非空源码，交给 AI 分析是否可读取 owner 及读取方式。没有源码则记录资料未取得，不能让 AI 无依据分析。
4. 将完成的分析结论、依据及可用读取方式关联源码与 `code_hash` 保存，供相同源码复用。AI 请求失败、超时或无效响应单独记录为技术异常，不保存成“不可读取”的源码结论。
5. 分析或复用结果提供可用方式时，由 Go 程序对当前链、当前合约执行只读查询，以本次采集时最新区块的状态取得 owner；没有可用方式时记录结果，结束本项获取。
6. 保存本次实际使用的方式、读取结果、来源区块与时间。取得地址后纳入 L1；未取得地址则保存原因，继续其他已知钱包与资料采集。

同一份源码共享 owner 分析结论和读取方式；各部署实例的 owner 地址仍分别读取，不能复制其他合约的地址或旧 owner 快照。源码质检报告与 owner 分析分别保存结果，不要求在同一次 AI 调用中取得，也不互相作为完成前提。Go 的 owner 查询不进入静态质检报告的链上核实过程。

### 读取结果与钱包资料

取得 owner 后，沿用关联钱包采集范围：以 `项目部署区块 - 1` 为截止高度，读取部署前最近的最多 300 笔普通交易；按钱包资产采集时最新区块读取 WETH、USDT 等已追踪代币余额，不读取原生币余额。owner 为合约地址时也按关联地址采集，不沿用初始接收钱包的无代码地址筛选来排除 owner。地址已在 L1 时追加当前项目的 owner 标签，保留其他角色并复用同一窗口的资料与分析。owner 地址来自当前采集时点，不将其自动解释为部署时的 owner。

没有源码、AI 完成分析但未识别到可用方式，以及 Go 链上调用未取得地址，需要分别保存实际结果与原因。“未识别到读取方式”或“未取得地址”不表示已经确认合约没有 owner，也不能填入部署者等推测地址。无法定位 owner 地址时，只跳过该未知地址的钱包采集；其他已知钱包继续研究，不因此排除项目或改变 Token 识别结论。项目首次 Swap 后不再继续研究；后续程序按管理员规则排除的项目同样停止。

读取说明的具体结构、Go 支持的读取方式及校验、多种方式或返回值冲突、零地址等特殊结果、AI 与链上请求的重试、分析更新与并发去重、owner 变化后的更新仍待细化。本轮只更新目标设计，不规定数据库结构、模型或新的重试次数。

| 源码中的情况 | 获取方式 |
| --- | --- |

AI 根据实际税费分配逻辑判断地址用途，不仅凭变量或函数名称识别。支持多个字段、多个读函数或返回多个地址的方式，不只保留第一个接收钱包。读取说明应足够 Go 编码调用与提取地址；需要参数时给出参数类型、值或可确定的取值依据，不猜测参数或执行 AI 生成的任意程序。

可修改变量的初始赋值即使在源码中写成地址字面量，也不能直接当成当前固定接收地址；需要通过可用读函数取得当前值。由部署参数决定但无法从实际源码确定的地址，也不能猜测填写。本项不新增部署初始化资料采集，不解析代理实现地址，也不获取或分析外部依赖源码。

先按 `code_hash` 查询对应源码已完成的税费接收钱包分析结果，命中直接复用，没有时才对非空源码进行 AI 分析。共享识别结论、源码依据、确实固定的地址和读取方式；动态地址由各合约分别读取并保存实际调用、返回值、来源区块与时间，不复制其他部署实例或旧快照。静态质检、owner、税费接收钱包和税率分析分别保存，不要求在同一次 AI 调用中生成，也不互相作为完成前提。

取得的全部地址按链和地址去重加入 L1，追加当前项目的“税费接收钱包”标签，并保留 owner、部署者和初始接收钱包等已有标签。同一地址对应多个税费用途时，保留各用途及其源码或读取依据。“最多 5 个”只限制初始接收钱包，不限制税费接收钱包数量；税费接收钱包可以是合约地址。

后续沿用每个钱包在区块 `0..B-1` 内最近最多 300 笔普通交易、同批回执日志、历史部署与代币交互分析、L2–L5 资金来源发现，以及 L1 已追踪代币余额采集，其中 `B` 为项目部署区块。动态读取得到的是采集时点的配置地址，不自动解释为部署时的接收地址；识别到接收配置也不代表已经发生税费支付。

源码中未发现税费接收钱包、已识别接收逻辑但未找到可用获取方式、未取得源码、AI 技术失败及链上读取失败分别保留实际结果与原因。只取得部分地址时保留成功结果并继续这些钱包的采集，不把未知部分解释为不存在，也不把技术失败保存为可复用的“未发现”结论。本项仅采集、解析和展示，不增加项目风险评级或过滤规则；后续程序按管理员规则排除项目的方向保留；当前 AI 不评级。

## 已明确的合约税率读取（尚未实现）

税率沿用“AI 分析源码确定读取方式 → Go 读取当前合约链上数据 → 保存并展示”的思路，作为独立项目资料。完整图示见 [合约税率读取流程](token-tax-rate-flow.md)。税率读取不增加 Token 识别条件，也不改变关联钱包范围。

1. 按当前合约运行时 `code_hash` 查询对应源码已完成的 AI 税率分析结果；已有结果直接复用，没有结果且取得非空源码时才分析。
2. AI 根据实际税费计算逻辑识别可读取的税率及其用途，例如买入税、卖出税、普通转账税或具体分项；不强制每个合约都有这些分类，也不只凭函数名称判断。对每项给出函数签名、必要参数及其确定取值或依据、返回类型与提取位置，以及单位、分母或换算公式的源码依据。
3. Go 按可执行的说明，对当前链、当前合约在本次采集的最新区块进行只读调用，解码原始返回值。同一税率相关分项和动态分母如需多个读函数，固定使用该次采集的区块。
4. 保存税率类型或分项、原始返回值、单位或分母、能够确定的百分比、源码与调用依据，以及实际区块与时间，关联当前项目展示。只有源码明确分项的组合公式时才计算总税率，不将总税率与其分项重复相加。

例如源码明确按 `10000` 为分母扣税，读函数返回 `500`，则展示 `500 / 10000 × 100% = 5%`。分母由源码计算逻辑或对应读函数确定，不统一假定为 `100`、`10000`，也不按代币 `decimals` 推算。单位、分母或组合关系无法确定时，保留原始值与原因，不编造百分比或总税率。

同一份源码共享税率语义、可读取性结论、读取方式和换算依据；实际税率及链上分母逐合约读取，不复用其他部署实例或旧快照。没有源码、未识别到可用读函数、AI 技术失败、链上读取失败与部分成功分别记录。保留成功读取的税率项，未取得的值不填成 `0` 或“无税”；实际读到 `0` 也只表示该项在该时点的返回值为零。技术失败不保存为可复用的“无读取方式”结论，不覆盖有效分析。

本项展示当前读到的税率配置及源码中的适用条件，不承诺某笔买卖的实际扣税结果。本轮不扩展为交易模拟、链上角色或免税名单核实，不解析代理实现或外部依赖，不增加直接读存储或固定函数探测兜底。源码中的固定数值或初始赋值可以作为分析依据，不能冒充本次链上读取结果。

税率资料只采集、解释和展示，不增加阈值、评分或项目过滤规则，也不作为 owner、税费接收钱包或其他资料采集的前置条件。AI 静态质检独立生成报告而不评级，后续程序依据管理员规则判断风险，报告不使用税率链上结果进行核实。各项源码分析分别复用，无需在同一次 AI 调用中完成。

调用与换算说明的具体结构、Go 支持与校验、参数或结果冲突、重试与并发协调、分析更新与后续税率刷新仍待细化。本轮仅更新目标设计，尚未实现税率读取。

用户已明确首版仅使用 ETH 链。现有 Etherscan 免费 Key 继续用于合约源码、钱包普通交易等既有采集；将来扩展其他链时，原有免费 Key 全部更换为付费版本。持币资料不再使用 Etherscan，不需要单独开通、配置或调度 Etherscan PRO Key。

本阶段只使用 Ave 的两项持币能力：Token Detail 的 `holders` 和 Top100 Holders 明细。不恢复现有 Ave 市场、池、流动性或风险标签采集，也不从 Contract Risk 等其他 Ave 接口拼接持币结果。Ave 未配置、暂未收录目标 Token、权限不足、配额或限流、网络或解析失败时保存实际原因，不解释为零持币地址或项目异常，也不回退 Etherscan 补齐。

当前实现的 Ave Token Detail 已读取 `holders`，但尚未形成本文要求的独立持币资料，也未接入 Top100 Holders。现有 [Ave 市场数据采集设计](../../design/token-intelligence/ave-market-data.md)仍说明当前运行行为，后续技术设计需将目标采集范围收敛到本节两项持币数据。具体 Ave token-id 链映射、认证配置复用、两项请求协调、错误处理、限频重试、刷新、标签展示、存储及接口结构后续设计；本轮不修改配置或服务。

### 结果保存与研究边界

按链、目标代币合约和持有人地址关联，逐项保存 Top 100 名次、地址、持有数量、持有占比、Ave 原始标签字段和查询时间，不按相同 `code_hash` 共享不同代币合约的持仓。当前 Top 100 不等于部署交易内的初始分配，也不能代替指定历史区块或当前时点的完整持有人名单；本次不增加完整名单、历史持有人重建或初始分配明细采集。

本需求不设计持币分页、游标、全量遍历状态或覆盖率。`holders` 只表达 Ave 提供的地址总数，Top 100 只表达提供方的有界排名；不能根据两者条数差异推断采集不完整，也不能将 Top 100 标为全量。Ave 成功空结果、字段缺失、未收录和技术失败分别表达，不把未采集、权限错误或解析失败填成 `0`，不推测地址标签。

本项只保存并展示当前持币总数与 Top 100 分布，不增加集中度阈值、评分或过滤规则，也不把 Top 100 地址自动纳入 L1–L5 历史研究。它记录目标代币的持有量，不扩充 L1 已追踪代币余额的资产配置。未取得持币信息不阻塞其他研究；源码报告不评级；后续程序风险过滤独立设计，首次 Swap 后不继续研究。

## 已明确的源码公开资料链接提取（尚未实现）

研究阶段增加“从合约源码提取项目公开资料”：由 AI 阅读已经取得的源码，包括注释及字符串中实际出现的链接，重点识别 `https://` 链接，整理并展示一份源码中的多条公开资料。图示见 [源码公开资料链接提取流程](token-public-links-flow.md)。本项只提取源码中的信息，不新增网络搜索、网页抓取、社交数据采集或审计报告内容分析。

| 资料类别 | 识别与展示要求 |
| --- | --- |
| 官网 | 依据源码上下文识别所指的网站，保留原始链接；分类不代表已经核验其官方身份。 |
| X | 收集源码中的 X / Twitter 链接，保留具体账号、帖子等完整路径。 |
| Telegram | 收集群组、频道或其他 Telegram 链接，按实际出现内容保存。 |
| 项目文档 | 收集文档站、白皮书或说明资料链接，不要求与官网域名相同。 |
| GitHub | 收集相关组织、仓库或具体文件等链接，保留具体路径。 |
| 公开审计报告 | 依据源码说明识别报告或审计页面链接；有链接不等于已取得、审阅报告或确认当前合约通过审计。 |
| 其他链接 | 保留无法进一步分类的链接及上下文；依赖库文档、许可证等第三方资料按实际用途标注，不冒充当前项目的官网或项目仓库。 |

### 多链接保存与来源展示

一份源码可以关联多条公开资料，同一类别也可以有多条，不设计成每类仅一个链接。按完整 URL 去重，相同链接在多处出现时合并展示并保留全部出处；同域名下的不同路径、查询参数或片段不能仅凭域名相同就合并。AI 只能提取实际出现的链接，不根据项目名称推测网址，也不将裸域名、账号名或 `http://` 链接自动补写为 HTTPS。其他协议的采集范围后续明确。

每条资料保存完整链接、资料类别、与项目的关系或用途说明、实际源码记录引用，以及文件名、可定位的位置或源码片段等提取依据。统一记录资料来源为“合约源码”，并保留提取时间；该时间不表示链接的发布时间或验证时间。

当这些资料展示在 UI 时，每条链接明确标注 **“来源：合约源码”**，并保留查看源码出处的能力。复用结果时仍关联原提取源码及其出处；不将源码复用描述为当前项目官网已经确认。具体页面布局后续设计，本轮不实现 UI。

### 同源码复用与研究边界

通过 `code_hash` 定位实际源码记录，同一份源码已有完成结果时直接复用，无需因新增项目地址重复调用 AI；缺失结果且已取得源码时才分析。结果绑定实际源码内容及出处，不能仅凭运行时字节码相同，就把另一份不同源码注释中的链接当作本次源码提取结果。

成功分析未发现链接时，保存“源码中未发现公开资料链接”；无源码或技术失败时保留未提取的实际原因，不把请求失败记为已确认没有链接。本项结果不依赖 owner、税率、持币或钱包研究完成，也不作为其他研究资料采集的前提。

公开资料链接只收集、分类和展示，不核验可访问性、官方归属、链接内容或审计结论，不跟随链接扩大代理或外部依赖分析，也不新增项目评分和过滤条件。没有链接不代表项目没有公开资料。后续程序风险过滤独立设计，首次 Swap 后不继续研究；公开链接不直接作为风险规则。

提示词、输出格式、链接解析细节、去重与并发协调、存储和接口结构仍待细化。本轮仅更新目标设计，尚未实现提取或展示功能。

## 已明确移除的黑名单设计（待删除、尚未实施）

目标设计不再保留系统自有的合约代码黑名单和钱包黑名单，也不将这两类黑名单命中作为项目筛选、关注或买入条件。

| 移除对象 | 当前实现与后续安排 |
| --- | --- |
| 合约代码黑名单 | 当前以合约链上字节码的 `code_hash` 记录黑名单；后续删除该黑名单能力 |
| 钱包黑名单 | 当前以钱包地址记录黑名单；后续删除该黑名单能力 |

后续代码重构时，一并清理两类黑名单对应的数据模型与存储、管理接口、前端页面与导航、接口权限映射和命中检查方法。合约源码、代码哈希及关联钱包仍按前述范围用于项目研究；删除黑名单不扩大其他研究数据的删除范围。

当前两类黑名单的存储和管理能力仍然存在，发现、采集和画像构建流程未调用其命中检查。本轮只记录已确认的移除决定，不删除代码或数据；实际清理前仍需完成并确认相应技术设计，实现时将关联设计同步为 `已实现`。现状入口见 [黑名单模型](../../../internal/token/policy/model.go)、[黑名单仓储](../../../internal/token/adapters/postgres/blocklist_store.go) 和 [Token 模块访问控制](../../design/token-intelligence/access-control.md)。

## 已明确的交易监控覆盖方向（待设计、尚未实现）

第二板块需要扩大底池覆盖范围，支持更多协议、报价资产和底池类型。当前实现只围绕 Ethereum 的 Uniswap V2、BSC 的 PancakeSwap V2，以及目标 Token 与 WETH/WBNB、USDT 组成的交易对采集底池信息；这些现状不作为新设计的固定限制。现状说明见 [ATHENA 聚合查询](../../design/token-intelligence/athena-contract.md)。

| 扩展方向 | 目标要求 |
| --- | --- |
| DEX 与协议 | 能够纳入其他 DEX 和交易协议，不将现有两个协议或固定 Factory 作为覆盖边界 |
| 报价资产 | 能够研究和监控与其他报价资产组成的底池，不将 WETH/WBNB、USDT 作为唯一允许的报价资产 |
| 底池类型 | 根据不同协议的池结构和交易机制识别流动性与交易条件，不要求所有协议都符合现有 V2 交易对模型 |
| 同一项目的多个底池 | 允许识别同一项目在不同协议、报价资产和池类型下的多个底池，不预设每个项目只有两个固定底池 |

底池深度和交易执行条件由第二板块承担；第一板块保留首次 Swap 匹配所需池身份与币种映射。第一板块继续从 `transaction.To() == nil` 的顶层创建交易发现项目，并按既定范围研究合约与相关钱包，不研究池深、流动性估值或 LP 风险。

扩大覆盖是已明确的设计方向，当前链仅 ETH，具体协议、报价资产与池类型清单、接入优先级、底池识别方式、多池选择及交易执行规则后续确定。文档不将扩展方向表述为已经支持所有链上协议，也不在本轮固定技术方案或修改代码。

| 源码公开资料链接 | 已明确 AI 从源码提取多条公开资料，重点 HTTPS 链接，支持官网、X、Telegram、项目文档、GitHub、公开审计报告等分类；完整 URL 去重保留出处，同一源码复用已完成结果，UI 标注“来源：合约源码”。只提取展示，不抓取或核验外部页面，不新增过滤；提示词、输出格式、解析细节、存储与展示结构后续设计 |
| 研究截止识别 | ETH 项目首次实际 Swap 结束研究；已确认按链共享监控、实时接收后固定 `H` 并补查 `B..H`、持久覆盖恢复、日志去重与链上顺序判断。可信 Swap 先立即停止研究，再补齐更早缺口并更新最早证据。协议事件目录、池与币种适配仍待实现，首批支持列表需选择；研究截止不等于实际可以买入 |
| 买入条件 | 研究结论以外还需要检查哪些条件，何时允许执行，以及条件不满足后的处理方式 |
| 研究与开盘的先后关系 | 首次 Swap 即停止研究，未交接项目放弃本轮参与；已交接项目的交易行为仍由第二板块决定 |
| 监控与时效 | 第一板块已明确 Approval/Transfer 与 Swap 的动态目标、实时订阅和历史补查连续性；具体地址分片、资源限流、组件与持久化边界，以及第二板块发现和买入响应的时间目标仍待设计 |
| 交易执行 | 使用的钱包、执行方式、额度、滑点、手续费、路由、授权与异常处理规则 |
| 买入之后的范围 | 是否包括持仓跟踪、卖出和退出策略，以及这些职责如何组织 |

当前业务主线覆盖到首次买入；持仓和卖出的范围尚未确定。除上述已明确的发现范围与扫描调度、Token 识别条件与逐项诊断要求、阶段采集安排、研究筛选目的与结果记录要求、后续研究需求、黑名单移除决定和交易监控覆盖方向外，本轮不自行设定其他规则阈值、技术选型、数据库结构、接口契约或状态枚举。

## 与当前实现及研究资料的关系

当前 Token 代码主要实现按区块发现项目、创建六类一次性采集任务，并在任务全部结束后尝试构建唯一的不可变画像。当前 `ChainProcessor.RunOnce` 仍在单链内执行“获取一块、处理并保存一块、再获取下一块”的串行循环，并一次处理到本轮启动时查询到的最新高度，尚未实现每轮最多 100 块的并行预取流水线。当前 ATHENA 合约已有接收地址数组的批量判断入口，传入单个地址也能取得单个结果；目标方案还需在技术设计中明确单个与批量调用形态，并补齐合约内部代码检查和逐项诊断返回。该流程提供现状背景，尚未实现本文描述的完整两板块业务主线。现有 Ave Token Detail 采集已经读取 `holders`，但仍处于更宽的市场数据采集与画像流程中，尚未接入 Top100 Holders，也没有形成本文要求的独立持币总数与 Top 100 资料。前述基础信息与底池采集拆分、AI 质检报告与程序评级分工、首次 Swap 截止、AI 确定 owner 与税费接收钱包及税率读取方式、从源码提取公开资料链接、Ave 持币资料收敛、不研究池深或 LP 风险但识别首次 Swap、模拟结果非必采及不采集 Ave 其他市场、池或风险标签的目标安排也尚未实现。相关说明见：

- [Token 链扫描与项目初始化](../../design/token-intelligence/chain-processor.md)。
- [Token 六源采集与项目画像](../../design/token-intelligence/collection-profile.md)。
- [Token 项目查询模型](../../design/token-intelligence/project-read-model.md)。

六类数据源、一次性采集、不可变画像以及现有组件边界均不作为新方案的固定约束。相关需求确认后，应依据业务要求在[后端技术设计](../../design/README.md)中决定保留、替换或重新组织哪些能力；技术设计确认且另行派发实现后才能修改源码。

## 第三方发现方案调研备忘（本阶段未采用）

以下记录截至 2026 年 9 月 6 日的官方公开资料，供以后重新评估时参考，不是接入计划或当前开发依赖。价格、权限和数据覆盖可能调整，尚未实际调用接口核验完整性、延迟与账单消耗。

### Bitquery

Bitquery 的 EVM `Calls` 数据可按区块号与合约创建条件查询创建记录，包括内部创建路径，可作为未来扩展发现范围的候选来源。能力说明见 [合约创建查询](https://docs.bitquery.io/docs/blockchain/Ethereum/calls/contract-creation/) 与 [Calls 数据说明](https://docs.bitquery.io/docs/schema/evm/calls/)。

API 积分是调用查询时消耗的额度。根据 [积分规则](https://docs.bitquery.io/docs/ide/points/#how-are-points-calculated-for-the-realtime-dataset)，使用 `dataset: realtime` 时，每次查询每个数据集合（cube）消耗 5 积分，与返回记录数量无关；同一请求涉及多个数据集合时分别计费。只查询一次 `Calls` 按 5 积分计算，不能将所有 HTTP 请求一概视为 5 积分。

| 套餐 | 月付价格（美元） | 每月 API 积分 | 单次只查一个实时数据集合时的查询次数 |
| --- | --- | --- | --- |
| Personal | $49 | 10 万 | 约 2 万次 |
| Pro | $99 | 100 万 | 约 20 万次 |
| Scale | $299 | 500 万 | 约 100 万次 |

例如，1,000 个区块各发起一次仅查询 `Calls` 的实时请求，预计消耗 5,000 积分。分页、重复轮询和额外的数据查询增加用量；历史查询不直接套用这项实时计费规则。积分按付款日期对应的账期刷新，且与每分钟请求数、并发数限制独立。详见 [套餐与账期说明](https://docs.bitquery.io/docs/ide/paid/)。

Personal 仅限个人非商业用途；按区块主动查询可从商用 Pro 评估。若需要 Calls / Traces 的持续推送，则应评估 Scale，其订阅时长和推送数据量单独计量。完整历史数据不包含在基础套餐中，需要核实具体数据集合的历史范围及购买方式。详见 [官方定价](https://bitquery.io/pricing)。

### Allium

Allium 的 [Ethereum contracts 表](https://docs.allium.so/historical-data/supported-blockchains/evm/ethereum/raw/contracts) 来源于 `CREATE` / `CREATE2` 创建记录，包含 `block_number`，可供按区块查询。Explorer 属于历史分析产品；[产品比较](https://docs.allium.so/product-comparison)给出的通用数据新鲜度约为 1 小时，不能直接视为秒级发现新合约的能力，具体合约表延迟和实时产品覆盖仍需确认。

官网列出 [通用付费入口 $200/月起](https://www.allium.so/use-case/product-engineering)，但未承诺该价格包含所需 contracts SQL 权限和额度；[常规生产套餐](https://www.allium.so/compare/allium-vs-zerion)中的 Explorer SQL 与实时数据服务需具体报价。

另有 [Machine Payments 按次付费方式](https://docs.allium.so/ai/machine-payments/endpoints-pricing)：提交 SQL 为 $0.01/次，查询状态为 $0.01/次，获取结果为动态计费。因此 $0.01 不是一次完整查询的总成本；该价格表中状态与结果接口仍要求 API key，具体表权限也需确认，不能只凭提交价格确定可用性和总预算。
