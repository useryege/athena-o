## 业务目标

本文设计 Token 的项目发现与研究第一板块：发现区块链上的新代币项目，从合约部署后开始采集、解析、保存和展示能够取得的事实，让用户基于事实继续规划后续规则。

Token 领域另设独立的[钱包交易与战绩](wallet-trading-performance.md)，以用户输入的钱包地址为起点，查询 Ethereum 主网的代币交易记录与战绩。用户已选择接入 Nansen API，采用供应商的交易和统计结果，不再自研本功能的日志解析、成本与盈亏引擎；接入细则尚在讨论，尚未实现。此决定不改变本文项目发现与研究的 Etherscan、日志、资产估值及关联钱包采集边界。

本阶段不由 AI 或程序给出风险等级、值得关注、通过／不通过、排除、移交或买入结论，也不把资料缺失解释为项目不合格。第二板块的筛选、交易监控与执行，以及未来移交后的撤回能力，均留待第一板块事实足够后另行讨论；本文不提前定义。

## 已明确的实施顺序与前端范围

### 旧版归档、清理与新版开发

**执行顺序已确认，2026-09-16；尚未执行。** 后续启动 Token 重构开发时，按以下三步推进。本次只编排需求，不执行代码归档、删除或新版开发。

1. **归档旧版。** 确认需要保留的旧 Token 代码已经提交，固定提交并打 Git 标签，记录提交号和标签，作为后续查阅、比较和取用代码的稳定依据。归档版本保留旧实现，不随新版开发改写。
2. **清理旧实现。** 从实际目标开发分支创建独立清理分支，以独立提交完整移除旧 Token 业务实现及其专属接口、后台任务、构建与部署配置、生成入口和失效引用。按实际依赖核对清理范围，验证其他模块仍能构建和运行，通过后合回目标开发分支，并记录清理提交及合入后的基线。清理完成至新版接入期间，旧 Token 采集与 API 不再提供服务。
3. **开发新版。** 从清理合入后的基线创建新的重构分支，记录分支与起点提交，按当前有效需求和目标设计继续完成 Token 设计与实现。已有确认决定继续有效，补齐剩余设计，不因删除旧代码而重新确认相同决定；新版设计与实现的内部顺序见下节。

需要参考旧实现时，可为归档版本另建独立目录（Git worktree），与新版并排查阅，按需取用已经验证且符合新设计的实现细节。旧数据模型、任务划分和接口不能反向限定新版架构。

有效需求、目标设计和仍有价值的研究资料保留；实际清理时，将旧实现说明及源码引用改为指向归档版本，并同步其实现状态，避免删除后仍将旧能力描述为当前可用。代码归档只保留已提交文件，运行数据库、历史数据和数据卷的处置另行明确，不随本次代码清理安排自动删除。

### 新版设计与实现顺序

第三步继续采用“设计后端 → 设计前端 → 实现后端 → 实现前端”的顺序。后端方案形成后，在后端编码前完成前端页面结构、用户操作、状态展示和数据需求设计，并据此核对、调整后端 API、数据契约及权限。前后端方案对齐并按 Superpowers 完成设计审阅后，先实现后端，再实现前端。

### 旧业务 UI 清理现状与保留边界

原有 Token 项目、源码、黑名单、节点状态、链处理及采集任务页面，以及它们的路由、前端服务、专用组件、样式和资源已移除；文中研究资料的展示要求作为前端设计依据，不要求恢复原有页面。

成员端保留 `Token & Risk` 分组。`Token` 父菜单保留原名称、图标及 Token 读取权限可见性，显示为禁用项，无子菜单、跳转路径或占位页面；独立的 `Wallets` 保留。桌面侧栏与移动端抽屉采用相同结构，访问 `/token` 或 `/token/*` 使用现有通用 404 页面。成员端默认首页继续为 Active 账户的个人资料页或 Pending 账户的权限页，不再将 Token 作为获得权限后的自动跳转目标。

管理员权限编辑器及账户中心不展示或编辑 Token 权限项，相应展示统计也排除 Token。完整九项权限模型、后端鉴权及已有 Token 授权继续保留；编辑其他权限时必须保留原有 Token 值，不得遗漏或重置。仅持有 Token 授权的账户仍按原规则判定为 Active。

此前旧 UI 清理保留了 Token HTTP/gRPC 接口、采集服务、数据库、API 文档及管理员通用服务状态中的 Token API 健康信息；这是第二步执行前的现状。第二步按上述范围移除旧 Token 专属实现，并同步清理已移除接口的文档及健康查询接入。Token 板块标识、上述菜单与账户权限边界、通用服务状态框架、共享 Etherscan Manager／Gateway、独立 Wallets、Worm Trading 和账户 API Key 功能继续保留。后续业务逻辑开发按 [Superpowers 工作流](../../developer-guide/superpowers-development.md)推进，本文提供长期业务背景、已明确决定和尚未解决的问题。

## 已明确的开发阶段发现范围

当前开发阶段只开发和使用 Ethereum Mainnet（chain ID `1`），不启动其他链的 Token 业务。源码、普通交易及按地址内部交易查询继续使用现有免费 Etherscan Key；以后扩展其他链时，用户会将现有免费 Key 全部更换为付费 Key，届时再核对目标链与接口权限。持币地址总数与前 100 名明细改由 Ave 获取，不再预留 Etherscan PRO Key 或完整分页持币名单。

当前开发阶段仅关注区块内满足 `transaction.To() == nil` 的顶层合约创建交易，使用交易发送者和 nonce 推导候选合约地址。该范围沿用当前扫描入口，便于先推进第一板块的事实研究。

- 工厂合约内部通过 `CREATE` 或 `CREATE2` 创建的合约暂不纳入发现范围；即使内部创建发生在顶层部署交易中，也只跟踪顶层候选合约。
- 项目发现暂不接入 Bitquery 或 Allium，也不在本阶段增加内部调用追踪或工厂事件扫描来扩展创建路径覆盖。
- `transaction.To() == nil` 只用于确定部署候选，不代表候选一定是代币。发现地址后，由聚合合约内部先检查代码是否存在，再按下文已明确的条件识别 Token；不设置独立的部署结果确认环节，也不通过交易回执判断交易是否成功。通过后进入事实研究，不执行项目筛选。

因此，本阶段的发现结果不代表区块内创建的全部合约。内部创建路径的扩展可在后续重新讨论，不作为当前开发的前置条件。首版链范围已限定为 ETH。首版七协议的 Swap 事件覆盖用于研究停止识别；不以项目已存在池子作为顶层发现或启动研究的前提。

## 已明确的单链实例运行方式

同一职责使用同一套代码和同一个构建产物，每个链任务实例通过启动配置选择唯一的 `chain_id`。ETH 与 BSC 分别运行、独立启停和恢复；首版只运行 ETH（`1`），以后扩展 BSC（`56`）时使用同一程序增加实例。运行 ETH 不要求填写 BSC 配置，扩链仍遵守前述付费 Key 要求。

- 区块扫描与共享项目事件监控仅处理实例所属链；目标 Token 日志、部署者／当前 owner 主动交易与首次已识别 Swap 的实时接收、补查进度、覆盖版本、池与代币映射均有明确链范围。
- 外部采集器按实例所属链领取和处理源码、钱包历史、链上状态及持币任务；资料汇总和 AI 静态分析可以共享运行，不要求全部研究步骤合并进扫描进程。
- 项目、钱包、任务、扫描与日志进度共用数据库，按链区分身份和来源；相同非空源码及已完成分析继续按 `code_hash` 跨实例复用，实际链上地址和值逐合约读取，查询 API 保持统一。
- 实例只加载、校验和连接自己负责链所需的配置，分别提供健康状态、日志和指标。系统链启用状态与实例负责链分开，启动或停止某个实例不得覆盖其他链的启用状态、运行状态或进度。
- 每块完成 Token 识别并可靠保存结果、项目资料和研究任务后推进，源码、AI 及五层钱包继续在后台独立执行。拆分不改变扫描调度、三类研究停止及首版不处理区块替换的规则。

详细边界、运行关系图和当前启动逻辑需要调整的部分见 [单链实例运行设计](token-chain-runtime.md)。本节属于已确认目标，具体启动参数与部署配置尚未实现；共享数据库和 API Key 的容量限制仍需统一管理。

## 已明确的区块扫描调度（目标规则、尚未实现）

扫描采用主动查询最新区块的有界流水线。每轮固定最多 100 个区块的范围，在范围内并行预取区块数据到有界内存缓冲，同时按高度严格串行处理、保存和推进游标。下一应处理区块一旦取得就开始处理，不等待整批预取完成。轮末重新查询最新高度；追平后等待 1 秒再查询。历史补扫和新区块扫描沿用同一条连续扫描流水线。

### 启动与扫描进度

- 数据库已有该链的扫描进度时，从已保存位置继续，不重新按三天回看窗口初始化。
- 数据库没有该链的扫描进度时，读取当前最新区块，定位向前回看三天所对应的起始区块，从该区块开始扫描。三天是时间范围，不固定换算成某个区块数量；定位方式见发现与生命周期目标设计。
- 本文将扫描游标 `C` 定义为最后一个已成功处理并保存进度的区块高度，下一块为 `C + 1`。首次确定起始区块后，将初始扫描位置设为该区块之前，以包含起始区块。
- 每个区块成功处理后保存进度；没有部署候选的区块也需要记录扫描完成。每轮 100 块是调度上限，不是要求整批完成后才保存进度。

### 每轮执行规则

1. 查询本轮最新区块高度 `H`。
2. 若 `H > C`，确定本轮范围为 `C + 1` 到 `min(C + 100, H)`，两端均包含；本轮上限确定后不随新块产生而延长。
3. 对本轮范围并行预取区块数据，完成一块即按高度放入有界内存缓冲，允许乱序到达。处理端只等待当前应处理的 `C + 1`；该块取得后立即开始处理，不等待整批预取完成。本轮最多 100 块是范围和缓冲上界，不表示必须同时发出 100 个节点请求；实际并行数、限流与背压见关联目标技术设计。
4. Token 识别、结果/项目/研究任务保存和游标推进按区块高度严格串行。成功处理一块后立即保存该块进度、释放对应内存数据，再处理下一块；没有部署候选的区块也需保存完成进度。
5. 某个区块获取失败时，本轮其他区块仍可继续预取并缓冲；但处理和游标停在最早未取得的高度。区块获取、处理或保存的每次失败都通过通知组件通知管理员，并持续重试对应区块，不设次数上限。后续区块即使已在内存中，也不得越过失败块进行处理或推进为已完成。
6. 本轮全部区块成功处理后立即回到第 1 步，重新查询最新高度，再计算下一轮范围；仍有积压时不额外等待 1 秒。
7. 若 `H == C`，说明按当前高度已追平，等待 1 秒后回到第 1 步。等待应允许程序停止时退出。
8. 若 `H < C`，进入异常分支，保留已保存的扫描进度，通过通知组件向管理员发送异常通知，交由管理员人工处理。该分支不按正常追平处理，也不自动回退或重新初始化扫描进度。

例如，已成功处理到 1800，最新高度为 2000，下一轮范围为 **1801–1900，共 100 块**。预取端并行获取这些区块；1801 一旦到达，处理端立即按 1801、1802……1900 的顺序逐块识别和保存，不等待其余区块全部到达。完成 1900 后重新查询最新高度，再从 1901 继续。若 1805 获取失败，1806–1900 可继续预取，但处理和游标在 1804 之后等待 1805，直到它成功。若游标为 1900 且最新高度为 1950，则这一轮范围只有 1901–1950，共 50 块。已处理到 2100 且最新高度也为 2100 时，等待 1 秒后重新查询。

图示见 [Token 区块扫描流程](token-block-scan-flow.md)，包含启动、批次、进度保存、追平等待、失败通知与无限重试，以及 `H < C` 人工处理分支。

本节确定正常扫描的启动、预取、顺序处理、批次和等待规则；不采用新区块订阅作为扫描触发方式，也不增加实时优先与历史补扫的独立处理流程。预取可并行、完成可乱序，但单块处理和提交顺序不变：单块完成需完成候选 Token 识别并可靠保存识别结果、项目资料和研究任务；后续源码、AI 及五层钱包研究不阻塞扫描。

区块获取、处理或保存失败的每一次尝试都产生一次管理员通知，不因同一区块或同类错误重复发生而去重、合并或抑制，也不设置只通知首次失败的规则。每轮最多 100 个区块限制的是本轮预取和处理范围，不限制同一区块的重试次数；预取可继续向后进行，但失败块成功后才继续串行处理本轮的下一块。重试间隔及通知提交失败时的处理方式后续细化。

预取缓冲仅是运行时加速手段，不构成扫描进度。进程停止或重启时可直接丢弃尚未处理的内存数据，并从数据库已保存的 `C + 1` 重新预取；只有区块的识别结果、项目资料、研究任务和扫描游标可靠保存后，该块才算已完成。

区块处理失败后的持续通知与重试，以及 `H < C` 时通知管理员人工处理，均复用仓库的 [系统通知组件](../../design/notifications/system-notification-operations.md)。每次真实扫描失败分别形成可靠保存的通知记录，异步交入通知组件；同一次通知的传输重试不能制造新的真实失败记录，也不能合并不同失败。扫描的通知责任以可靠交入该组件为界，最终投递沿用组件已有机制；通知服务短暂不可用不阻止对应区块重试。`H < C` 的人工处理分支独立于区块失败重试循环；该分支的通知、暂停与管理员处理后核验恢复见发现与生命周期目标设计。具体告警内容、通知接入方式与接收配置在关联目标技术设计中说明。

当前明确不考虑区块被替换或链重组，不设计自动回滚、重组修复或因区块替换恢复研究。`H < C` 的既有异常通知与人工处理保留。区块处理采用已选择的 A 边界：完成该块 Token 识别并可靠保存结果、项目资料与研究任务后推进；源码、AI和五层研究独立后台执行，见 [扫描与研究衔接](token-block-scan-flow.md#已确认的扫描与研究衔接)。本轮只更新目标文档，尚未接入异常通知或修改扫描代码，现状见 [Token 链扫描与项目初始化](../../design/token-intelligence/chain-processor.md)。

## 已明确的 Token 识别与逐项诊断

图示见 [Token 候选发现与识别流程](token-discovery-identification-flow.md)，从顶层创建交易推导地址开始，展示单个与批量判断能力、区块批量识别、代码检查、六项检测、识别结论与原因的持久保存。

### 聚合合约同时支持单个与批量判断

聚合合约必须同时支持单个候选合约判断和多个候选合约批量判断，两种调用形态共享完全相同的代码检查、六项检测、结论与逐项诊断语义。这里确认的是能力和行为；具体 Solidity ABI 方法数量、方法名及返回结构见关联目标技术设计。

区块扫描处理当前区块时，先汇总该区块全部顶层部署候选，再统一使用批量判断形态，不在 Go 中逐个调用单个判断。即使区块只有一个候选也沿用批量路径；没有候选则跳过判断。一次批量输入只属于同一条链、同一个区块，结果与输入一一对应并保持顺序。单个候选不通过只影响自己的识别结论，不中断其他候选；只有节点请求或整个聚合调用失败才使当前区块进入失败重试。

单次批量最大候选数和超限后的拆分方式由技术设计确定；需要拆分时仍使用批量判断形态，并在当前区块全部候选完成识别、结果可靠保存后才推进游标。单个判断能力供区块扫描以外需要判断一个指定合约的调用场景使用，具体调用入口后续确定。

### 合约内部先检查目标地址代码（待实现）

Token 识别入口在聚合合约内部先检查目标地址的 `code.length`：

- `code.length == 0`：直接判定为 **不是 Token**，返回并保存原因“地址无合约代码”，不继续执行后续六项调用。
- `code.length > 0`：继续执行下述现有筛选条件。

不单独检查部署交易是否成功，也不把交易回执的 `status` 作为识别前置条件。诊断原因记录查询时的实际事实“地址无合约代码”，不将其直接推断为原始部署交易失败。回执中的转账日志仍可作为初始接收钱包等研究资料的来源，具体研究采集范围按相关章节设计。

### 保留现有六项检测条件

Token 识别保留当前全部筛选条件，不放宽元数据、精度或供应量要求，也不以其他识别建议替换现有规则。以下五组业务条件对应六个独立调用。

**识别结论只有两种：是 Token、不是 Token。** 目标地址有代码且六项全部通过时判定为 Token；目标地址无代码或任意一项未通过时判定为不是 Token，并返回对应原因。不设置“暂时无法判断”“待进一步识别”等第三种识别结果。

| 检测项 | 通过条件 |
| --- | --- |
| `name()` | 能读取且非空 |
| `symbol()` | 能读取且非空 |
| `decimals()` | 能读取且大于 0 |
| `totalSupply()` | 能读取且大于 0 |
| `balanceOf(零地址)` | 能正常返回并按现有要求解码；允许返回 0 |
| `allowance(零地址, 零地址)` | 能正常返回并按现有要求解码；允许返回 0 |

读取和解码要求沿用 [当前 Token 探测逻辑](../../../pkg/abi/ATHENA/ATHENA.sol) 的 `_getToken` 及相关 `_safe*` 方法。名称或符号为空、精度或总供应量为 0，均按现有规则判定该项不通过；余额和授权额度不增加大于 0 的要求。这一步只记录 Token 身份事实，不判断是否值得关注。

每次 Token 识别使用开始执行该次识别时可取得的最新区块状态，并保存实际观察区块号与区块时间。批量调用或因上限拆分的调用都必须记录各自实际观察点；具体如何固定 RPC block tag 在技术设计中确定，不能把候选部署区块状态或未记录的隐含 `latest` 冒充观察时点。

六项业务检测不通过属于最终“不是 Token”结论，不自动重试，也不提供人工重新识别入口。只有节点、聚合调用或结果保存等技术失败才阻塞当前区块并按区块规则重试。项目进入研究后对 Token 当前状态的刷新只更新事实快照，不能改写最初的 Token 识别结论。

### 返回并保存逐项检测结果（待实现）

本次新增要求是在“是 Token / 不是 Token”的整体识别结论之外，让调用方能够明确知道哪些检测未通过。识别结论、未通过的检测项及对应原因必须随结果返回，并关联到对应链和合约持久保存，供后续人工查询排查。判定为不是 Token 的合约也要保留这份记录，不能仅返回原因或输出日志后丢弃。

- 记录合约内部的代码存在检查结果；目标地址无代码时返回不是 Token 及“地址无合约代码”的原因，不把未执行的六项调用伪造为已经检测失败。
- 目标地址有代码时，分别返回六个调用对应的检测结果；`name` 与 `symbol` 各自记录，不合并成一个无法定位的失败项。
- 对未通过项说明原因，区分调用失败、返回数据无法解码，以及成功读取但值不满足条件。这些情况均判定对应检测项未通过，整体为不是 Token。例如，`balanceOf(零地址)` 调用失败和 `decimals()` 返回 0 是不同原因。
- 单项不通过时，继续完成其余可执行检测，并列出所有已发现的未通过项，避免只保留第一个失败原因。
- 已取得的返回值可作为诊断依据；底层失败原因只能记录实际取得的信息，不能把“调用失败”直接断言为“方法不存在”。
- 若节点请求或外层聚合调用整体失败，按实际情况记录执行错误，不伪造逐项检测结果，也不新增第三种 Token 识别结论。此类外层执行错误按区块失败规则通知并重试，不推进当前区块；目标合约的单项检测不通过仍作为业务识别结果保存。

以下为目标地址有代码时的诊断内容示意，不定义实际返回字段或错误码：

| 检测项 | 检测结果 | 排查信息 |
| --- | --- | --- |
| `name()` | 通过 | 返回非空名称 |
| `symbol()` | 通过 | 返回非空符号 |
| `decimals()` | 不通过 | 调用成功，返回 0，不满足大于 0 的条件 |
| `totalSupply()` | 通过 | 返回值大于 0 |
| `balanceOf(零地址)` | 不通过 | 调用失败，未取得余额结果 |
| `allowance(零地址, 零地址)` | 通过 | 正常返回 0 |

该示例的整体识别结论为 **不是 Token**，未通过项为 `decimals()` 和 `balanceOf(零地址)`，两项原因均应返回并保存，后续人工能够按对应合约查到该结论和原因。具体诊断、存储、查询和资源边界见发现与生命周期目标设计。本轮只记录目标要求；当前 Token 识别条件继续保留，逐项诊断能力尚未实现。

本节针对合约部署后的早期项目发现与事实研究。第一板块不研究池深、流动性估值或 LP 风险，不要求通过底池状态证明项目尚未添加流动性；为识别首版覆盖内的首次已识别 Swap，允许取得必要的池身份与代币映射；为 L1 固定资产 USDT 估值，允许读取管理员指定可信路径中的必要池现货状态。添加流动性不停止研究。以下为已确定的目标安排，尚未修改当前六源采集代码。

### 链上状态的拆分

链上状态是研究的重要依据，需要将现有 `chain_state` 中的代币基础信息与底池信息拆开，保留前者作为本阶段资料，通用底池研究由后续板块另行设计。本阶段仅为 Swap 匹配和 L1 固定资产估值取得各自必要的池资料。税率作为新增的独立研究资料，按源码确定的读取方式采集，不扩充 Token 识别的六项条件；具体采集任务和数据结构见研究运行时目标设计。

| 数据部分 | 内容 | 归属与采集时机 |
| --- | --- | --- |
| 代币基础信息 | 合约地址、ERC-20 探测结果、名称、符号、精度、总供应量、合约 `code.length`（链上运行时代码的字节数）及对应区块与时间 | 项目发现与研究阶段采集，不依赖项目已经建立交易池或添加流动性 |
| 合约税率 | 源码识别的税率类型与分项、读函数、当前返回值及换算依据 | 项目研究阶段按 AI 确定的方式读取当前合约，保存实际区块与时间，不作为 Token 识别条件 |
| 池资料边界 | Swap 所需池身份和币种映射，以及 L1 资产固定价格路径中的必要现货状态 | 不开展目标 Token 的池深、LP 供应与持有、锁定情况或流动性风险研究；L1 估值使用首版七协议可信部署中的固定路径，不自动搜索交易路径 |

代币基础信息、字节码信息、合约 owner、需要链上读取的税费接收地址、税率及钱包资产等链上状态，明确以各自采集时的最新区块作为数据源，保存实际读取的区块号及对应时间。不同采集不要求使用同一个区块；同一税率的相关读函数及动态分母固定使用该次税率采集区块；一次 L1 钱包资产快照中的六项余额、池状态及价格固定使用同一观察区块。同一数据时点已取得的信息可以复用，旧识别快照不能直接当作本次最新状态。部署资料仍保留实际部署区块，钱包历史仍采集部署前交易；Etherscan 源码查询记录查询时间与资料来源，不视为指定区块的源码快照。直接从源码提取的固定税费接收地址保留源码依据，不记成链上读取结果。

持币地址总数和 Top 100 明细来自 Ave 的两次独立查询，分别记录查询时间、接口来源与取得状态；接口未提供对应区块时，不填写推测区块，也不将总数、排名、数量和占比视为同一区块的一致快照。Top 100 是有界排名，不表示完整持币名单。该时点范围独立于部署区块及关联钱包部署前普通、内部各最多 300 条的历史窗口。

代币基础信息需要获取并保存目标代币合约地址在查询区块的 `code.length` 具体数值，以字节为单位，关联对应链、合约、区块与时间。该值描述目标地址上已部署的运行时代码长度，不是源码文本长度或部署交易输入长度。识别入口已有的 `code.length == 0` 检查继续保留；本次补充要求保存实际长度，不能只保留“有无代码”的判断。长度数据先作为基础事实采集，具体研究用途待用户后续明确，本轮不增加长度阈值、评分或筛选规则。该采集与保存要求尚未实现。

启动研究不以池子已经存在或已取得底池状态快照为前提。首次已识别 Swap 按首版协议取得必要的池身份与币种映射，不采集池深或 LP 风险；没有匹配到事件只表示当前协议版本与已完成覆盖中未识别到 Swap，不表示已证明项目无池或全市场没有交易。添加流动性不停止研究。

这里先确定数据职责与阶段边界，不预先确定拆分后的任务名称、服务数量、采集频率、接口或数据库结构。当前基础信息、池信息和模拟字段的实现背景见 [ATHENA 聚合查询](../../design/token-intelligence/athena-contract.md) 与 [现有采集数据定义](../../../internal/token/collection/payload.go)。

### 合约源码按字节码哈希复用

源码采集以目标合约的运行时字节码哈希 `code_hash` 查询数据库，不是对源码文本计算哈希。相同哈希已有非空源码时关联并复用；没有可复用源码时，使用当前合约所属链和地址调用 Etherscan。其他地址此前返回空源码不阻止当前地址查询，只有哈希记录也不代表已取得源码。

必须区分三类采集结果：

| 结果 | 处理 |
| --- | --- |
| 成功取得非空源码 | 保存源码、来源链与地址、查询时间及哈希关联，进入 AI 分析或复用已完成报告。 |
| 请求成功但源码为空 | 记录本次查询无源码、合约可能尚未开源；等待管理员手动补采，或由具有续期资格的目标 Token `Transfer`、部署者／当前 owner 主动交易触发再次查询。处理时仍在研究且仍无非空源码才发起或合并补采，不设置定时轮询。`Approval` 不触发源码重查。 |
| 请求失败 | 保存技术错误与次数，重试并通过系统通知组件通知管理员处理；不能标记为未开源，也不能当作正常空源码结果。 |

请求失败的既有次数口径先保留：首次请求之外最多再重试三次，总计最多四次；重试耗尽后通知管理员，保留请求失败状态及人工处理线索。请求成功返回空源码不消耗技术失败重试预算；它属于另一个需要再次查询的分支。重试间隔、通知提交失败时的处理和人工恢复入口待细化。研究停止后不再发起新的项目源码补采；排队但未开始的任务取消，已经开始的请求继续沿用原本的有限技术重试规则，完成后保存成功结果或最终失败。

图示见 [合约源码获取流程](token-contract-source-flow.md)。源码不可得不自动产生风险等级；未取得源码时的其他资料仍保留。源码后来取得后，可以补充共享源码与报告，不沿用别的未取得源码地址发起查询。

按 `code_hash` 定位的实际源码共享 AI 静态质检报告、owner 分析与读取方式、税费接收钱包分析、固定地址与读取方式、税率分析与解释方案，以及公开资料链接和出处。需要链上读取的 owner、税费接收地址与税率逐合约读取。复用源码不将新地址标记为在 Etherscan 独立完成源码验证，也不将不同初始化参数或链上状态视为相同；链接保留实际提取源码及出处，不宣称已经核实新项目的官方归属。

当前实现 `ContractSourceProcessor.Process` 在缓存记录 `Fetched` 为真时复用，包括空源码；当前采集任务在第三次失败时结束。这与目标中的空源码再次查询、请求失败独立记录及首次加三次重试存在差异，后续实现时调整。参考 [源码处理器](../../../internal/token/collection/application/processors.go)和[当前采集任务设计](../../design/token-intelligence/collection-profile.md)。

### AI 静态质检与报告复用（待实现）

AI 只阅读实际取得的源码并生成质检事实报告，不给出风险等级，也不判断项目是否通过或应被排除。报告保存后供有 Token 读取权限的成员查看。程序筛选属于未来阶段，本轮既不定义标准，也不创建风险结果。图示见 [合约源码静态质检流程](token-contract-review-flow.md)。

报告至少明确包含下列能力判断，并附对应源码位置、函数、权限、触发条件和影响：

| 必含检查项 | 源码分析要求 |
| --- | --- |
| 是否可以无限增发 | 说明增发入口、权限与供应量约束，是否存在可绕过或修改的上限。 |
| 是否可以修改余额 | 说明谁可以改变哪些地址的余额以及所需条件，区分正常转账记账与额外修改余额的能力。 |
| 是否可以限制转出 | 说明是否存在限制转出、禁止转账或针对地址施加转出限制的能力及条件。 |
| 是否可绕过持有人授权转账 | 检查特殊转账分支是否跳过授权、是否可替其他持有人设置授权，以及源码中存在的签名授权是否有可导致未经有效授权转账的缺陷。说明权限、实际路径、条件与影响；正常的本人转账、有效额度及有效签名授权不记为绕过。 |
| 是否在放弃 owner 后仍保留控制权 | 检查放弃所有权后仍能执行敏感操作的角色、硬编码地址、其他权限或权限恢复路径，给出具体操作及源码依据。没有放弃入口或无法判断时说明原因；不把 owner 清零等同于全部控制权消失，不声称已核实当前部署的放权状态或角色持有人。 |
| 是否使用代理 | 识别源码中的代理转发结构并保存依据，不读取或分析实际代理实现。 |
| 是否存在外部未知依赖 | 指出本次源码未提供或无法确定具体实现的外部逻辑；已完整提供的库或父合约不因 import 自动判为未知。 |

前五项是已明确的必查事实，其中“绕过持有人授权转账”和“放弃 owner 后仍保留控制权”已作为新增单项业务要求确认；本项确认不将整份需求推进为已确认。每项分别保存结论、入口、权限、触发条件、作用范围、可能影响和源码依据；不足以判断时保存原因，不直接等同于高风险规则。同一逻辑涉及多个维度时关联同一份依据，不虚构多个独立漏洞。具体检查边界见 [AI 静态审阅流程](token-contract-review-flow.md#首版范围)。正常业务输出始终是基于所提供源码的质检报告；AI 请求失败、超时或响应格式无效单独作为技术异常处理，不保存为报告，也不伪造否定结论。源码范围限制与触发条件在报告中说明，不宣称已经核实当前链上角色、开关或参数。

本阶段不接入静态分析工具、不执行合约、不读取链上状态核实报告，也不继续获取或分析代理实现或外部依赖。owner、税费接收钱包和税率的 AI 分析及 Go 读取属于独立研究资料流程，不是静态报告的完成前提。

同一份源码默认只生成一份共享报告，按 `code_hash` 匹配到其实际源码后直接复用，多个部署不重复调用 AI。默认按 AI 报告准确的前提使用，不增加自动复核或多模型评审。管理员可以针对某一份源码报告人工触发重新检测。成功后形成最新有效版本；失败保留上一个有效版本并记录最近失败。具体版本替换与并发读取机制在技术设计中确定。

管理员重新检测某份共享源码时，只更新该 `code_hash` 的共享事实报告，不重新启动任何已停止项目。所有关联项目（包括已停止项目）都展示该共享资料的最新有效版本；程序风险判断、筛选与交接不在当前阶段设计。

公开链接、owner、税费接收钱包、税率与静态报告分别复用已完成分析，不要求同一次 AI 调用或共同完成。并发去重、报告输出结构、提示词、Go 消费格式、技术重试和人工重检接口待细化，不改变已经确认的职责分工。

### 研究证据与完成条件

项目进入研究后保持“研究中”状态，直到出现以下任一停止原因：首版覆盖内的首次已识别 Swap、活动观察超时、管理员手动停止。资料是否齐全不改变停止判断；当前没有程序风险排除这一停止原因。研究状态和停止原因作为事实保存，不能覆盖最初的 Token 识别记录。

部署交易、部署者、代码哈希、初始接收钱包及分配线索等发现阶段已经取得的信息，应一并作为研究材料。目标设计的 L1 直接关联钱包包括部署者、最多 5 个初始接收钱包、取得的合约 owner 及一个或多个税费接收钱包，四类角色对应的地址均纳入普通与内部两类历史交易，以及六项资产余额、USDT 估值采集。初始接收钱包沿用部署交易内该代币的转账日志，按净接收量从高到低排序，在净接收量为正且查询时无合约代码的地址中最多选取 5 个。该上限仅针对初始接收钱包，不限制税费接收钱包数量；owner 和税费接收钱包也可为合约地址。相同地址保留多个角色标签并去重采集。后台按项目原生币金额门槛快照从 L1 自动发现 L2，再逐层查找 L3、L4、L5；交易所／跨链节点完成本层分析后停止向上追溯，不等待前端展开。

钱包历史保留 Etherscan 普通交易 `account/txlist` 的原有规则，并新增免费按地址内部交易查询：对每个去重钱包，两类分别取项目部署前最近最多 300 条原始记录。L1–L5 各层均使用下表范围，两类额度独立，不合并截成总共 300 条，不在过滤后翻页凑数。内部历史只用于部署前研究，不改变研究期活动续期规则。

| 查询项 | 已确认规则 |
| --- | --- |
| 起始区块 `startblock` | `0` |
| 截止区块 `endblock` | `项目部署区块 - 1`，不包含部署区块内及之后的交易 |
| 排序 `sort` | `desc`，从新到旧 |
| 页码 `page` | `1`，只取第一页，不继续翻页补充更早交易 |
| 每页数量 `offset` | 普通与内部两类各 `300`；分别保留实际数量、无记录、采样上限和失败状态 |

例如项目部署在第 `30000` 区块，则 L1–L5 查询范围均固定为 `0–29999`，每钱包普通与内部各取倒序第一页最多 300 条。即使采集时区块已推进，或来源节点之后才发现，截止仍为 `29999`。先取得原始样本再判断状态、金额和用途；零额、低额和失败记录不通过过滤后补采替换。内部记录关联的新增顶层交易与普通交易去重后共同参与行为分析，可补充必要回执和日志，但不扩大两类采样入口，不宣称完整钱包、代币事件或调用轨迹。

这些交易用于整理并展示各层钱包直接部署过的合约、交易或交互过的项目，以及多层资金来源和地址间的交易联系。钱包资料当前只采集、解析和展示，不据此筛选或排除项目。层级范围、资金来源定义和分析内容按下节执行；具体行为证据和未分类边界见钱包目标设计。

当前代码只实现普通交易的上述区块范围、排序、页码及数量规则，本轮原样保留；按地址内部历史采样、发起人归因及扩展行为样本均尚未实现。当前钱包范围仍只覆盖部署者和最多 10 个初始接收钱包；初始接收钱包缩减为最多 5 个、owner 与税费接收钱包的获取及纳入采集、L2–L5 来源发现、多层历史分析与资金来源图均待实现。详见 [钱包历史交易现状](../../design/token-intelligence/wallet-normal-transactions.md)及对应的[截止区块计算](../../../internal/token/collection/application/processors.go)与[Etherscan 查询参数](../../../internal/token/adapters/normaltransactions/provider.go)。

现有 `simulation_result` 是六项独立的 `transfer` / `transferFrom` 调用成功探测，不是完整的买入、卖出模拟。第一版将该数据源整体移除，不创建任务、不采集、不展示，也不保留为手动或按需选项。未来如需买卖可执行性检查，由后续板块重新定义目标和方式。现状依据见 [当前模拟调用](../../../internal/token/adapters/evm/project_state_reader.go)。

研究阶段不再以现有采集任务全部结束作为完成条件。项目停止时，尚未开始的研究与刷新任务直接取消；已经开始的任务继续执行原本的有限重试策略，直到成功或重试耗尽，再保存结果或最终失败。此前已经开始、正在等待重试的任务仍属在途任务，不因回到排队状态而变成未开始。停止后不得再启动新的下游任务；所有在途任务收尾后，项目专属事实冻结。未取得或只取得部分资料时记录实际状态和原因，不填充推测值。

按 `code_hash` 共享的源码静态资料不随单个项目冻结：质检报告、源码公开链接，以及 owner、税费接收地址和税率的静态分析／读取方案始终展示最新共享有效版本。共享资料因其他研究中项目或管理员重检而更新时，已停止项目也能看到新版，但不会据此重新启动该项目的链上读取、钱包、持币或其他专属采集。

## 已明确的多层关联钱包研究与资金来源图（尚未实现）

当前阶段的职责为“采集钱包数据 → 解析事实与关联关系 → 保存并展示”。多重角色标签、L1–L5 资金来源图、历史部署与交易项目清单、交易依据和 L1 资产余额与估值均用于查看，不设置基于这些钱包数据的风险评级、通过／不通过判断或项目排除逻辑。采集失败、结果为空或解析未完成按实际情况记录并展示，也不转为项目筛选结论；钱包数据驱动的筛选不属于当前第一板块。

独立图示见 [多层关联钱包研究流程](token-wallet-research-flow.md)、[内部 ETH 转账需求](token-wallet-internal-transfers-flow.md)与[钱包资金来源关系图](token-wallet-funding-graph.md)。L1 为部署者、最多 5 个初始接收钱包、已取得的 owner 及全部已取得的税费接收钱包；从 L1 交易样本发现资金来源形成 L2，再依次查找 L3、L4、L5。L5 对应从 L1 向上查找四轮来源；各层统一使用当前项目部署前普通与内部各最多 300 条原始记录的窗口，L5 仍开展历史行为分析，但不继续发现 L6。

当前持币地址属于独立分布资料。可按链和地址匹配已知的钱包角色及资金来源关系供展示，但不会仅因持币而自动成为 L1，也不自动触发该地址的两类历史、资金来源扩展或其他资产余额采集。已属于 L1–L5 的地址继续沿用其原有采集范围。

管理员按链配置原生币最小资金来源金额，项目开始时保存该配置快照；ETH 默认 `0.01 ETH`，未来 BSC 默认 `0.01 BNB`。项目内所有 L1–L5 节点固定使用该快照，后续链级配置变更不重算既有项目的资金边，也不改变其后续扩展门槛。

首版资金研究同时使用普通与内部样本，两类均须成功、未回滚、实际转入当前钱包、非零且单条金额达到项目门槛。普通交易由直接入账的实际发送方形成关系；内部 ETH 入账按下述规则确定上游。L1–L4 使用相同规则扩展，保留实际转出方、接收钱包、顶层发起人、关系类别、金额、区块、时间、可区分明细的交易依据、样本来源与门槛快照。每条独立判断，即使同一顶层交易内两条 `0.006 ETH` 也不累计跨过 `0.01 ETH`，不改用净额。低额和失败记录保留原始事实，失败、回滚和代币入账不形成成功资金关系；内部出账不自动扩展下游。样本不代表完整资金来源，历史金额门槛不影响研究期成功零 ETH 主动调用的续期资格。

内部入账采用**顶层发起人归因**：A 发起交易、C 实际转入 ETH 给 W 时，默认展示 A→W 并继续研究 A，C→W 流水保留为证据，C 不因中转占用层级。归因只表示研究口径，不证明 A 实际出资、控制 C 或 W。若 C 精确命中管理员交易所／跨链地址库，优先保留 C→W 并在 C 终止，完成 C 本层两类历史和行为分析，不再穿透 A；C 未命中但 A 命中时，对 A 应用终止规则。未取得 A 时保留缺失原因，不猜测归因或据此扩展；未触发 C 地址库优先终止例外且 W 自己发起并收到内部回款时，保留自身证据，不新增外部来源节点。具体优先级、去重和边界见[内部 ETH 转账需求](token-wallet-internal-transfers-flow.md)。

管理员按链维护交易所／跨链地址库，记录地址、类型、名称和依据。L1–L5 任一钱包精确命中后，保留标签、已有资金边和转账证据，仍完成本层普通与内部各最多 300 条历史及部署、代币交互分析，但不再从该节点发现上游来源。提供方标签可以作为独立资料展示，不自动替代管理员地址库的判断；终止追溯不代表排除项目或认定同一团队。

地址库新增标签时，研究中项目停止该节点后续上游扩展，保留已有节点、连线和事实。尚未开始的扩展取消，已经开始的任务允许按原规则收尾，但不得继续派生上游任务。标签移除后，研究中项目可恢复此前尚未执行的上游追溯，仍受项目门槛与 L5 边界约束；已停止项目不重开，历史事实不因标签变更被改写。

L1–L5 每个钱包均整理两份清单：

| 分析内容 | 需要保存的结果 |
| --- | --- |
| 直接部署过的合约 | 成功的顶层创建交易对应的合约地址、部署交易、区块与时间；进一步识别是否为 Token，匹配已有项目及研究报告，保留引用和依据 |
| 交易或交互过的项目 | 按链和代币合约地址关联项目，保存具体行为、交易哈希、区块与时间；识别有证据的买入、卖出，并与授权、普通转账、被动收款和其他交互分别记录，失败调用按实际结果记录 |

对普通样本与内部记录关联的顶层交易去重后补充回执与日志，并结合调用数据识别当前钱包有证据的代币交互。内部记录不作为新增项目发现或内部合约部署识别入口。普通交易的 `to` 可能是路由合约，不能直接当成交互代币；创建出的合约地址可从 Etherscan `contractAddress` 或创建交易回执取得。当前 Token 交易模型尚未保存创建出的合约地址及本流程所需的回执日志，这部分随历史分析实现。

钱包“交易过什么项目”的明确买入／卖出识别，首版与研究截止采用相同七个协议：Uniswap V2/V3/V4、Sushi V2/V3、PancakeSwap V2/V3。采样入口为普通与内部各最多 300 条原始记录关联的顶层交易，不先按固定 Router 或少量方法名筛选；经聚合器、通用路由或多跳交易最终进入上述支持池的，可以根据可信底层池证据识别。RFQ、订单结算、自定义路由或其他未支持路径保留原始证据及能够确定的代币关系，行为标记为未分类，不伪造成买入、卖出或“没有交易”。

授权、普通转账、被动收款和实际买卖分别记录，不单凭 `Transfer`、净收支或顶层方法名推断买卖，也不把路由中间经过的全部代币都归为钱包主动交易过的项目。协议尚未识别时保留原始证据及能够确定的关系，不丢弃交易或据此断言没有交易过项目。具体解析覆盖及必要补充数据后续细化，详见 [交易项目识别的协议覆盖](token-wallet-research-flow.md#交易项目识别的协议覆盖)。这项历史研究范围独立于现有 V2 底池查询和 Swap 索引；L1 固定路径池状态仅为资产估值采集，不扩展历史交易样本或通用底池研究。

同一项目内按链和钱包地址去重，共同来源只保存一个节点并分析一次，钱包角色与所有资金关系完整保留。同一钱包可以同时具有“部署者”“owner”“初始接收钱包”“税费接收钱包”等多个角色标签，各标签并存且不互相覆盖，相同标签去重。角色关联具体项目及证据，不能把其他项目中的身份直接套用到当前项目。一个钱包有四个标签仍计为一个钱包，同一历史窗口的普通与内部各采一份最多 300 条记录并复用分析，同一数据时点的余额按地址复用；具体示例见 [多重身份与标签](token-wallet-research-flow.md#同一钱包的多重身份与标签)。

来源已在图中时连接已有节点，保留跨层、循环和回流关系，避免重复采集或无限展开。L1 保持为直接关联入口，其他节点按已发现关系中距离任一 L1 的最短上游追溯距离分层；层级与角色标签分别记录，不因多个角色复制钱包或资金连线。发现更短路径时更新层级，复用已有分析并按新层级判断扩展边界。跨项目复用需匹配链、地址、截止区块和采样规则，不能永久复用某钱包的一次历史样本。

后台在项目门槛、交易所／跨链终止节点及 L5 深度边界内自动采集并分析，展示五层实际结果，不以用户点击展开作为取数触发。底层保存有向关系图，以分层资金来源树呈现；允许折叠控制显示，折叠不删除数据或暂停后台采集。除原生币资金门槛外，不增加每层来源数量上限；并发、限流、进度保存与局部重试见关联目标技术设计。项目停止时按统一任务收尾规则取消未开始任务、允许已开始任务完成，不等待五层齐备。

资金连线按链、来源、接收方和资产组织，明确区分普通直接转账、内部发起人归因与内部地址库终止关系，按同一关系口径显示金额、笔数及首次／最近时间。普通交易按链和交易哈希去重，内部记录须进一步区分同交易中的不同条；跨样本关联保留，同一条不重复计额。真实内部流水与归因展示不作为两笔入账相加，普通与内部记录中的同一实际转账也不重复计额。点击可核对实际转出方、顶层发起人及归因依据。点击任一层的钱包可查看其历史部署合约、交互代币及已匹配的项目、研究报告。显示筛选与完整资料分开，连线汇总与其交易明细使用相同范围。

历史关系图中存在连续连线，不自动代表同一笔资金连续流动。例如 L2 在 `25000` 区块向 L1 转账，L3 在 `28000` 区块才向 L2 转账，两笔虽都早于项目部署区块 `30000`，后一笔仍不能解释前一笔的来源。查看某笔入账的上游路径时，按区块与区块内交易序号逐跳核对上游入账早于下游出账；这只筛选已取得的证据，不改变 `B - 1` 和两类各最多 300 条的查询规则，也不单凭时序判断混合资金中的金额归属。同交易内缺少可靠先后证据时不声称资金先入后出；发起人归因只表达关联，不能将其时间描述为 A 已证实的实际出账，也不能将归因连线描述为已证实资金路径。

最终将各层历史项目、代币交互与资金关系关联当前项目，保存交易证据供展示与核对。共同来源本身不直接等同于同一团队；即使关联历史项目已有风险报告，也只展示关联和报告引用，不据此排除当前项目。图上的显示筛选、折叠和路径核对仅影响查看范围，不属于项目筛选。这一资料流程独立于源码 AI 静态质检，自身不执行项目排除或关注项目交接。L1 采集下节固定资产余额与 USDT 估值，L2–L5 仅研究历史交易、行为及资金关系。

数据组织参考 GraphSense，节点展开与交易明细参考 MetaSleuth 和 Arkham，Etherscan 多层遍历实现可参考 chainmap。资料链接与适用边界见 [资金来源图参考方案](token-wallet-funding-graph.md#参考方案)。沿用自己的采集和数据库能力承载地址、资金关系及证据，具体结构与接口见钱包及查询管理目标设计。

## 已明确的 L1 资产余额与 USDT 估值（尚未实现）

ETH 首版每个 L1 钱包固定读取原生 ETH、WETH、USDT、USDC、DAI、WBTC；L2–L5 不读取余额。每项保存原始余额和独立 USDT value，并计算钱包已知 USDT 小计、标明总值完整性。这里的“总值”仅指六项固定资产的价值合计，不宣称覆盖钱包全部资产。

管理员按链、按资产配置固定 DEX 现货价格路径，支持资产直接到 USDT 或经一个中间资产的最多两跳路径。池只能来自首版七协议的可信部署：Uniswap V2/V3/V4、Sushi V2/V3、PancakeSwap V2/V3。实际使用的路径与池必须能够追溯，不因配置缺失自动改用其他路径或提供方价格。

| 资产或情况 | 估值规则 |
| --- | --- |
| 原生 ETH | 读取原生余额，复用 WETH 的 USDT 估值路径，单独保存 ETH 的余额与价值 |
| USDT | 按自身精度直接计入 USDT value |
| WETH、USDC、DAI、WBTC | 按各自配置路径取得现货价格；USDC、DAI 等资产不得固定假设与 USDT 为 `1:1` |
| 零余额 | 已成功读到零余额时，可直接记录零 USDT value，不要求价格路径可用 |
| 非零余额无法估值 | 池缺失、储备为零、路径不可用或读取失败时，保留余额、失败原因、其他逐项结果及已知小计；钱包总值标记为“不完整”并列出缺失资产，不得按零代替 |

一次钱包资产采集选定执行时最新区块作为观察区块，六项余额、路径池状态和价格均使用该区块，不拼接不同时点的结果。每次结果保留价格路径、池、观察区块、区块时间、采集时间及失败原因；USDT 直接计值或零余额无需路径时，保留实际计值依据。余额本身未读取成功时同样不能当作零或完整估值。

部分成功的快照保留已取得的事实；已知小计只计算本次观察区块内可确定的逐项价值，不用上次成功余额或价格填补本次缺失。上一快照可作为历史事实保留，不冒充当前结果。配置变更只影响后续刷新，不回算或改写历史快照。具体 API、数据结构、存储与计算实现留到技术设计阶段确定。

BSC 的资产清单、合约地址和估值路径留到接入 BSC 时确定；当前只记录 `0.01 BNB` 默认资金门槛及同代码独立实例原则。详见 [L1 资产余额与 USDT 估值](token-wallet-research-flow.md#l1-资产余额与-usdt-估值)。

## 已明确的研究观察与停止规则（待实现）

### 首次已识别 Swap

每条链使用一套共享事件监控，动态覆盖本链所有研究中项目。首版 ETH 的明确协议范围为：Uniswap V2、Uniswap V3、Uniswap V4、Sushi V2、Sushi V3、PancakeSwap V2、PancakeSwap V3 的 Ethereum 部署。

- 在上述可信协议中，任何实际交换币种涉及目标 Token 的有效 Swap 都立即停止研究，不增加成交额、钱包身份、方向或普通买卖阈值；flash swap 也属于 Swap。添加任意流动性、创建或初始化池、普通 `Transfer`、`Approval` 都不停止研究。
- “首次”统一表述为“首次已识别 Swap”：它是当前协议覆盖版本、已完整日志范围与已解析映射内，按 `blockNumber`、`transactionIndex`、`logIndex` 排序最早的事件，不声称是全市场绝对首笔。
- 每个项目保存并展示协议覆盖清单、覆盖版本、连续日志覆盖进度和未解析原因。未接入协议、RFQ、未知池或映射缺失保持“未知”，不能写成“无 Swap”。
- 新目标先接收实时日志，再固定补查终点 `H` 并补查部署区块 `B..H`。断线或重启从持久覆盖进度恢复；重复日志不得重复触发。已识别 Swap 可先停止研究，随后补齐此前缺口并用更早事件更新证据，但不恢复研究。
- 后续新增协议适配器时，只从部署区块回补仍在研究的项目；已因 Swap、超时或人工操作停止的项目保留停止时的覆盖版本和结论，不重新匹配或改写状态。

具体协议事件、真实部署校验、池映射及覆盖表达见 [ETH Swap 事件调研](token-swap-events-research.md)。

### 活动续期与超时

默认观察时长为 72 小时，由管理员按链配置。项目初始观察期限为“部署区块时间 + 当前配置时长”；配置修改只影响之后新建项目及之后发生的续期事件，不批量改写已经保存的期限。

所有研究中项目持续覆盖目标 Token 合约自身发出的合法 ERC-20 `Approval`、`Transfer`，以及部署者／当前 owner 的主动交易。合法 Token 日志包括金额为零、撤销授权、mint、burn 和自己转给自己的事件。主动交易必须成功、属于顶层交易且 `from` 为对应监控地址，包括成功的零 ETH 合约调用；仅收到交易、失败交易和内部调用不能作为该监控地址的主动活动。

部署者从部署交易之后开始监控，部署交易自身不重复作为活动；当前 owner 从成功读取它所用的观察区块开始监控，包含该区块。owner 更换后停止旧 owner 的后续活动监控并切换到新 owner；部署者在项目研究期间始终保留。owner 尚未取得时不推测地址，部署者监控仍独立工作。地址重合时同一项目同一交易只处理一次，并保留全部命中角色；同一交易关联不同项目时，各项目分别处理。

日志或交易区块时间早于或等于处理前的当前期限时，把观察期限重置为“该时间 + 处理活动时的当前配置时长”，续期次数不设上限。重复日志或交易不重复执行相同动作。晚于当前期限的活动只保留迟到依据，不续期、不重查源码、不刷新；即使覆盖滞后导致超时状态尚未写入，也不能阻止随后按期限停止，更不能恢复已停止项目。

只有在链上已经出现区块时间晚于当前期限，并且目标 Token `Approval`、`Transfer`、部署者交易、当前 owner 在各自有效监控区间内的交易，以及首版 Swap 的连续覆盖与必要解析均完整越过该期限，能够证明期限内没有尚未处理的有效活动或首次已识别 Swap 时，项目才因不活跃停止。任一覆盖落后、查询失败或映射待解析时继续补齐，不可按服务器收到时间提前过期。期限、续期依据和停止时间统一使用链上区块时间；各类活动保留首次与最近证据及去重计数，交易证据还应包含命中地址和角色。

### 管理员手动停止与任务收尾

管理员可以手动停止研究，其他成员不能。无论因首次已识别 Swap、活动超时还是人工停止，项目一旦停止均不能恢复或重开，之后到达的活动和 Swap 只按覆盖需要处理，不启动项目资料采集。

多个停止条件同时出现时，主停止原因保留首次成功写入的值，不反复改写。之后补齐的 Swap 等证据另行保存；此前缺口补查仍可更新当前覆盖版本内更早的 Swap 证据，但不改变已经保存的主停止原因或恢复项目。

停止时排队但未开始的研究与刷新任务直接取消；已经开始的任务继续原本的有限重试策略，直至成功或重试耗尽后保存结果或最终失败。停止后不得启动新的下游任务。在途任务全部收尾后，项目专属的链上状态、地址、税率、余额、持币和钱包资料冻结，不再提供手动补充或刷新入口。

按 `code_hash` 共享的静态产物例外：质检报告、源码公开链接，以及 owner、税费接收地址和税率的静态分析／读取方案始终展示该源码的最新有效版本。管理员重检或其他研究中项目产生新版时，已停止项目也看到新版，但不会据此重启项目专属采集或改变停止状态。

## 已明确的活动触发刷新策略（待实现）

| 活动 | 期限内始终执行 | 其他资料刷新 |
| --- | --- | --- |
| 目标 Token `Approval` | 记录证据并续期；不重查源码 | 无，不提供配置 |
| 目标 Token `Transfer` | 记录证据并续期；无非空源码时重新查询源码 | 可配置，默认 Token 当前状态、Ave 持币地址总数与 Top 100 |

每个项目、每个数据组使用独立冷却时间，默认 10 分钟，并可由管理员按链配置。冷却期内或同组任务正在执行时发生的重复 `Transfer` 合并为一次后续刷新；观察期限续期不受冷却或合并限制。缺少非空源码时，符合期限的 `Transfer` 或监控地址主动交易触发源码查询的资格不可关闭，同类查询与在途或冷却中的请求合并。已有非空源码不因活动重复下载或重新调用 AI。

项目动态资料通常展示最近一次成功事实，失败保留上次成功值并单独记录最近失败时间与原因。L1 资产同时保留每次估值快照：部分成功仍记录本次已知小计、不完整状态和缺失资产，不用上次完整结果掩盖本次缺项，也不混合观察区块。

## 已明确的合约 owner 与关联钱包研究（尚未实现）

本节属于钱包资料的采集、解析与展示阶段，owner 的取得、缺失及其钱包历史结果均不触发项目筛选或排除。源码质检只生成事实报告，第一板块不进行风险判断。

合约 owner 是项目的关联钱包。取得 owner 地址后，连同部署者、初始接收钱包及税费接收钱包一并纳入普通交易与资产余额采集，并保留各自的角色关联；不同角色可能对应同一地址，也可能对应不同地址。图示见 [合约 owner 获取与关联钱包采集流程](token-owner-wallet-flow.md)。

### AI 分析源码，Go 读取链上 owner

owner 获取统一采用“AI 判断源码是否提供可用读取方式，Go 程序按该方式读取链上数据”的流程。读取方式依据实际源码确定，不限定为 `owner()`、`getowner()` 或其他固定函数名，也不设置预先尝试固定函数的流程。

AI 对每一份源码分析 owner 能否读取，并在可读取时给出 Go 可以执行的读取说明。例如源码提供 `getowner()` 并返回地址，则说明函数签名、所需参数及返回类型，由 Go 程序编码调用、解码结果。分析依据应指向源码中对应的字段或函数，不能只凭函数名称推断其返回值就是 owner。AI 输出读取方式，实际 owner 地址通过当前合约的链上读取取得。

每次获取 owner 时，按以下流程处理：

1. 使用当前合约的运行时字节码 `code_hash` 查询数据库，匹配对应源码已完成的 owner 分析结果。
2. 命中时复用“可读取及读取方式”或“未识别到可用读取方式”的结论，同一份源码不因新部署地址重复分析。
3. 没有已完成结果时，取得或复用对应的非空源码，交给 AI 分析是否可读取 owner 及读取方式。没有源码则记录资料未取得，不能让 AI 无依据分析。
4. 将完成的分析结论、依据及可用读取方式关联源码与 `code_hash` 保存，供相同源码复用。AI 请求失败、超时或无效响应单独记录为技术异常，不保存成“不可读取”的源码结论。
5. 分析或复用结果提供可用方式时，由 Go 程序对当前链、当前合约执行只读查询，以本次采集时最新区块的状态取得 owner；没有可用方式时记录结果，结束本项获取。
6. 保存本次实际使用的方式、读取结果、来源区块与时间。取得地址后纳入 L1；未取得地址则保存原因，继续其他已知钱包与资料采集。

同一份源码共享 owner 分析结论和读取方式；各部署实例的 owner 地址仍分别读取，不能复制其他合约的地址或旧 owner 快照。源码质检报告与 owner 分析分别保存结果，不要求在同一次 AI 调用中取得，也不互相作为完成前提。Go 的 owner 查询不进入静态质检报告的链上核实过程。

### 读取结果与钱包资料

取得 owner 后，沿用关联钱包采集范围：以 `项目部署区块 - 1` 为截止高度，分别读取部署前普通与内部各最多 300 条原始记录；按本次资产观察区块读取原生 ETH、WETH、USDT、USDC、DAI、WBTC，并在同区块逐项估值。资金来源扩展遵守项目门槛快照和交易所／跨链终止节点规则。owner 为合约地址时也按关联地址采集，不沿用初始接收钱包的无代码地址筛选来排除 owner。地址已在 L1 时追加当前项目的 owner 标签，保留其他角色并复用同一窗口的资料与分析。owner 地址来自当前采集时点，不将其自动解释为部署时的 owner。

成功读取的观察区块同时作为当前 owner 主动交易的监控起点。owner 更换后切换监控地址，部署者始终保留；只有监控地址发出的成功顶层交易可续期和触发缺失源码重查，零原生币交易也有效，不触发其他资料刷新。研究期活动监控与部署前两类历史分析分别覆盖各自时间范围，新增内部收支不构成研究期续期活动。

没有源码、AI 完成分析但未识别到可用方式，以及 Go 链上调用未取得地址，需要分别保存实际结果与原因。“未识别到读取方式”或“未取得地址”不表示已经确认合约没有 owner，也不能填入部署者等推测地址。无法定位 owner 地址时，只跳过该未知地址的钱包采集；其他已知钱包继续研究，不因此排除项目或改变 Token 识别结论。活动触发刷新与项目停止后的冻结按统一规则执行。

owner 读为零地址时，原值与观察依据照实保存，不纳入 L1 或主动交易监控；结束旧 owner 当前角色及其监控，部署者监控仍保留。多个读取入口返回冲突结果且无法确定语义时，保存全部证据并标记本次未能更新，不擅自选值；已有最近成功 owner 及其监控保留，同时明确显示本次冲突。零地址以外的地址不因外观、名称或被推测为销毁地址而自动排除。

读取说明的具体结构、Go 支持方式与校验、版本和并发协调在关联目标技术设计中说明。AI 每轮最多 2 次请求，其他瞬态链上采集最多 3 次，详见[重试边界](#研究请求的重试边界)。owner 变化后替换当前角色、切换活动监控并启动新 L1 初始研究的业务语义保持不变。

## 已明确的税费接收钱包获取与研究（尚未实现）

税费接收钱包是项目的 L1 直接关联钱包，可以是一个，也可以是多个。由 AI 分析已取得的合约源码，识别税费去向、对应字段或函数及依据，再取得具体地址。图示见 [税费接收钱包获取流程](token-fee-recipient-wallet-flow.md)。

| 源码中的情况 | 获取方式 |
| --- | --- |
| 可以由源码确定且写死的接收地址 | AI 直接提取地址，保存代码位置及税费接收用途依据。 |
| 接收地址保存在链上状态中，源码提供可用读函数 | AI 提供函数签名、必要参数及返回类型等读取说明，Go 按本次采集时最新区块，对当前链、当前合约执行只读调用，解码出一个或多个地址。 |
| 同时存在固定地址和需读取的地址 | 分别处理并合并结果，保留每个地址的来源；不将两种方式设为整个合约只能选择其一。 |

AI 根据实际税费分配逻辑判断地址用途，不仅凭变量或函数名称识别。支持多个字段、多个读函数或返回多个地址的方式，不只保留第一个接收钱包。读取说明应足够 Go 编码调用与提取地址；需要参数时给出参数类型、值或可确定的取值依据，不猜测参数或执行 AI 生成的任意程序。

可修改变量的初始赋值即使在源码中写成地址字面量，也不能直接当成当前固定接收地址；需要通过可用读函数取得当前值。由部署参数决定但无法从实际源码确定的地址，也不能猜测填写。本项不新增部署初始化资料采集，不解析代理实现地址，也不获取或分析外部依赖源码。

先按 `code_hash` 查询对应源码已完成的税费接收钱包分析结果，命中直接复用，没有时才对非空源码进行 AI 分析。共享识别结论、源码依据、确实固定的地址和读取方式；动态地址由各合约分别读取并保存实际调用、返回值、来源区块与时间，不复制其他部署实例或旧快照。静态质检、owner、税费接收钱包和税率分析分别保存，不要求在同一次 AI 调用中生成，也不互相作为完成前提。

取得的全部非零地址按链和地址去重加入 L1，追加当前项目的“税费接收钱包”标签，并保留 owner、部署者和初始接收钱包等已有标签。同一地址对应多个税费用途时，保留各用途及其源码或读取依据。“最多 5 个”只限制初始接收钱包，不限制税费接收钱包数量；税费接收钱包可以是合约地址。零地址原值与用途依据照实保存，但不作为钱包节点加入研究或监控。部分地址读取失败时，保留已取得结果，不将未取得部分当作已经删除。

后续沿用每个钱包在区块 `0..B-1` 内普通与内部各最多 300 条原始记录、去重后的关联顶层交易及必要回执日志、历史部署与代币交互分析、受项目门槛和地址库优先终止约束的 L2–L5 直接来源与发起人归因研究，以及 L1 六项资产余额和 USDT 估值，其中 `B` 为项目部署区块。动态读取得到的是采集时点的配置地址，不自动解释为部署时的接收地址；识别到接收配置也不代表已经发生税费支付。

源码中未发现税费接收钱包、已识别接收逻辑但未找到可用获取方式、未取得源码、AI 技术失败及链上读取失败分别保留实际结果与原因。只取得部分地址时保留成功结果并继续这些钱包的采集，不把未知部分解释为不存在，也不把技术失败保存为可复用的“未发现”结论。本项仅采集、解析和展示，不增加项目风险评级、过滤或排除规则；当前 AI 不评级。

读取说明、Go 校验、零地址与部分结果、共享版本及刷新协调见[源码事实与读取方案](../../design/token-intelligence/source-facts-and-read-plans.md)。旧税费地址保留历史 L1 并继续未完成研究；本轮形成目标设计，尚未实现。

## 已明确的合约税率读取（尚未实现）

税率沿用“AI 分析源码确定读取方式 → Go 读取当前合约链上数据 → 保存并展示”的思路，作为独立项目资料。完整图示见 [合约税率读取流程](token-tax-rate-flow.md)。税率读取不增加 Token 识别条件，也不改变关联钱包范围。

1. 按当前合约运行时 `code_hash` 查询对应源码已完成的 AI 税率分析结果；已有结果直接复用，没有结果且取得非空源码时才分析。
2. AI 根据实际税费计算逻辑识别可读取的税率及其用途，例如买入税、卖出税、普通转账税或具体分项；不强制每个合约都有这些分类，也不只凭函数名称判断。对每项给出函数签名、必要参数及其确定取值或依据、返回类型与提取位置，以及单位、分母或换算公式的源码依据。
3. Go 按可执行的说明，对当前链、当前合约在本次采集的最新区块进行只读调用，解码原始返回值。同一税率相关分项和动态分母如需多个读函数，固定使用该次采集的区块。
4. 保存税率类型或分项、原始返回值、单位或分母、能够确定的百分比、源码与调用依据，以及实际区块与时间，关联当前项目展示。只有源码明确分项的组合公式时才计算总税率，不将总税率与其分项重复相加。

例如源码明确按 `10000` 为分母扣税，读函数返回 `500`，则展示 `500 / 10000 × 100% = 5%`。分母由源码计算逻辑或对应读函数确定，不统一假定为 `100`、`10000`，也不按代币 `decimals` 推算。单位、分母或组合关系无法确定时，保留原始值与原因，不编造百分比或总税率。

同一份源码共享税率语义、可读取性结论、读取方式和换算依据；实际税率及链上分母逐合约读取，不复用其他部署实例或旧快照。没有源码、未识别到可用读函数、AI 技术失败、链上读取失败与部分成功分别记录。保留成功读取的税率项，未取得的值不填成 `0` 或“无税”；实际读到 `0` 也只表示该项在该时点的返回值为零。技术失败不保存为可复用的“无读取方式”结论，不覆盖有效分析。

本项展示当前读到的税率配置及源码中的适用条件，不承诺某笔买卖的实际扣税结果。本轮不扩展为交易模拟、链上角色或免税名单核实，不解析代理实现或外部依赖，不增加直接读存储或固定函数探测兜底。源码中的固定数值或初始赋值可以作为分析依据，不能冒充本次链上读取结果。

税率资料只采集、解释和展示，不增加阈值、评分、项目过滤或排除规则，也不作为 owner、税费接收钱包或其他资料采集的前置条件。AI 静态质检独立生成事实报告而不评级，报告不使用税率链上结果进行核实。各项源码分析分别复用，无需在同一次 AI 调用中完成。

调用与换算结构、参数和结果校验、重试及版本机制见[源码事实与读取方案](../../design/token-intelligence/source-facts-and-read-plans.md)；税率按分项保存，冲突或无法换算不得伪造成零。尚未实现税率读取。

### 结果保存与研究边界

按链、目标代币合约和持有人地址关联，逐项保存 Top 100 名次、地址、持有数量、持有占比、Ave 原始标签字段和查询时间，不按相同 `code_hash` 共享不同代币合约的持仓。当前 Top 100 不等于部署交易内的初始分配，也不能代替指定历史区块或当前时点的完整持有人名单；本次不增加完整名单、历史持有人重建或初始分配明细采集。

本需求不设计持币分页、游标、全量遍历状态或覆盖率。`holders` 只表达 Ave 提供的地址总数，Top 100 只表达提供方的有界排名；不能根据两者条数差异推断采集不完整，也不能将 Top 100 标为全量。Ave 成功空结果、字段缺失、未收录和技术失败分别表达，不把未采集、权限错误或解析失败填成 `0`，不推测地址标签。

本项只保存并展示当前持币总数与 Top 100 分布，不增加集中度阈值、评分或过滤规则，也不把 Top 100 地址自动纳入 L1–L5 历史研究。研究中项目默认由具有续期资格的目标 Token `Transfer` 刷新该组数据，管理员可调整此映射；`Approval` 与部署者／当前 owner 主动交易不触发持币刷新。只展示最近一次成功事实，失败另存时间与原因。项目停止后按统一规则冻结项目专属持币快照。

### 多链接保存与来源展示

一份源码可以关联多条公开资料，同一类别也可以有多条，不设计成每类仅一个链接。按完整 URL 去重，相同链接在多处出现时合并展示并保留全部出处；同域名下的不同路径、查询参数或片段不能仅凭域名相同就合并。AI 只能提取实际出现的链接，不根据项目名称推测网址，也不将裸域名、账号名或 `http://` 链接自动补写为 HTTPS。其他协议的采集范围后续明确。

每条资料保存完整链接、资料类别、与项目的关系或用途说明、实际源码记录引用，以及文件名、可定位的位置或源码片段等提取依据。统一记录资料来源为“合约源码”，并保留提取时间；该时间不表示链接的发布时间或验证时间。

当这些资料展示在 UI 时，每条链接明确标注 **“来源：合约源码”**，并保留查看源码出处的能力。复用结果时仍关联原提取源码及其出处；不将源码复用描述为当前项目官网已经确认。具体页面布局后续设计，本轮不实现 UI。

### 同源码复用与研究边界

通过 `code_hash` 定位实际源码记录，同一份源码已有完成结果时直接复用，无需因新增项目地址重复调用 AI；缺失结果且已取得源码时才分析。结果绑定实际源码内容及出处，不能仅凭运行时字节码相同，就把另一份不同源码注释中的链接当作本次源码提取结果。

成功分析未发现链接时，保存“源码中未发现公开资料链接”；无源码或技术失败时保留未提取的实际原因，不把请求失败记为已确认没有链接。本项结果不依赖 owner、税率、持币或钱包研究完成，也不作为其他研究资料采集的前提。

公开资料链接只收集、分类和展示，不核验可访问性、官方归属、链接内容或审计结论，不跟随链接扩大代理或外部依赖分析，也不新增项目评分和过滤条件。没有链接不代表项目没有公开资料。该结果属于按 `code_hash` 共享的静态产物；共享版本更新时，已停止项目也展示最新有效结果，但不恢复项目研究。

输出格式、链接证据、去重、共享版本及查询见[源码事实与读取方案](../../design/token-intelligence/source-facts-and-read-plans.md)；首版处理实际 HTTPS 链接，其他协议留到后续。尚未实现提取或展示。

## 已明确的正常运行时效目标（尚未验证）

正常追平运行时，以下三项分别采用 **P95 ≤ 15 秒**的设计目标，即各自至少 95% 的样本在 15 秒内完成，不将不同链路混合统计：

| 链路 | 起点 | 完成点 |
| --- | --- | --- |
| 新 Token 发现 | 配置节点首次可查询到对应新区块 | 新项目及其初始研究任务可靠落库 |
| 已登记项目活动续期 | 配置节点首次可查询到活动所在新区块 | 合法且具有期限资格的活动使项目续期结果可靠落库 |
| 已登记项目 Swap 停止 | 配置节点首次可查询到 Swap 所在新区块 | 支持协议内涉及目标 Token 的有效 Swap 使研究停止结果可靠落库 |

该目标包含上述链路的内部排队、识别或必要解析及持久化时间，不从工作进程开始执行时重新计时。链上区块时间仍用于活动资格、观察期限与停止证据；上述节点可查询时点用于衡量系统处理延迟，两者不能混用。

本项仅确认正常追平运行的目标，不代表当前实现已达到该性能。首次三天发现补扫、首轮基础资料、AI 首次分析、L1 首轮钱包资料，以及刷新、恢复和其他停止目标见下文。超时停止仍须满足完整覆盖门槛，不能用 15 秒目标绕过覆盖检查。测量方式、统计窗口、承载规模和容量验收在目标技术设计中明确。

### 首次三天发现补扫

首次启动没有扫描游标时，从开始扫描三天历史到发现游标追平最新高度，以 **2 小时内完成**为设计目标，尚未验证容量。补扫仍执行已经确认的每轮最多 100 块并行预取、按高度串行识别和逐块可靠保存；完成点要求候选识别结果、项目及初始研究任务已经保存，不要求源码、AI 或钱包研究完成。不跳过历史区块，也不另开新区块优先扫描通道。

三天起点仍按实际区块时间定位，不固定换算成区块数。以 [Ethereum 的 12 秒槽位](https://ethereum.org/developers/docs/consensus-mechanisms/pos/block-proposal/)估算，三天约有 21,600 个出块机会，实际可能存在空槽。若两小时内追平并处理期间新增区块，需要约 `21,600 / 7,200 + 1 / 12 ≈ 3.1` 块/秒的持续能力；这只是容量估算，不是当前实现的测量结果。技术设计须明确负载、依赖条件与验收方式，失败不允许以越过区块或漏建任务来满足时限。

### 首轮基础资料

正常追平期间，新项目可靠落库后，Token 当前状态、源码首次查询、Ave 持币地址总数和 Top 100 的首轮结果分别以 **P95 ≤ 1 分钟可查**为设计目标，包含内部排队与请求时间，各项独立统计和展示，不等待整组资料齐备。

首轮可查结果包括成功取得的事实，以及实际的空结果、未收录、失败待重试等状态；其中源码成功空内容不代表请求失败，Ave 未收录或字段缺失不填为零。该目标衡量首轮响应与状态可见时间，不代表保证取得非空源码或完整资料。成功率须单独衡量，不能以快速失败替代成功采集；没有发出请求的排队状态也不能冒充已经完成首轮查询。技术重试继续按各能力规则执行，不要求在一分钟内耗尽。

AI 分析、钱包研究和首次补扫期间产生的后台资料积压不属于本项正常追平目标，另行明确时效和资源安排。

### AI 首次分析

非空源码可靠保存且尚无对应有效缓存时，静态质检报告、owner 读取说明、税费接收钱包分析、税率读取与解释说明、源码公开链接分析分别采用 **P95 ≤ 5 分钟首次完成**的设计目标，从源码就绪起计并包含排队时间。各项独立保存和统计，不设置共同完成屏障；已有有效产物直接复用，不因新部署重复调用 AI。

技术失败、超时或无效响应单独记录，不作为完成的事实报告或可复用分析结论，不用失败结果满足本项完成目标。依赖缺少源码时明确显示等待源码，不从项目发现时计算为已经开始 AI 分析。人工重检已有报告、项目停止导致的未开始任务取消及在途收尾仍遵守既定规则，不能为了满足时效重新开启项目。具体模型、并发额度、请求资源边界和容量验收在技术设计中确定。

### L1 首轮资料与五层研究进度

从每个钱包加入项目 L1 起，普通历史、内部历史及六项资产首轮快照分别采用 **P95 ≤ 10 分钟可查**的设计目标，包含排队时间；失败或部分结果如实展示，不填补缺失或将排队记为已查询。六项资产仍使用同一观察区块，部分估值不以旧快照补齐。

历史行为所需补充证据、行为解析及 L2–L5 持续推进并展示实际进度，**不设所有项目统一的整图完成期限**。调度优先保障 L1 首轮资料，深层研究在各项目间公平使用剩余配额；不增加每层来源钱包数量上限，不减少已确认的两类采样范围，不因界面未展开而停止采集。

研究停止规则保持不变：未开始的任务取消，已开始任务按有限重试规则收尾，停止后不再派生新任务，保存已取得的五层结果和未取得原因。五层范围不表示一定能在停止前取得整图；既定停止事件不能为等待资料而延后。

旧 owner 或税费钱包失去最后一个当前角色后，保留该项目的历史 L1 入口及角色依据，继续未完成的历史与上游研究，仍受 L5、地址库和项目停止规则约束。角色变化只关闭失效的当前角色与旧 owner 活动监控，不撤销已经建立的历史研究范围；查询时必须区分当前身份与历史关联。

### 活动刷新、恢复与停止

| 环节 | 已确认的时效目标及计时边界 |
| --- | --- |
| 活动刷新 | 前置资料已就绪且冷却结束后，首轮查询结果分别 P95 ≤ 1 分钟可查；包含具备执行资格后的排队与请求时间，不能用仅入队替代结果。冷却与依赖等待单独展示，不混入一分钟执行目标。 |
| 短时断线恢复 | 对缺口不超过 1 小时的已登记目标，在上游恢复正常后 5 分钟内补齐相应覆盖并追平；不将收到最新消息当作已经补齐。 |
| 超时停止 | 链上时间、活动与 Swap 完整覆盖、必要解析等全部停止条件满足后，P95 ≤ 15 秒可靠写入停止状态；不因达到时间指标而绕过任何条件。 |
| 人工停止 | 管理员请求到达 API 后，P95 ≤ 2 秒持久确认研究停止，并禁止新的任务首次启动；在途任务仍按既定规则收尾，不要求两秒内完成全部在途工作。 |

更长故障、动态目标的大段历史补查，以及补扫产生的研究积压，按实际工作量展示已完成进度、积压和预计耗时，不设置统一完成期限。估算依赖实际处理速度与上游可用性；尚不足以估计时明确展示原因，不能伪造预计完成时间。不以漏采、跳过失败区块、截断钱包分支或提前确认超时来满足指标。

以上均为待容量验收的设计目标。目标已确定不代表当前代码已满足，也不代表发生外部故障时仍能保证取得全部资料。

### 研究请求的重试边界

源码每轮最多 4 次请求；其他瞬态采集错误每轮最多 3 次请求；AI 每轮最多 2 次请求。尚未取得配额的等待不计为请求，实际发出后收到限流、超时或其他错误须记录该次请求。配置、凭据或权限错误隔离对应能力并通知，不对已知无效配置持续发送请求；数据库故障按持久任务恢复，不伪造成提供方返回的资料结论。重试间隔、请求超时和资源状态模型由技术设计确定。

领取任务或等待配额本身不算已经开始；取得配额并登记执行后才具有在途收尾资格。刷新轮次、共享分析版本和执行租约分别表达，防止旧工作进程或旧轮次覆盖较新的结果。研究停止不能取消已经开始的有限重试，也不能借重试继续派生新的项目任务。

## 与当前实现及研究资料的关系

当前 Token 代码主要实现按区块发现项目、创建六类一次性采集任务，并在任务全部结束后尝试构建唯一的不可变画像。当前 `ChainProcessor.RunOnce` 仍在单链内执行“获取一块、处理并保存一块、再获取下一块”的串行循环，并一次处理到本轮启动时查询到的最新高度，尚未实现每轮最多 100 块的并行预取流水线。当前 ATHENA 合约已有接收地址数组的批量判断入口，传入单个地址也能取得单个结果；目标方案已明确单个与批量调用形态，合约内部代码检查和逐项诊断尚待实现。现有 Ave Token Detail 采集已经读取 `holders`，但仍处于更宽的市场数据采集与画像流程中，尚未接入 Top100 Holders，也没有形成本文要求的独立持币总数与 Top 100 资料。本文确定的事实型第一板块、三类活动矩阵、首版七协议 Swap 覆盖、三类停止原因、任务收尾、项目事实冻结、L1 六项资产逐项 USDT 估值、资金门槛快照、内部 ETH 双样本与发起人归因、交易所／跨链优先终止节点，以及彻底移除 `simulation_result` 等目标均尚未实现。相关说明见：

- [Token 链扫描与项目初始化](../../design/token-intelligence/chain-processor.md)。
- [Token 六源采集与项目画像](../../design/token-intelligence/collection-profile.md)。
- [Token 项目查询模型](../../design/token-intelligence/project-read-model.md)。

六类数据源、一次性采集、不可变画像以及现有组件边界均不作为新方案的固定约束。后续按 [Superpowers 工作流](../../developer-guide/superpowers-development.md)依据业务要求决定保留、替换或重新组织哪些能力；任务规格与计划使用 `docs/superpowers/specs/`、`docs/superpowers/plans/`，并将有效决定与实现事实同步到[系统设计](../../design/README.md)。

## 第三方发现方案调研备忘（本阶段未采用）

以下记录截至 2026 年 9 月 6 日的官方公开资料，供以后重新评估时参考，不是接入计划或当前开发依赖。价格、权限和数据覆盖可能调整，尚未实际调用接口核验完整性、延迟与账单消耗。

### Bitquery

Bitquery 的 EVM `Calls` 数据可按区块号与合约创建条件查询创建记录，包括内部创建路径，可作为未来扩展发现范围的候选来源。能力说明见 [合约创建查询](https://docs.bitquery.io/docs/blockchain/Ethereum/calls/contract-creation/) 与 [Calls 数据说明](https://docs.bitquery.io/docs/schema/evm/calls/)。

API 积分是调用查询时消耗的额度。根据 [积分规则](https://docs.bitquery.io/docs/ide/points/#how-are-points-calculated-for-the-realtime-dataset)，使用 `dataset: realtime` 时，每次查询每个数据集合（cube）消耗 5 积分，与返回记录数量无关；同一请求涉及多个数据集合时分别计费。只查询一次 `Calls` 按 5 积分计算，不能将所有 HTTP 请求一概视为 5 积分。

| 套餐 | 月付价格（美元） | 每月 API 积分 | 单次只查一个实时数据集合时的查询次数 |
| --- | --- | --- | --- |
| Personal | $49 | 10 万 | 约 2 万次 |
| Pro | $99 | 100 万 | 约 20 万次 |
| Scale | $299 | 500 万 | 约 100 万次 |

例如，1,000 个区块各发起一次仅查询 `Calls` 的实时请求，预计消耗 5,000 积分。分页、重复轮询和额外的数据查询增加用量；历史查询不直接套用这项实时计费规则。积分按付款日期对应的账期刷新，且与每分钟请求数、并发数限制独立。详见 [套餐与账期说明](https://docs.bitquery.io/docs/ide/paid/)。

Personal 仅限个人非商业用途；按区块主动查询可从商用 Pro 评估。若需要 Calls / Traces 的持续推送，则应评估 Scale，其订阅时长和推送数据量单独计量。完整历史数据不包含在基础套餐中，需要核实具体数据集合的历史范围及购买方式。详见 [官方定价](https://bitquery.io/pricing)。

### Allium

Allium 的 [Ethereum contracts 表](https://docs.allium.so/historical-data/supported-blockchains/evm/ethereum/raw/contracts) 来源于 `CREATE` / `CREATE2` 创建记录，包含 `block_number`，可供按区块查询。Explorer 属于历史分析产品；[产品比较](https://docs.allium.so/product-comparison)给出的通用数据新鲜度约为 1 小时，不能直接视为秒级发现新合约的能力，具体合约表延迟和实时产品覆盖仍需确认。

官网列出 [通用付费入口 $200/月起](https://www.allium.so/use-case/product-engineering)，但未承诺该价格包含所需 contracts SQL 权限和额度；[常规生产套餐](https://www.allium.so/compare/allium-vs-zerion)中的 Explorer SQL 与实时数据服务需具体报价。

另有 [Machine Payments 按次付费方式](https://docs.allium.so/ai/machine-payments/endpoints-pricing)：提交 SQL 为 $0.01/次，查询状态为 $0.01/次，获取结果为动态计费。因此 $0.01 不是一次完整查询的总成本；该价格表中状态与结果接口仍要求 API key，具体表权限也需确认，不能只凭提交价格确定可用性和总预算。
