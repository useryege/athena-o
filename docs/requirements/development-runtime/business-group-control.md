<a id="confirmed"></a>
## 已确认决定

| 编号 | 决定 | 约束 |
| --- | --- | --- |
| R01 | 本地与生产都需要管理员整组启停 | 两种环境采用同一组控制概念；各自的启动与重启规则见 R06、R08 |
| R02 | 核心服务始终运行 | 管理员业务控制中没有核心服务启停功能，控制接口也不能接受核心服务的业务停止命令 |
| R03 | Wallet、Notification 属于核心服务 | 两者不随某个业务组一同停止，核心服务自身持续提供能力 |
| R04 | 业务按板块整组启停 | 一个板块包含多个进程时共同接受控制；内部进程只展示状态，不提供逐进程启停入口 |
| R05 | 业务进程保持运行 | 停止业务不终止命令行程序；恢复业务通过常驻进程完成，管理与健康接口持续可用 |
| R06 | 本地 `make run` 启动全部纳入范围的服务，业务默认停止 | 核心立即可用；业务等待管理员开启，不能先执行采集等任务再切换为停止 |
| R07 | 业务停止后禁止所有业务查询和写入 | 包含已有数据查询；会员与管理员的业务访问均受限，前端不继续展示该板块业务数据 |
| R08 | 生产每次重启后业务默认停止 | 整体重启后全部业务组等待管理员开启；单个业务进程重启影响其所属组，不自动恢复此前运行状态 |
| R09 | 停止时立即关闭新入口，并处理在途工作 | 取消可取消的任务；已提交到外部系统的操作完成必要收尾，期间显示“停止中”，确认结束后才显示“已停止”；不终止常驻进程 |
| R10 | 业务组通知随组暂停，恢复时复核有效性 | 未发送消息暂停保留；组重新开启后只发送未过期且仍符合条件的消息；已开始发送按 R09 收尾；账户绑定、系统故障等核心通知继续发送 |
| R11 | 运行中必需成员故障时整组停止业务 | 关闭该组新业务入口，其余成员按 R09 收尾、通知按 R10 处理；修复后由管理员重新开启；不主动停止核心服务或无关业务组 |
| R12 | 必需依赖组未开启时拒绝本组启动 | 提示管理员先开启依赖组，本组保持停止；不自动开启其他业务组，也不在依赖后来开启时自动重试本组启动 |
| R13 | 手动停止被依赖组前，先停止依赖方并完成收尾 | 若其他业务组仍必需依赖本组且尚未完成停止和收尾，拒绝本次停止并提示先停止依赖方；不自动停止其他组，待依赖方结束后由管理员重新发起停止 |
| R14 | 必需依赖组故障时，使用方也停止业务并收尾 | 依赖故障使所需能力不可用时，使用方按 R09/R10 停止与收尾，并显示依赖故障原因；修复后由管理员先开启被依赖组再开启使用方，无关组继续运行 |
| R15 | 停止超时后显示异常，继续禁止新业务 | 超过约定时限仍无法确认收尾结束时显示“停止异常／需处理”，保留常驻进程和管理能力；外部结果未知则如实保留，不自动重发；后续确认收尾结束才显示已停止，恢复业务仍由管理员操作 |
| R16 | 全部必需成员就绪后才开放业务，部分启动失败则整组收尾 | 任一必需成员启动失败，整组启动失败；停止本次已启动的业务任务并按既定规则收尾，保留常驻进程和失败原因；修复后由管理员重新开启 |
| R17 | Etherscan Manager / Gateway 属于常开核心服务 | 业务组停止时禁止该组的新业务请求，Manager/Gateway 与管理员网关检查继续可用；不提供业务启停开关，不允许通过共享网关绕过停止组的访问限制 |
| R18 | 两个 BSC 索引器不再需要，确认删除 | 普通交易与 Swap 索引器移出本地及生产目标服务清单，不纳入全服务启动或管理员控制；撤回 BSC 业务组建议，删除范围见[独立需求](../blockchain-data/bsc-indexer-removal.md)，当前尚未实施 |
| R19（历史，Worm 部分已撤回） | 2026-09-15 曾确认 Worm 与 Sports 删除；2026-09-16 Worm 改为保留 | 含 Worm Markets／Trading、Sports Live／History 与 World Cup Corners；移出本地及生产目标服务与控制清单，不再评审两组启停；[删除需求](sports-removal.md)已记录，当前尚未实施 |
| R20 | 页面随业务状态隐藏数据，断线与恢复时先确认状态 | 正常联网且在前台的页面，从后端接受停止起最多 5 秒更新，收到停止状态立即隐藏业务数据并展示实际状态；断线或无法确认时隐藏数据且不误报已停止；重新打开、切回或重连后先确认运行再加载，管理员保留管理信息并标注过期；5 秒不延迟后端关闭入口，详见 [Q06](#page-rules) |
| R21 | 本地独立运行，继续使用五个远端 Gateway | 本地启动自己的业务、核心进程、数据库和 Etherscan Manager；Gateway 使用现有远端池，不另起本地 Gateway，本地启停和清理不操作远端实例；生产使用自身进程、存储和业务状态，API 额度是否独立由密钥配置决定，详见[运行范围](service-inventory-review.md#gateway-scope) |

“核心始终运行”和“进程常驻”描述系统运行期间的目标行为。关闭整个本地环境、部署维护、进程故障属于不同的生命周期，不由管理员业务启停按钮承担。

## 背景、目标与术语

开发主要由 AI 完成，用户通过本地环境复核成果；生产环境也需要统一管理业务运行。用户需要执行一次本地启动命令后，在管理员后台自行开启需要验收的板块，并在生产采用同一组控制概念。

| 术语 | 含义 |
| --- | --- |
| 核心服务 | 支持系统入口、身份、管理、共享能力或基础设施，持续提供服务 |
| 业务组 | 管理员一次启动或停止的业务板块，覆盖其成员进程和附属于核心 API 的对应业务入口 |
| 必需成员 | 缺少其能力时，业务组无法按约定完整提供业务的内部服务；具体名单按实际依赖在 Q05 明确，不将所有成员直接认定为必需 |
| 进程在线 | 程序存在且可被检查；不能单独证明管理接口可用或业务已开启 |
| 可管理 | 管理通道可用，能够查询控制状态或接收启停请求 |
| 业务停止 | 组内业务不执行，对外和内部调用均不能读取业务数据或发起业务写入 |
| 管理信息 | 组名、成员在线情况、控制状态、转换结果和必要故障说明；不包含可绕过停止限制的业务正文或记录 |
| 业务状态与健康状态 | 两种不同信息。业务停止可以是正常受控状态，健康检查通过也不代表业务已运行 |

<a id="boundaries"></a>
## 业务边界

### 使用者与访问入口

R07 覆盖普通会员、管理员、具备业务权限的 API 调用者以及服务间业务调用。界面隐藏按钮不能代替业务访问拒绝。

逐组审查列表、详情、导出、批量请求、订阅流和后台入口；仅列出实际存在的入口，不为本需求虚构新接口。现有账户与模块授权继续独立成立：业务组开启不会给用户增加权限。

业务停止必须呈现为对应板块不可用，不应被误报为登录失效或自动退出整个系统。核心账户、Wallet、Notification 和其他运行中的业务组保持其既定能力。

### 数据、任务和核心聚合入口

停止控制不代表清库、删除历史记录、撤销账户权限或取消用户订阅。生产重启后先保持业务停止；管理员再次开启时，通知队列按 R10/Q03 复核有效性，过期消息不补发。其他未完成业务任务按既有规则和 Q02 明确恢复边界。

以下入口不能遗漏：

- 停止组自身的查询与写入，包括管理员业务页。
- 核心 API 内直接实现的、属于保留业务组的接口；World Cup Corners 按 R19 删除。
- 搜索、概要、导出及通知历史等实际聚合了停止组业务数据的核心入口。
- 已打开页面和浏览器缓存的业务数据；可见切换时机见 Q06。
- 核心服务已接受但尚未完成的业务组工作；通知单独见 Q03。

停止期间可保留必要的控制与故障信息，但不能借诊断接口返回被禁止查询的业务详情。诊断信息的最终字段范围属于后续接口设计。

### 环境与资源所有权

本地实例与生产环境各自具有明确控制范围。对本地组的操作不能改变生产业务状态；不同工作目录或实例也不能因组名相同而互相控制。

核心服务不接受业务启停操作。进程部署、整套环境关闭和基础设施维护继续由其所属运行方式负责，遵守[服务开发规范](../../developer-guide/service-development-standards.md)与现有资源归属规则。

### 启动流程（原则已确认）

1. 管理员选择环境中的一个业务组并请求启动。
2. 按 R12 检查必需依赖组；尚未开启时拒绝本次启动并列出需先开启的组，本组保持停止，不替管理员开启依赖组。
3. 检查核心依赖、必需成员和配置，展示启动进度；按 R16，仅在全部必需成员就绪后才显示整组运行并开放业务入口。
4. 任一必需成员启动失败，整组启动失败并保留原因；停止本次已启动的业务任务，按 R09/R15 完成收尾和处理超时，保留常驻进程。
5. 修复后由管理员重新发起启动；失败成员自行恢复不自动开放业务。

### 停止流程（原则已确认）

1. 对管理员主动停止请求先检查依赖方；若仍有必需依赖本组的其他业务组尚未完成停止和收尾，按 R13 拒绝本次请求并列出需先停止的组，本组继续保持当前状态。
2. 检查通过并接受停止请求后，立即拒绝新业务查询、写入和新后台任务领取。
3. 进入“停止中”，取消可取消的任务；已提交到外部系统的操作完成必要收尾。共享 Notification 中该组未发送消息按 R10/Q03 暂停，已开始发送的操作完成必要收尾，核心通知继续发送。
4. 确认组内业务与必要收尾结束后才显示“已停止”；超时仍无法确认时，按 R15 显示“停止异常／需处理”并继续禁止新业务，保留原因和未知结果。后续确认结束后才更新为已停止；具体结束证据见 Q02，成员故障见 Q04。
5. 所有进程保留管理通道；停止操作不清理所属环境的数据库或容器。

操作目标、实际状态和最近确认时间应分别展示。重试或超时不能使旧的启动请求在新的停止决定之后重新开启业务。并发命令的处理办法、控制状态存储和通信方式留给技术设计，本轮不预设协议或中间件。

**技术决定 D03 已确认，2026-09-15**：用户回复“采用”，确认[重复命令、并发与生效点](../../superpowers/specs/2026-09-15-business-group-control-commands.md)中的规则：复用相同请求、对新请求校验控制版本，同向操作复用且冲突不排队；主动停止先预约并核对所有入口关闭，再报告 R09 的停止接受／生效，最后以收尾证据确认完成。预约阶段与无法确认的展示已单列，不把收到请求当作成功。故障／重启的停止目标仍按已确认规则处理；本次确认仅记录设计决定，尚未进行实现或运行验证。

## 评审事项、已决记录与建议

### Q01：生产初始化与重启恢复

**已确认，2026-09-15**：用户选择“每次重启都默认停止，等待管理员重新开启”。不恢复上次管理员设置的运行状态。

- 生产首次启动、整套环境重启后，全部业务组默认停止，核心服务正常运行。
- 单个业务进程重启后，其所属业务组也须回到停止，等待管理员重新开启。依据整组控制 R04，不能仅让重启成员停止而让其余成员继续作为运行组执行业务。
- 单成员重启不自动改变无关业务组的状态；核心服务仍遵守常开分类。
- 旧实例记录、旧启动命令或队列恢复不能在重启后重新开放业务；只有管理员面向当前运行实例的新开启决定才可生效。
- 关闭所属组的过程若尚未完成，仍须按 Q02、Q04 展示停止中或异常，不能因一个成员重启就伪造全组已停止。

本地完整 `make run` 默认停止仍按 R06；独立运行命令、环境启动批次识别和多成员先后重启的协调由技术设计落实，不能给本地全栈引入自动运行的例外。

### Q02：停止时的在途工作与完成标准

**停止原则已确认，2026-09-15**：用户接受“立即拒绝新请求，取消可取消的任务；已提交到外部系统的操作完成必要收尾，期间显示‘停止中’，确认结束后再显示‘已停止’”。

- 停止请求生效后不再接受新的业务读写，也不再领取新的后台业务任务。
- 对能够取消的在途任务发起取消，并等待其结束。
- 对已提交到外部系统的操作完成必要收尾；该许可不用于继续领取任务或执行下一业务步骤。
- 上述过程显示“停止中”；确认业务与必要收尾结束后才显示“已停止”。常驻进程、健康检查和管理通道仍然可用。

**停止超时与未知结果处理已确认，2026-09-15**：用户确认“超过约定时间仍无法确认结束，显示‘停止异常／需处理’；继续禁止新业务，保留常驻进程和管理能力；外部结果不明确就保留‘未知’，不自动重发请求；后续确认收尾结束才显示‘已停止’，重新开启仍由管理员操作”。各业务的具体超时时长在技术设计中确定。

- 达到约定收尾时限仍不能确认结束时，显示异常及原因，不能因计时结束就显示“已停止”。
- 超时后继续拒绝新的业务读写和任务领取，保留常驻进程、健康检查及管理能力，不通过强制终止进程伪造停止完成。
- 外部结果无法确认时如实保留未知事实；不伪造失败，也不自动重发原请求。
- 后续取得收尾完成证据后，才可更新为已停止。状态恢复不自动开启业务，仍须管理员操作。

**技术设计需落实**：逐组确定收尾期限、必要只读对账与结果记录、数据库事务处理及其结束条件，明确哪些证据足以确认业务执行和收尾结束。仅用于结束旧工作的记录不能演变为新的业务执行；外部未知结果本身不能证明本组已停止，也不能被改写为业务成功。这些内容用于落实已确认规则，不再把相同的停止超时策略列为待用户决定事项。

Notification 在 HTTP 起点之后的取消也可能形成 unknown，统一组停止须保留真实结果与未知事实。先前参考的 Worm Run 收尾约束仅作为原有实现记录；Worm 已按 R19 确认删除，不再设计其组停止控制。

### Q03：核心 Notification 中的业务组消息

**已确认，2026-09-15**：用户接受“尚未发送的消息暂停保留；业务重新开启后只发送未过期、仍符合发送条件的消息；已经开始发送的操作完成必要收尾；账户绑定、系统故障等核心通知继续正常发送”。Notification 本身保持运行，停止组不能继续产生新的业务工作。

- **尚未发送**：暂停并保留该组消息，停止期间不发起新的发送请求。即使已经取得内部发送许可，只要尚未真正开始对外发送，也属于暂停范围。
- **重新开启**：管理员开启所属业务组后，重新核对原有时效、收件人资格、绑定与业务条件，只发送仍符合条件的消息。暂停不延长原有有效期；已过期、资格已撤销或已终结的消息不因开启业务组而复活。
- **已经开始发送**：按 R09/Q02 完成必要收尾。停止期间不为这些消息新发起重试；恢复后是否可重试仍受已有结果与资格规则约束，不能把未知结果当作未发送。
- **核心通知**：账户绑定、系统自身故障等核心工作持续运行。按消息业务来源判断归属；通过系统通知接口发送的业务告警仍属于对应业务组，不能仅因名称包含“系统通知”就豁免。

**实现需明确的边界**：现有通知设计区分许可、实际发送起点和结果，不能仅用 `sending` 状态判定已开始发送，也不能仅凭缺失发送起点记录就判定未发送。技术方案需落实停止与发送并发时的控制边界、暂停记录和恢复资格复核，并保持已有结果证据和幂等约束。具体消息的有效期沿用业务规则，缺失规则时需补齐，不能在本轮虚构统一时长。外部结果未知及收尾完成判定仍见 Q02。

通知列表中的该组业务正文和详情也要遵守 R07；保留哪些纯运行信息由 Q06 明确。不能只停止生产者后宣称跨服务工作已停止，也不能为一个业务组停掉全部 Notification。

### Q04：部分失败、失联与跨组依赖

**运行中故障处理已确认，2026-09-15**：用户在 Token 示例说明后接受必需成员故障时暂停整个业务板块，不让剩余成员继续对外提供部分业务。

- 判定某必需成员故障后，关闭整组新的业务读写和后台任务入口；其他成员按 R09 取消可取消任务并完成必要外部收尾，通知按 R10 暂停或收尾。
- 后台显示故障成员与原因。尚未确认组内业务和必要收尾结束时，不显示“已停止”；成员失联不能当作停止已成功的证据。
- 修复故障后等待管理员重新开启整组；进程重新在线或探测恢复成功不会自行恢复业务。
- 核心服务和无关业务组保持各自状态，不因本组故障主动执行联动停止。必需依赖该组的业务组按 R14 处理。
- 此处故障指程序退出或关键能力持续不可用；偶发一次请求超时不直接触发整组停止。具体探测、持续时间、重试和故障判定依据由技术设计明确。

评审示例：假设 Token 的链上处理程序被列为必需成员，持续无法处理新区块时，即使查询 API 还能返回旧数据，也停止整个 Token 板块的业务访问与后台任务，修复后由管理员重新开启。该示例用于解释故障策略，最终必需成员名单仍由 Q05 核对。

**启动时跨组依赖处理已确认，2026-09-15**：用户接受“若 A 必须依赖 B，B 尚未开启时，启动 A 应提示‘请先开启 B’，A 保持停止，由管理员决定是否开启 B”。

- 判定依赖是否开启使用其业务控制状态；B 的进程在线、健康检查通过，不等于 B 的业务已开启。
- 必需依赖组未开启时拒绝 A 的本次启动，列出缺少的依赖，A 不开始执行业务；B 保持其当前状态。
- 管理员开启 B 后，仍需重新发起 A 的启动请求；被拒绝的请求不转成等待依赖恢复的自动启动任务。
- A/B 为规则示例，实际必需依赖关系在 Q05 清单中核对；本次确认不据此新增服务耦合。

**手动停止被依赖组的顺序已确认，2026-09-15**：用户接受“若 A 依赖 B 且两组都在运行，管理员停止 B 时拒绝本次请求，提示‘请先停止 A’；等 A 停止并完成收尾后，再允许停止 B”。

- 拒绝本次停止时，B 保持运行，A 不被自动停止；后台列出所有尚未完成停止和收尾的必需依赖方。
- 管理员先停止 A；A 处于“停止中”且必要收尾未结束时，仍不允许手动停止 B，避免切断收尾所需能力。
- 确认全部依赖方已停止并完成收尾后，管理员重新发起 B 的停止请求，B 再按 R09 处理；被拒绝的停止请求不自动排队执行。
- 本规则约束管理员主动发起的业务停止；真实故障按 R11/R14 处理，不能因为仍有依赖方而阻止故障组关闭业务入口。整套环境关闭继续按既有资源生命周期管理。

**必需依赖故障处理已确认，2026-09-15**：用户接受“若 A 必须依赖 B，B 运行中故障且无法提供所需能力，A 也停止接收业务并完成收尾；后台显示 A 因依赖 B 故障而停止；修复后管理员先开启 B，再开启 A，无关业务组继续运行”。

- 识别必需依赖故障使所需能力不可用后，A 关闭新业务读写和任务入口，按 R09 取消可取消任务并完成必要外部收尾；业务通知按 R10 暂停或收尾。
- 后台区分自身成员故障与依赖故障，明确显示故障依赖组和受影响原因；A 的收尾未确认结束时仍不能提前显示已停止。
- B 修复或进程恢复在线不会自动开启 A；管理员先恢复 B 的业务运行，再重新开启 A。依赖组尚未开启时，A 的启动仍按 R12 拒绝。
- 无关组和核心服务保持各自状态。此规则针对实际必需依赖及其所需能力故障，具体依赖清单和故障判定仍按 Q05 与技术设计核对。

**整组就绪与部分启动失败处理已确认，2026-09-15**：用户接受“全部必需成员就绪后才开放整组业务；任一必需成员启动失败，整组启动失败，停止本次已启动的业务任务并完成收尾，保留常驻进程和失败原因；修复后由管理员重新开启”。

- 全部必需成员就绪前维持业务访问关闭，不能把部分成员就绪当作整组运行。
- 启动失败后，本次已启动的业务任务按 R09 停止并收尾；后台保留失败成员与原因，常驻进程继续提供管理能力。
- 收尾仍未结束时不显示已停止；超过约定时限按 R15 显示停止异常，外部未知结果如实保留。本次收尾不代表撤销已提交的外部操作。
- 修复后等待管理员重新开启，不能因成员恢复或旧启动请求重试自动开放业务；其他业务组和核心服务保持各自状态。

**技术设计需落实**：逐组给出必需成员、就绪条件与确认依据，定义初始化、业务准入和正常任务执行之间的顺序，以及并发失败与停止时的收尾归属。启动准备不成为绕过 R06 默认停止或 R16 整组就绪条件的业务入口。

### Q06：页面、缓存与管理信息边界

**页面规则已确认，2026-09-15**：用户接受以下四类页面表现及 5 秒更新上限。在 R07 已确认的停止后禁止业务数据访问基础上，本次明确页面更新、断线与恢复行为，适用于会员和管理员的业务页面。

| 场景 | 已确认的页面表现 |
| --- | --- |
| 用户正在查看业务页面 | 收到停止状态立即隐藏业务数据；正常联网且页面在前台时，从后端接受停止起最迟 5 秒内更新，显示实际的“停止中”或“已停止”等状态，收尾未结束不能提前显示已停止 |
| 网络断开或无法确认业务状态 | 暂时隐藏业务数据，显示“暂时无法确认服务状态”，不把无法确认误报为已停止 |
| 重新打开页面、切回页面或恢复连接 | 先确认业务处于运行状态，再加载数据，避免先显示旧缓存；重新确认页面状态本身不会开启业务组 |
| 管理员查看控制页面 | 持续提供组状态、成员在线情况、失败原因和最近确认时间；无法取得新状态时明确标注旧信息已过期，不将历史状态显示为当前确认结果 |

**时间与访问边界**：5 秒仅是正常联网、前台页面的更新上限，从后端接受停止操作时起算。后端仍按 R09 在接受停止时立即拒绝新的业务访问，不等待页面刷新；依赖检查拒绝的停止请求不构成已接受停止。断线、后台挂起或尚未重新确认状态的页面遵守上表的隐藏与重新确认规则，不借此继续展示旧业务数据。

**业务与管理信息边界**：停止或无法确认时隐藏的是业务数据。管理员控制信息仍按上表展示，不能通过状态页、通知或聚合页面带出受限制的业务正文。停止异常、启动失败等状态按既定流程如实呈现；无法确认状态不等于业务或进程已停止，也不表示用户登录失效。

**技术设计需落实**：状态更新和失联探测方式、过期判定、逐页管理字段与业务正文映射、浏览器恢复与请求取消，以及缓存和迟到响应的处理。实现需满足已确认的展示边界和时间上限，不让旧响应重新填回已隐藏的数据。已经交付给客户端的数据无法被服务端追溯收回；本要求约束应用展示与后续访问，不宣称撤回用户已保存的离线副本。

### 技术设计需论证的内容

以下属于落实产品规则的设计工作，不单独包装成需要用户逐项批准的技术偏好：

- 控制权限沿用管理员身份边界；如何校验服务调用者，防止内部调用绕过。
- 环境标识、控制状态可靠保存、过期命令与并发操作处理。
- 依赖启停检查与并发命令的一致性，避免接受 B 的停止后仍允许 A 依赖它开始业务；被拒绝的请求不自动排队执行。
- 组内协调、管理通道与业务准入、进程故障和重复启停后的资源归属。
- 必需成员的故障探测、持续时间和重试依据，区分偶发请求失败与关键能力持续不可用；恢复探测不自动开启业务。
- 操作记录至少能够解释谁在何时对哪个环境和业务组作了什么决定、最终结果如何。
- 生产探针如何区分进程故障与正常业务停止，避免把受控停止当成需要重启进程的故障。
- 可配置的收尾期限、状态刷新预算、失败证据和恢复操作。

## 本轮评审结论与文档维护

Q01–Q06 中本轮讨论的产品规则形成 R01–R21 历史需求基线；该整组控制方案已暂停，不能作为当前实施指令。Q05 的[成员、依赖与部署差距清单](service-inventory-review.md)及本地使用五个远端 Gateway 的运行边界仍供核对；D01–D03 仅保留批准历史。Token 的详细接入设计待重构完成后再进行，目标仍以其文档为依据。BSC／Sports 清理与后续 Markets 源码退役分别按各自需求和验收记录执行，不能以本历史基线冒充任何环境的数据删除；Markets 的原 main default 数据和五来源通知结果仍由 Task 10 单列证据。

每次用户作出决定后，在相应 Q 项写入选择和日期，同步状态与验收行；不把评审建议直接改成用户已批准。未来技术方案使用 Superpowers 的规格目录，当前文档继续作为产品规则来源。

当前运行设计、管理员设计与通知设计保留现状说明，只增加本目标需求的关联。Solana 当前暂停与已有运行资源保持原状；本文不执行部署、恢复采集或修改产品代码。
