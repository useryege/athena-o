# Solana 项目研究需求

> 需求状态：讨论中；板块独立性、发行观测后持续研究、活动触发刷新及每项目一小时限频已确认，其余规则正在形成。
>
> 关联技术设计：[新项目发现方案调研](../../design/solana-intelligence/project-discovery.md)、[持续研究与刷新调度](../../design/solana-intelligence/research-lifecycle-and-refresh.md)（均设计中，尚未实现）。

## 背景与目标

ATHENA 需要在现有面向 EVM 生态的 Token 业务之外，新增独立的 Solana 代币项目研究板块。项目从发行开始被系统观测到后，进入研究流程，为用户持续取得和展示项目资料。

Solana 项目与 EVM Token 项目分开组织。两者可以参考相同的研究目标，但发行识别、事实含义和研究生命周期按各自生态设计。

## 已确认决定

- 新增独立 Solana 板块，Solana 代币项目不混入现有 Token 项目。
- 研究从新项目发行被系统观测到开始，不以已交易存量项目查询作为当前主流程。
- 项目持续研究，不因首次买入、Swap、已开始交易或长时间没有活动而自动结束研究。发行后第一天到第十天是持续研究的例子，不是十天到期限制。
- 项目交易或其他被系统识别的链上活动触发状态刷新；具体活动清单尚未确定。
- 按每个项目分别限频，本轮以一小时为刷新间隔：一小时内即使有三四十次活动，最多发起一轮刷新，下一轮至少间隔一小时。不是按自然整点重置次数。
- 先完成独立的需求和设计文档，再推进程序实现。
- 比较 Solana 节点发现与生态特有的发现方式；如果没有更合适的方式，沿用现有“链上发现后开始研究”的思路。具体数据接口和平台覆盖尚未选定。

## 业务术语

| 术语 | 当前含义 |
| --- | --- |
| 新项目发行 | 本板块希望观测的业务起点；对应哪一种链上事实仍需确认 |
| 被系统观测到 | 系统首次获得该发行行为的证据；与链上实际发行时间分别理解 |
| 研究项目 | 纳入本板块研究的 Solana 代币项目；候选代币的纳入规则尚未确定 |
| 发行平台 | 帮助创建代币及组织初期发行的链上平台；是否限制平台范围尚未确定 |
| 项目活动 | 与项目有关、可触发刷新的链上交易或状态变化；具体范围待确认 |
| 项目刷新 | 因发现或活动而取得并更新项目研究资料的一轮工作；包含哪些资料及采集项待确认 |

## 主流程与可见输出

当前已确认的主流程为：新项目发行 → 系统观测 → 开始项目研究 → 持续监控活动 → 按项目限频刷新 → 在独立 Solana 板块组织研究资料。

创建交易内已经发生买入的项目同样进入持续研究。无活动时继续保留项目及监控资格；后续活动仍可触发刷新，无需重新入选或重新开启研究。

一小时限制针对项目资料刷新，不表示每小时才监听一次链上活动。不能用暂停监控来实现刷新限频。EVM Token 的 72 小时观察期、活动续期截止时间、首次 Swap 停止及停止后冻结不适用于本板块。

## 刷新调度建议，尚待细化

以下是为满足活动驱动和限频目标提出的细化方案，不把用户尚未决定的执行语义写为已确认：

- 首次发现立即安排初始采集，不先空等一小时；初始采集开始后纳入同一项目限频。
- 冷却期内出现活动时，合并为一项待刷新需求。冷却到期后安排一次刷新，不要求到期后再有一笔活动，也不为每次活动排队补做。
- 新活动不把已经确定的冷却截止时间向后推；持续活跃的项目不会因不断延后而长期得不到刷新。
- 没有新活动且没有待处理刷新需求时，不因为一小时到了就重复采集；持续监控仍然进行。
- 建议从上一次实际开始刷新计算一小时；同一项目不并行执行多轮刷新。窗口到期表示可以调度，不代表承诺在该时刻完成全部采集。
- 本轮刷新覆盖范围之外的新活动，保留到下一次允许刷新；不能由本轮结果提交误清除。

这些建议的执行边界、异常与恢复见[持续研究与刷新调度](../../design/solana-intelligence/research-lifecycle-and-refresh.md)。

## 当前范围边界

现阶段任务为需求讨论与设计。自动筛选、买入卖出、钱包交易战绩、存量项目导入等能力尚未纳入已确认范围，也未被永久排除。

业务板块独立不预设独立仓库或独立数据库；公共能力复用及服务边界由技术设计根据需求说明。

## 角色与权限

用户需要查看 Solana 项目研究资料。成员与管理员的操作、Solana 是否拥有单独授权项、管理配置范围均待确认，不能直接沿用 Token 授权推导 Solana 权限。

## 待确认问题及其影响

| 问题 | 影响 |
| --- | --- |
| 将新 Mint 初始化、首次发行供应量还是平台创建定义为发现起点？ | 决定入库证据和早期无供应量代币的处理 |
| 首版覆盖哪些 Token 程序和发行平台？如何识别普通代币、NFT、LP 等资产？ | 决定发现覆盖和项目纳入边界；不能把每个新 Mint 直接等同于目标项目 |
| 哪些买卖、转账、供应量或权限变化，以及哪些关联钱包活动触发刷新？ | 决定活动识别范围与刷新负载；列举项是候选，不表示全部已纳入 |
| 需要研究哪些项目、权限、发行方和关联钱包事实？ | 决定采集、分析与页面范围 |
| 发现延迟、初始历史范围、断线补查及数据不完整如何对用户承诺？ | 决定可观察的时效、覆盖与异常行为 |
| 一小时从刷新开始还是结果发布计算？是否开放配置，以及谁能修改？ | 决定限频计时及管理边界；当前建议从实际开始计算 |
| 刷新失败如何重试，失败尝试如何计入限频？初始采集如何计时？ | 决定恢复时效与实际资源用量；不能默认失败重试绕过限频 |
| 冷却期内合并、到期补刷和无活动不采集是否按上述建议细化？ | 决定最后一笔活动能否最终被资料刷新覆盖及空闲成本 |

## 验收方向

以下为从已确认目标导出的验收方向，具体样本及阈值随细化需求补齐：

- 范围内的新项目发行被观测后，能进入 Solana 研究流程。
- 创建时或之后发生买入/Swap 不结束研究；第十天及更晚出现活动仍可触发限频刷新。
- 长时间无活动不会使项目到期或失去监控资格。
- 同一项目一小时内发生三四十次活动，不能发起三四十轮刷新；不同项目分别计时。
- 自然整点不重置冷却：10:59 刷新后，不能仅因到了 11:00 就再次刷新。
- Solana 项目在独立业务入口组织，不混入 EVM Token 项目列表。
- 文档能区分已确认规则、建议方案和未决问题，并与实际实现状态一致。

重复发现、失败交易、资料缺失、断线、刷新失败和冷却到期调度等边界行为的验收预期，需随对应细化规则一起确定。
