# 需求目标设计

`docs/requirements/` 是 ATHENA 业务需求与目标行为的唯一文档根目录，供需求讨论、确认和后续技术设计使用。这里回答“为什么做、为谁做、系统应表现成什么样”，不提前规定组件拆分、数据库表、RPC 字段或其他实现方案。

聊天记录不是跨任务事实来源。凡是会影响后续设计或实现的决定，都必须先写回对应需求文档；只有文档中的状态和内容可以作为下一阶段输入。

## 状态

每份可独立确认的需求文档必须在标题后标记以下状态之一：

| 状态 | 含义 | 允许的下一步 |
| --- | --- | --- |
| `讨论中` | 目标、范围、业务规则或验收行为仍可能变化 | 继续梳理需求；不得据此进入后端技术设计或实现 |
| `已确认` | 目标、范围、业务规则、边界和成功标准已经明确，且没有会改变方案的待确认问题 | 可以开始后端技术设计；仍不构成实现授权 |

业务规则、权限、状态、范围或可观察行为发生实质变化时，必须先将状态退回 `讨论中`，完成修改并由用户重新确认。措辞、排版、错别字或不改变含义的补充不触发回退。

## 确认门槛

需求进入 `已确认` 前，至少应明确：

- 背景、目标和非目标；
- 使用者、角色与权限边界；
- 业务术语、规则和必须保持的不变量；
- 主流程、关键状态变化、异常与边界场景；
- 对外可见的输入、输出和成功标准；
- 已确认决定与待确认问题；待确认问题不得包含会实质改变后端方案的事项。

需求文档可以描述现状问题和外部约束，但不承载后端组件、数据模型、事务、并发或基础设施设计。这些内容在需求确认后写入 [`docs/design/`](../design/README.md)。

## 组织与维护

- 按稳定业务域和能力组织文档，不按日期、聊天、任务、Issue、PR 或版本建立一次性文件。
- 一个大型能力可以拆成多份可独立确认的需求；每份文档单独维护状态。
- 新文档从[需求模板](template.md)开始，并在本索引或所属业务域索引中登记。
- 需求与技术设计必须互相链接。技术设计尚未创建时明确写“未创建”，创建后立即补齐链接。
- 不删除仍然有效的业务规则；发生实质变化时直接更新目标内容，不把聊天或提交历史复制进正文。
