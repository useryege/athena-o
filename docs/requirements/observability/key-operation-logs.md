# 用户关键操作日志需求目标

> 需求状态：已确认。2026-09-18 用户整体审阅通过，包含第一版范围、展示与保留策略；用户要求暂不进入实施。
>
> 关联设计：[技术设计入口](../../design/observability/operation-logs.md)、[详细规格](../../superpowers/specs/2026-09-18-key-operation-logs-design.md)。尚未实施。

## 已确认决定

- 用户需要记录用户行为，并由管理员查看。
- 本次实现“关键操作日志”，不采集普通页面浏览、详情查看或搜索行为。
- 日志暂时无法写入时，用户业务继续；系统尝试补记并向管理员显示日志异常。

## 目标

管理员能够按用户和时间追溯关键操作，理解操作者、动作、对象和观察结果。已受理的异步命令和最终成功必须明确区分，无法确认的结果不能写成成功或确定失败。

## 第一版范围

记录现有登录／注册／退出、账户资料和凭据管理、钱包关键操作、订阅管理、通知设置、Profit Sharing、Worm 及已注册的管理写操作；管理员自身关键操作也记录并与会员区分。API Key 发出的操作归属真实账户。具体动作清单见详细规格，不为记录日志新增业务功能或开启暂停中的模块。

日志仅供有效管理员查看。普通会员、API Key 和未登录用户不可查询全站记录。历史身份、对象标识和结果不会因当前资料变化而被改写；记录管理员对某个账户的修改时，操作者和被操作账户分别展示。

第一版持续保留，不提供日志编辑、删除、导出、统计大屏或自动消息提醒。私钥查看等敏感动作只记录行为与结果，不通过日志提供材料正文。私有备注、密钥、签名、登录令牌和完整业务内容保持原有访问边界。

## 异常与边界

- 身份未验证的失败记录不得归属输入者声称的账户。
- 交易、执行和通知请求受理不代表后续成功；完整后续业务结果继续由对应业务记录提供。
- 日志补记不重复执行用户操作。已保存的记录应能在日志处理恢复后继续展示；从未保存成功的记录可能无法补齐，必须如实反映。
- 日志采集正常、查询可用和历史完整是不同事实。管理员应能看到异常来源、时间及结果未确认的限制。
- 筛选、分页和详情应保持一致；新日志与晚到结果不能让当前翻页重复或跳过记录。权限失效后旧页面数据必须清除。

## 业务验收

1. 用户完成一项关键操作后，管理员能查询到真实账户、动作、对象和准确结果。
2. 失败、拒绝、异步受理、部分完成、取消和未知结果均有准确解释；原业务结果不被日志故障替换。
3. 管理员可按时间、操作者、模块和结果定位记录，在手机和桌面查看完整详情。
4. 日志处理暂时停止后，已保存记录可恢复处理；无法保证补齐的范围保留明确说明。
5. 日志不会绕过原有管理员数据权限，也不会采集本次排除的普通浏览行为。

## 当前执行状态

第一版动作清单（含管理员与已注册管理写操作）、记录字段、管理员查询方式及持续保留策略已随详细设计整体获批。按用户“先不进入实施”的要求，停留在设计阶段，尚未编写实施计划或修改产品代码；恢复工作需遵循用户后续指示。
