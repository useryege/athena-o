# 服务开发规范

本规范适用于新业务服务和服务边界改造。它不把纯解析器、数据转换器或其他只由一个进程内部调用的工具库变成服务；既有实现与本规范的差距不得继续扩大，但无关修复不要求借机重构全部系统。开发任务先阅读根目录 [AGENTS.md](../../AGENTS.md) 和本规范，并在设计与 PR 中按实际变更引用适用规则。

本文中的**必须**表示交付条件，**建议**表示通常应采用并需在不采用时说明理由，**允许**表示满足边界后可选的实现方式。共享仓库、Go module、通用库或经设计确认的共享数据库，都不等于共享进程；本规范不要求每个服务拥有独立数据库、仓库或 Go module。已有经确认的业务协议、事务和技术例外继续以其长期设计为准；新设计必须记录例外的业务依据，本规范不新增审批或工作流。

<a id="sds-r1"></a>
## SDS-R1：服务边界与适用范围

- 新的独立业务能力**必须**有明确的服务所有者（owner）、职责、输入输出和停止边界，并在设计中说明其与 API、存储和相邻服务的关系。
- 持有独立业务状态、持续采集外部事实或执行持续后台业务工作的独立业务能力**必须**运行在独立进程中；不得为了复用 API 进程而把它们作为 API 的后台 goroutine 组合。
- 纯解析器、协议适配器和仅被单一进程调用的内部工具库**允许**保持库形态；不能以“规模小”或“开发早期”作为独立业务能力不拆分的理由。
- 既有同进程实现的差距**必须**在其长期设计中如实说明；无关的小修复**允许**保持现状，但不得新增跨边界反向调用、全局状态或隐式生命周期耦合。

<a id="sds-r2"></a>
## SDS-R2：API 与业务职责

- API 的公共协议、身份/session、协议转换、聚合/facade、健康检查和 housekeeping **允许**留在 API 进程；它们不自动成为独立业务服务。API 不得持有或借用其他服务的 runtime 对象，也不得启动其后台任务。
- 独立业务服务对外或供内部调用的默认同步接口**必须**使用 gRPC，除非设计记录协议选择及其理由。
- 用户请求调用链**必须**传递可信用户 identity；后台或系统请求调用链**必须**传递可信服务身份。两类调用都必须执行内部鉴权；服务的业务权威权限检查仍**必须**在服务自身完成，不能只信任上游已检查。
- 服务不得把数据库 transaction 通过 gRPC 或其他 RPC 边界传递。

<a id="sds-r3"></a>
## SDS-R3：独立构建、启动、测试与停止

- 独立业务服务**必须**能独立构建、部署、配置、启动、测试和有界停止，不以 API、UI 或无关业务服务正在运行作为前提；必要依赖及其启动方式必须在设计和开发文档中列明。
- 服务构建入口**必须**以目标服务和它声明的最小依赖正向选择，不能经由导入无关实现的聚合入口构建。需要完整进程图时，必须显式选择完整栈，而不是由局部入口隐式启动。
- 服务的入口、监听地址、健康或就绪语义、优雅停止和资源所有者**必须**可定位。构建、测试和停止可以复用仓库级工具链，无需独立仓库或 Go module。
- 当前尚未实现的能力不得写成现有命令。新增服务时**必须**提供可验证的局部运行入口；在它实现前，文档只能写为目标能力和所需验证方式。

<a id="sds-r4"></a>
## SDS-R4：配置、凭据与故障隔离

- 每个服务**必须**声明自己读取的配置、凭据、默认值、校验和故障表现；只校验自身及其声明依赖所需的配置，不得依赖其他进程已读取配置后的内存状态，也不得因无关服务配置无效而拒绝启动。
- 服务间 RPC **必须**设置符合调用语义的 deadline、取消和错误传播边界。依赖不可用、配置错误或自身后台任务失败时，服务**必须**给出可观察的健康/就绪或退出语义，并限制影响到自己的职责边界；无关业务服务的故障不得关闭 API。
- 共享数据库或共享基础设施**允许**带来已知共同故障域；设计**必须**说明这个事实及恢复方式，不能把共享误写成故障隔离。

<a id="sds-r5"></a>
## SDS-R5：本地编排与资源所有权

- 局部运行时编排器**必须**以目标服务和声明的最小依赖正向选择，只启动、停止和回收自己创建或明确拥有的进程、容器、端口、临时目录和连接；完整栈必须由显式命令或配置选择。
- 局部停止或清理**禁止**调用全局 reset，也不得删除共享 volume、其他服务数据或不属于本次运行的资源。
- 仓库级 `make run`、`make stop` 和 `make run-reset` 的实际语义以[本地运行编排](../design/development-runtime/local-runtime-orchestration.md)为准；局部服务命令只有在实现后才能列为当前可用命令。

<a id="sds-r6"></a>
## SDS-R6：同库事务与撤权边界

- 同一数据库内、同一原子业务不变量所需的受控 adapter 和事务**允许**保留。adapter 必须明确借用关系，且只有资源 owner 可以关闭连接池或 transaction。
- 原子撤权、资格冻结和发送许可等现有事务边界**不得**为了服务拆分而随意改成异步；需要改变时，设计必须证明新的原子性与失败恢复语义。
- 跨服务协调**必须**使用明确的 RPC、持久状态或其他已设计的协议，不能把 `tx`、连接池或进程内锁跨进程传递。

<a id="sds-r7"></a>
## SDS-R7：设计记录与实施范围

- 服务或边界变更的设计**必须**记录服务所有者（owner）、独立进程与部署、独立入口、必要依赖、配置与授权、事务归属、故障影响和验证证据；不适用项必须说明理由，避免重复填写同一事实。
- 已实现的长期设计必须保留真实源码和验收证据。历史“暂不新增服务进程”等表述若来自原实现决定，**必须**标明它不是今后服务设计的约束。
- 不得为本规范修改历史任务 spec；当前设计只记录事实、目标和差距。

<a id="sds-r8"></a>
## SDS-R8：验证与 PR 证据

- PR **必须**按实际变更填写适用的 `SDS-R1` 至 `SDS-R8`、设计链接和验证证据。独立进程或跨服务契约变更必须提供构建/部署、最小依赖选择、RPC deadline、故障隔离和停止语义的证据。仅文档改动可用链接与静态检查作为验证，不要求运行无关业务测试。
- CLI、UI 或其他消费者因变更而需要调整时，**必须**在同一 PR 完成并按需求验证；没有受影响消费者时说明不适用。不得把已知必需的消费者留给未确定的后续 PR。
- 验证范围**必须**与变更相称：服务边界、授权、事务、停止或故障语义变化时，应覆盖对应行为和失败路径。

## 设计与 PR 快速映射

| 变更内容 | 必须引用的规则 | 证据位置 |
| --- | --- | --- |
| 新业务服务或改造边界 | SDS-R1、R2、R3、R4、R7 | 长期设计的边界、入口、配置、故障和验证章节 |
| 局部运行、停止或清理 | SDS-R3、R5、R8 | 运行文档、资源所有权和停止验证 |
| 同库事务、撤权或跨服务协调 | SDS-R2、R6、R8 | 事务设计、授权路径和失败恢复验证 |
| 文档、CLI、UI 或消费者改动 | SDS-R7、R8 | PR 检查项、受影响消费者和实际验证 |
